## 学習パイプラインをデバッグする[[debugging-the-training-pipeline]]

<Youtube id="L-WSwUWde1U"/>

`trainer.train()` でエラーに遭遇した時の問題は、その原因が複数ありうることです。`Trainer` は通常、データの読み込みから最適化まで、複数の処理をまとめて実行するからです。

データセットをデータローダに変換するので、問題はデータセットの何かが間違っていることかもしれませんし、データセットの要素をバッチにまとめようとした時の問題かもしれません。次に、データのバッチをモデルに投入するので、問題はモデルコードに在るかもしれません。その後、勾配を計算して最適化ステップを実行するので、問題はオプティマイザに在るかもしれません。更に、学習が全て順調に進んでも、指標に問題があれば評価の段階で何かがうまくいかないこともあります。

`trainer.train()` で発生したエラーをデバッグする最良の方法は、このパイプライン全体を手作業でたどり、どこで問題が起きたのかを突き止めることです。そうすれば、エラーはたいてい非常に簡単に解決出来ます。

これを示す為に、[MNLI データセット](https://huggingface.co/datasets/glue)で DistilBERT モデルをファインチューニング（しようと）する次のスクリプトを使います。

```py
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)


trainer = Trainer(
    model,
    args,
    train_dataset=raw_datasets["train"],
    eval_dataset=raw_datasets["validation_matched"],
    compute_metrics=compute_metrics,
)
trainer.train()
```

これを実行すると、かなり不可解なエラーに出迎えられます。

```python out
'ValueError: You have to specify either input_ids or inputs_embeds'
```

### データを確認する[[check-your-data]]

言うまでもありませんが、データが壊れていれば、`Trainer` はバッチを作ることなど出来ず、ましてやモデルを学習させることなど出来ません。ですから、先ず最初に、学習セットの中身を見る必要があります。

バグの発生源ではないものを直そうとして何時間も無駄にするのを避ける為、確認には `trainer.train_dataset` だけを使うことをお勧めします。ここでもそうしましょう。

```py

```

```python out

 'idx': 0,

 'premise': 'Conceptually cream skimming has two basic dimensions - product and geography.'}
```

（データセットの文の訳：前提文は「概念的には、クリームスキミングには製品と地理という2つの基本的な次元が有ります」、仮説文は「製品と地理こそがクリームスキミングを成り立たせるものです」）

何かおかしいことに気づきますか？`input_ids` が欠けているというエラーメッセージと合わせると、これはモデルが理解出来る数ではなくテキストだと分かるはずです。ここでは、元のエラーが非常に誤解を招くものになっています。`Trainer` が、モデルのシグネチャ（つまり、モデルが期待する引数）に一致しない列を自動で削除するからです。つまり、ここではラベル以外の全てが捨てられました。その為、バッチを作ってモデルに送る段階では問題がなく、モデルが適切な入力を受け取っていないと文句を言ったのです。

何故データが処理されなかったのでしょう。データセットに `Dataset.map()` メソッドを使い、各サンプルにトークナイザを適用しました。しかし、コードをよく見ると、`Trainer` に学習セットと評価セットを渡す時に間違いをしていたことが分かります。ここで使うべきは `raw_datasets` ではなく `tokenized_datasets` でした。では、修正しましょう。

### データセットからデータローダへ[[from-datasets-to-dataloaders]]

学習パイプラインで次にうまくいかなくなる可能性が有るのは、`Trainer` が学習セットや検証セットからバッチを作ろうとする時です。`Trainer` のデータセットが正しいと確信出来たら、次のコードを実行して手作業でバッチを作ってみることが出来ます（検証データローダの場合は `train` を `eval` に置き換えます）。

```py
for batch in trainer.get_train_dataloader():
    break
```

このコードは学習データローダを作成し、反復して、最初の反復で停止します。コードがエラーなく実行されれば、検査出来る最初の学習バッチが手に入ります。コードがエラーになれば、問題がデータローダに在ることが確実に分かります。ここでのケースがそうです。

```python out

    106             else:
```

トレースバックの最後のフレームを調べるだけで手がかりは得られるはずですが、もう少し掘り下げてみましょう。バッチ作成中の問題の殆どは、複数のサンプルを1つのバッチにまとめる処理から生じるので、迷った時に最初に確認すべきは、あなたの `DataLoader` が使っている `collate_fn` です。

```py
data_collator = trainer.get_train_dataloader().collate_fn

```


これは `default_data_collator` ですが、今回のケースで望むものではありません。サンプルをバッチ内の最長の文に合わせてパディングしたいのですが、それを行うのは `DataCollatorWithPadding` コレータです。そしてこのデータコレータは、`Trainer` がデフォルトで使うことになっているはずです。では、何故ここでは使われていないのでしょう。

答えは、`Trainer` に `tokenizer` を渡さなかった為、望む `DataCollatorWithPadding` を作成出来なかったからです。実際には、この種のエラーを確実に避ける為、使いたいデータコレータを明示的に渡すことをためらうべきではありません。コードを適応させて、まさにそれを行いましょう。

```py
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    DataCollatorWithPadding,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)


data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

trainer = Trainer(
    model,
    args,
    train_dataset=tokenized_datasets["train"],
    eval_dataset=tokenized_datasets["validation_matched"],
    compute_metrics=compute_metrics,
    data_collator=data_collator,
    tokenizer=tokenizer,
)
trainer.train()
```

よい知らせは、前と同じエラーは出ないことで、これは間違いなく進歩です。悪い知らせは、代わりに悪名高い CUDA エラーが出ることです。

```python out
RuntimeError: CUDA error: CUBLAS_STATUS_ALLOC_FAILED when calling `cublasCreate(handle)`
```

これは、CUDA エラーが一般にデバッグが非常に難しい為、悪いことです。その解決方法は直ぐに見ますが、先ずバッチ作成の分析を終わらせましょう。

データコレータが正しいものだと確信している場合は、データセットのいくつかのサンプルにそれを適用してみるべきです。

```py
data_collator = trainer.get_train_dataloader().collate_fn
batch = data_collator([trainer.train_dataset[i] for i in range(4)])
```

このコードは失敗します。`train_dataset` には文字列の列が含まれていて、通常 `Trainer` がそれらを削除するからです。手作業で削除することも出来ますし、`Trainer` が裏側でやっていることを正確に再現したい場合は、それを行う非公開メソッド `Trainer._remove_unused_columns()` を呼ぶことが出来ます。

```py
data_collator = trainer.get_train_dataloader().collate_fn
actual_train_set = trainer._remove_unused_columns(trainer.train_dataset)
batch = data_collator([actual_train_set[i] for i in range(4)])
```

そうすれば、エラーが続く場合に、データコレータの内部で何が起きているかを手作業でデバッグ出来るはずです。

バッチ作成プロセスをデバッグ出来たので、次はバッチをモデルに通してみましょう。

### モデルに通してみる[[going-through-the-model]]

次のコマンドを実行すれば、バッチが取得出来るはずです。

```py
for batch in trainer.get_train_dataloader():
    break
```

このコードをノートブックで実行している場合、先程見たものと似た CUDA エラーが出ることがあります。その場合は、ノートブックを再起動し、`trainer.train()` の行なしで最後のスニペットを再実行する必要があります。これが CUDA エラーの2番目に厄介な点です。CUDA エラーによって、カーネルが正常に動作しなくなることがあります。最も厄介な点は、デバッグが難しいという事実です。

何故でしょう。それは GPU の動作方法に関係しています。GPU は大量の操作を並列に実行するのが非常に効率的ですが、その欠点は、それらの命令の1つがエラーになっても、直ぐには分からないことです。

プログラムが GPU 上の複数のプロセスの同期を呼んだ時に初めて、何か問題が起きたことに気づく為、実際にエラーの原因となった処理とは無関係に見える場所で、エラーが報告されることがあります。例えば、先程のトレースバックを見ると、エラーは逆伝播の最中に発生しましたが、実際にはフォワードパスの何かが原因だと直ぐに分かります。

では、そのようなエラーをどうデバッグすればよいのでしょう。答えは簡単です。デバッグしません。CUDA エラーがメモリ不足エラー（GPU のメモリが足りないという意味）でない限り、デバッグは常に CPU に戻って行うべきです。

今回のケースでそれを行うには、モデルを CPU に戻し、バッチで呼び出すだけです。`DataLoader` が返すバッチは、まだ GPU に移されていません。

```python
outputs = trainer.model.cpu()(**batch)
```

```python out
~/.pyenv/versions/3.7.9/envs/base/lib/python3.7/site-packages/torch/nn/functional.py in nll_loss(input, target, weight, size_average, ignore_index, reduce, reduction)
   2386         )
   2387     if dim == 2:
-> 2388         ret = torch._C._nn.nll_loss(input, target, weight, _Reduction.get_enum(reduction), ignore_index)
   2389     elif dim == 4:
   2390         ret = torch._C._nn.nll_loss2d(input, target, weight, _Reduction.get_enum(reduction), ignore_index)
```

これで、状況ははっきりしてきました。CUDA エラーの代わりに、今度は損失計算に `IndexError` が出ています（先程言ったように、逆伝播とは関係ありません）。より正確には、ラベル値 2 がエラーの原因になっていると分かるので、モデルのラベルの数を確認する絶好のタイミングです。

```python
trainer.model.config.num_labels
```

```python out
2
```

ラベルが2つでは、ターゲットとして許されるのは0と1だけですが、エラーメッセージによれば2が得られました。2が得られるのは実は普通のことです。前に取り出したラベル名を思い出すと、3つあったので、データセットにはインデックス0、1、2があります。問題は、それをモデルに伝えなかったことです。モデルは3つのラベルで作成すべきでした。では、修正しましょう。

```py
from datasets import load_dataset

model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint, num_labels=3)

    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",

)

    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)

    model,
    args,
    train_dataset=tokenized_datasets["train"],
    eval_dataset=tokenized_datasets["validation_matched"],
    compute_metrics=compute_metrics,
    data_collator=data_collator,
    tokenizer=tokenizer,
)
```

全て問題なさそうか確認する時間を取る為、まだ `trainer.train()` の行は含めていません。バッチを要求してモデルに渡せば、今度はエラーなく動作します。

```py
for batch in trainer.get_train_dataloader():
    break

outputs = trainer.model.cpu()(**batch)
```

次のステップは、GPU に戻し、全てが依然として動作するか確認することです。

```py
import torch

device = torch.device("cuda") if torch.cuda.is_available() else torch.device("cpu")
batch = {k: v.to(device) for k, v in batch.items()}

outputs = trainer.model.to(device)(**batch)
```

まだエラーが出る場合は、ノートブックを再起動し、スクリプトの最後のバージョンだけを実行して下さい。

### 最適化ステップを1回実行する[[performing-one-optimization-step]]

バッチを作って実際にモデルに通せることが分かったので、学習パイプラインの次のステップ、つまり勾配の計算と最適化ステップの実行に進む準備が出来ました。

最初の部分は、損失に対して `backward()` メソッドを呼ぶだけのことです。

```py
loss = outputs.loss
loss.backward()
```

この段階でエラーが出るのはかなりまれですが、もし出たら、有益なエラーメッセージを得る為に CPU に戻って下さい。

最適化ステップを実行するには、`optimizer` を作成し、その `step()` メソッドを呼ぶだけです。

```py
trainer.create_optimizer()
trainer.optimizer.step()
```

繰り返しますが、`Trainer` のデフォルトのオプティマイザを使っている場合は、この段階でエラーは出ないはずですが、カスタムのオプティマイザが有る場合は、ここでデバッグすべき問題があるかもしれません。この段階で奇妙な CUDA エラーが出たら、CPU に戻ることを忘れないで下さい。CUDA エラーと言えば、先程特殊なケースに触れました。次はそれを見てみましょう。

### CUDA のメモリ不足エラーに対処する[[dealing-with-cuda-out-of-memory-errors]]

`RuntimeError: CUDA out of memory` で始まるエラーメッセージが出たら、それは GPU メモリが不足していることを示しています。これはコードに直接関係するものではなく、完璧に動作するスクリプトでも起こりえます。GPU メモリの容量を超えるデータを確保しようとした為、エラーが発生したという意味です。他の CUDA エラーと同様に、学習を再び実行出来る状態にする為に、カーネルを再起動する必要があります。

この問題を解決するには、GPU の使用量を減らすだけです。これは、言うのは簡単でも行うのは難しいことがよくあります。

先ず、GPU 上に2つのモデルが同時に在る状態になっていないか確認して下さい（勿論、問題にそれが必要な場合を除きます）。次に、おそらくバッチサイズを減らすべきです。バッチサイズは、モデルの全ての中間出力とその勾配のサイズに直接影響するからです。問題が続く場合は、モデルのより小さいバージョンの使用を検討して下さい。

> [!TIP]
> コースの次のパートでは、メモリ使用量を削減し、最大級のモデルをファインチューニング出来る、より高度なテクニックを見ていきます。

### モデルを評価する[[evaluating-the-model]]

コードの問題を全て解決したので、全て完璧で、学習はスムーズに進むはずですよね？そう早まってはいけません。`trainer.train()` コマンドを実行すると、最初は全て順調に見えますが、しばらくすると次のようになります。

```py
# これは時間がかかり、エラーで終わります。実行しないでください
trainer.train()
```

```python out
TypeError: only size-1 arrays can be converted to Python scalars
```

このエラーは評価フェーズの最中に現れることに気づくでしょう。ですから、これがデバッグすべき最後のものです。

`Trainer` の評価ループは、学習とは独立に次のように実行出来ます。

```py
trainer.evaluate()
```

```python out
TypeError: only size-1 arrays can be converted to Python scalars
```

> [!TIP]
> エラーにぶつかる前に大量の計算リソースを無駄にするのを避ける為、`trainer.train()` を実行する前に `trainer.evaluate()` を実行出来ることを常に確認して下さい。

評価ループの問題をデバッグしようとする前に、先ずデータを見たことがあり、バッチを適切に作ることが出来、それをモデルで実行出来ることを確認すべきです。これらのステップは全て完了しているので、次のコードはエラーなく実行出来るはずです。

```py
for batch in trainer.get_eval_dataloader():
    break

batch = {k: v.to(device) for k, v in batch.items()}

with torch.no_grad():
    outputs = trainer.model(**batch)
```

エラーが発生するのは、もっと後の評価フェーズの終盤です。トレースバックを見ると、次のようになっています。

```python trace
~/git/datasets/src/datasets/metric.py in add_batch(self, predictions, references)
    431         """
    432         batch = {"predictions": predictions, "references": references}
--> 433         batch = self.info.features.encode_batch(batch)
    434         if self.writer is None:
    435             self._init_writer()
```

これは、エラーが `datasets/metric.py` モジュールに由来することを示しています。つまり、これは私たちの `compute_metrics()` 関数の問題です。この関数は、ロジットとラベルを NumPy 配列として含むタプルを受け取ります。では、それを渡してみましょう。

```py
predictions = outputs.logits.cpu().numpy()
labels = batch["labels"].cpu().numpy()

compute_metrics((predictions, labels))
```

```python out
TypeError: only size-1 arrays can be converted to Python scalars
```

同じエラーが出るので、問題は間違いなくその関数にあります。そのコードを見返してみると、`predictions` と `labels` を `metric.compute()` に転送しているだけだと分かります。では、そのメソッドに問題が有るのでしょうか。そうではありません。形状を手早く見てみましょう。

```py
predictions.shape, labels.shape
```

```python out
((8, 3), (8,))
```

私たちの予測はまだロジットであり、実際の予測ではない為、指標がこの（やや不可解な）エラーを返しています。修正はかなり簡単です。`compute_metrics()` 関数に argmax を追加するだけです。

```py
import numpy as np


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    predictions = np.argmax(predictions, axis=1)
    return metric.compute(predictions=predictions, references=labels)


compute_metrics((predictions, labels))
```

```python out
{'accuracy': 0.625}
```

これでエラーは修正されました。これが最後の1つだったので、スクリプトは今度はモデルを適切に学習させるはずです。

参考の為に、完全に修正されたスクリプトを次に示します。

```py
import numpy as np
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    DataCollatorWithPadding,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint, num_labels=3)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    predictions = np.argmax(predictions, axis=1)
    return metric.compute(predictions=predictions, references=labels)


data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

trainer = Trainer(
    model,
    args,
    train_dataset=tokenized_datasets["train"],
    eval_dataset=tokenized_datasets["validation_matched"],
    compute_metrics=compute_metrics,
    data_collator=data_collator,
    tokenizer=tokenizer,
)
trainer.train()
```

この場合、もう問題は無く、スクリプトは妥当な結果を与えるモデルをファインチューニングするはずです。しかし、学習がエラーなく進むのに、学習されたモデルの性能がまったく良くない場合は、どうすればよいでしょう。それは機械学習で最も難しい部分であり、役立つテクニックをいくつか示します。

> [!TIP]
> 手作業の学習ループを使っている場合は、学習パイプラインをデバッグする為に同じステップが当てはまりますが、分離するのがより簡単です。適切な場所で `model.eval()` や `model.train()` を忘れていないか、各ステップで `zero_grad()` を忘れていないかを確認して下さい。

## 学習中のサイレントエラーをデバッグする[[debugging-silent-errors-during-training]]

エラーなく完了するのに良い結果が得られない学習を、どうデバッグすればよいでしょう。ここではいくつかの手がかりを示しますが、この種のデバッグは機械学習で最も難しい部分であり、魔法のような答えはないことに注意して下さい。

### データを（もう一度！）確認する[[check-your-data-again]]

データから実際に何かを学ぶことが可能でなければ、モデルは何も学習しません。データを壊すバグがあったり、ラベルがランダムに付けられたりしている場合、そのデータセットで学習するモデルはおそらく何も得られません。ですから、常にデコードされた入力とラベルを再確認することから始め、次の質問を自分に投げかけて下さい。

- デコードされたデータは理解出来ますか？
- ラベルに同意出来ますか？
- 他より一般的なラベルはありますか？
- モデルがランダムな答えや常に同じ答えを予測した場合、損失や指標はどうなりますか？

> [!WARNING]
> ⚠️ 分散学習をしている場合は、データセットのサンプルを各プロセスで出力し、各プロセスで同じデータが得られることを念入りに確認して下さい。よくあるバグの1つは、データ作成に何らかのランダム性の源泉があり、各プロセスがデータセットの異なるバージョンを持つことです。

データを見た後は、モデルの予測をいくつかたどり、それらもデコードして下さい。モデルが常に同じものを予測している場合、それはデータセットが或るカテゴリに偏っている為かもしれません（分類問題の場合）。まれなクラスのオーバーサンプリングのようなテクニックが役立つことがあります。

初期モデルの損失や指標が、ランダムな予測に期待する値と大きく異なる場合は、損失や指標の計算方法を再確認して下さい。おそらくそこにバグが有ります。最後に加算する複数の損失を使っている場合は、それらが同じスケールであるか確認して下さい。

データが完璧だと確信したら、モデルがそのデータで学習出来るかどうかを、1つのシンプルなテストで確認出来ます。

### モデルを1つのバッチに過学習させる[[overfit-your-model-on-one-batch]]

過学習は、通常は学習時に避けようとするものです。モデルが、学習してほしい一般的な特徴を認識することを学ぶのではなく、学習サンプルをただ記憶してしまうことを意味するからです。しかし、モデルを同じ1つのバッチで何度も学習させてみるのは、自分が組み立てた問題を、学習させようとしているモデルで解けるかどうかを確認するよいテストです。初期の学習率が高過ぎないかを見る助けにもなります。

`Trainer` を定義したら、これは本当に簡単です。学習データのバッチを1つ取得し、そのバッチだけを使って、20ステップ程度の小さな手作業の学習ループを実行するだけです。

```py
for batch in trainer.get_train_dataloader():
    break

batch = {k: v.to(device) for k, v in batch.items()}
trainer.create_optimizer()

for _ in range(20):
    outputs = trainer.model(**batch)
    loss = outputs.loss
    loss.backward()
    trainer.optimizer.step()
    trainer.optimizer.zero_grad()
```

> [!TIP]
> 学習データが不均衡な場合は、全てのラベルを含む学習データのバッチを必ず作って下さい。

結果のモデルは、同じ `batch` に対してほぼ完璧な結果を示すはずです。結果の予測について指標を計算してみましょう。

```py
with torch.no_grad():
    outputs = trainer.model(**batch)
preds = outputs.logits
labels = batch["labels"]

compute_metrics((preds.cpu().numpy(), labels.cpu().numpy()))
```

```python out
{'accuracy': 1.0}
```

正解率100%。これは過学習の良い例です（つまり、モデルを他のどんな文で試しても、おそらく間違った答えが返ってくるでしょう）。

このテストでモデルがほぼ完璧な結果を出せない場合、それは問題の組み立て方かデータに何か問題が有ることを意味するので、それを修正すべきです。過学習テストに合格して初めて、モデルが実際に何かを学習出来ると確信出来ます。

> [!WARNING]
> ⚠️ このテストの後は、モデルと `Trainer` を再作成する必要があります。得られたモデルは、おそらく回復して、完全なデータセットで有益なものを学習することは出来ないでしょう。

### 最初のベースラインが出るまで何もチューニングしない[[dont-tune-anything-until-you-have-a-first-baseline]]

ハイパーパラメータチューニングは、機械学習で最も難しい部分だと常々強調されますが、それは評価指標を更に改善する為、最後に取り組む調整作業に過ぎません。殆どの場合、`Trainer` のデフォルトのハイパーパラメータで良い結果が十分に得られるので、データセットについて持っているベースラインを上回るものが得られるまで、時間とコストのかかるハイパーパラメータ探索に乗り出さないで下さい。

十分に良いモデルが得られたら、少しずつ調整を始めることが出来ます。異なるハイパーパラメータで千回も実行しようとはせず、1つのハイパーパラメータについて異なる値の実行をいくつか比較して、どれが最も影響が大きいか感触をつかんで下さい。

モデル自体を調整する場合は、シンプルに保ち、合理的に正当化出来ないことは試さないで下さい。変更が意図しない結果を招いていないか確認する為に、過学習テストに常に戻って下さい。
