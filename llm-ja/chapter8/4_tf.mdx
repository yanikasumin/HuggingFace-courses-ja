## 学習パイプラインをデバッグする[[debugging-the-training-pipeline]]

<Youtube id="N9kO52itd0Q"/>

`model.fit()` でエラーが出た場合、原因の候補は複数あります。学習には、それまでに用意したものが全て関わるからです。データセット自体の誤りかもしれませんし、データセットの要素をバッチにまとめる段階の問題かもしれません。モデルのコード、損失関数、オプティマイザのいずれかに原因があることもあります。更に、学習自体は順調でも、指標に問題があれば評価の段階で失敗します。

`model.fit()` のエラーをデバッグするには、パイプライン全体を手作業で順にたどり、どこで問題が起きたのかを突き止めるのが最良の方法です。原因の場所が分かれば、解決はたいてい簡単です。

ここでは、[MNLI データセット](https://huggingface.co/datasets/glue) で DistilBERT モデルをファインチューニングする（しようとする）次のスクリプトを例に使います。

```py
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    TFAutoModelForSequenceClassification,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)

train_dataset = tokenized_datasets["train"].to_tf_dataset(
    columns=["input_ids", "labels"], batch_size=16, shuffle=True
)

validation_dataset = tokenized_datasets["validation_matched"].to_tf_dataset(
    columns=["input_ids", "labels"], batch_size=16, shuffle=True
)

model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)

model.compile(loss="sparse_categorical_crossentropy", optimizer="adam")

model.fit(train_dataset)
```

実行すると、データセットの変換時に `VisibleDeprecationWarning` がいくつか出るかもしれません。これは既知の UX 上の問題です。無視してください。例えば、2021年11月を過ぎてもまだ起きている場合は、@carrigmat 宛てに怒りのツイートを送って直してもらってください。

より深刻な問題は、エラーそのものです。しかも、そのエラーメッセージは非常に長いものです。

```python out
ValueError: No gradients provided for any variable: ['tf_distil_bert_for_sequence_classification/distilbert/embeddings/word_embeddings/weight:0', '...']
```

これは何を意味するのでしょうか。データで学習しようとしたのに、勾配が得られなかったというエラーです。どこから手をつければよいのか分かりにくいエラーです。エラーメッセージから問題の場所が直ぐに分からない場合、最良の方法は、処理を順番にたどり、各段階で全てが正しく見えるかを確認することです。そして、始める場所はいつも……

### データを確認する[[check-your-data]]

データが壊れていれば、Keras が代わりに直してはくれません。まず、学習セットの中身を確認します。

確認する対象は、`raw_datasets` や `tokenized_datasets` ではありません。モデルに入力される直前のデータです。つまり、`to_tf_dataset()` 関数で作成した `tf.data.Dataset` の出力を読みます。`tf.data.Dataset` オブジェクトはバッチ全体を一度に渡すもので、インデックス付けには対応していません。`train_dataset[0]` のようにインデックスで要素を取り出すことは出来ません。但し、次のようにループを使えば最初のバッチを取り出せます。

```py
for batch in train_dataset:
    break
```

`break` は1回の反復でループを終了します。これで、`train_dataset` から出てくる最初のバッチを取得し、`batch` として保存出来ます。次に、その中身を見てみましょう。

一見、正しく見えます。モデルには `labels`、`attention_mask`、`input_ids` を渡しており、出力を計算して損失を算出する為に必要なものは全てそろっているはずです。それでも勾配が得られません。よく見ると、入力として渡しているのは単一の辞書です。通常の学習バッチは、入力テンソル又は辞書と、ラベルテンソルの組み合わせです。ここではラベルが、入力辞書の1つのキーにすぎません。

これは問題になるのでしょうか。常にそうとは限りません。但し、TensorFlow で Transformer モデルを学習する時に遭遇する最も一般的な問題の1つです。

Transformers のモデルは、全て内部で損失を計算出来ます。その為には、ラベルを入力辞書の中に渡す必要があります。`compile()` に損失の値を指定しない場合に使われるのが、この内部の損失です。一方、Keras は通常、ラベルが入力辞書とは別に渡されることを前提としています。そうしないと、損失の計算はたいてい失敗します。

問題ははっきりしてきました。`loss` 引数を渡した以上、損失の計算は Keras に任せています。ところが、ラベルは Keras が期待する場所ではなく、モデルの入力辞書の中に渡しています。どちらかに統一する必要があります。モデルの内部損失を使い、ラベルを今の場所に置いておくか、Keras の損失を使い、ラベルを Keras が期待する場所へ移すかです。ここでは簡単な前者を選びます。`compile()` の呼び出しを次のように変更します。

```py
model.compile(optimizer="adam")
```

これでモデルの内部損失を使うようになり、この問題は解決するはずです。

> [!TIP]
> **やってみましょう。** 追加の課題です。他の問題を解決した後にこのステップに戻り、モデルの内部損失ではなく、Keras 側で損失を計算する元の方法でもモデルを学習させてみてください。その為には、`to_tf_dataset()` の `label_cols` 引数に `"labels"` を追加し、ラベルが正しく出力されるようにする必要があります。そうすれば勾配が得られます。但し、指定した損失にはもう1つ問題があります。この問題があっても学習は進みますが、学習は非常に遅くなり、高い学習損失で頭打ちになります。何が問題か分かりますか？

>
> そして2つ目のヒント：Jura lbh fcrpvsl bcgvzvmref, npgvingvbaf be ybffrf jvgu fgevatf, Xrenf frgf nyy gur nethzrag inyhrf gb gurve qrsnhygf. Jung nethzragf qbrf FcnefrPngrtbevpnyPebffragebcl unir, naq jung ner gurve qrsnhygf?

では、学習を試してみましょう。今度は勾配が得られるはずです。うまくいけば、`model.fit()` を呼ぶだけで全てが順調に進みます。


うまくいきませんでした。

`nan` は、損失の値としては望ましくありません。それでもデータは確認済みで、問題はなさそうに見えます。データが原因でないなら、次に確認する場所は明らかです。次のステップは……

### モデルを確認する[[check-your-model]]

`model.fit()` は非常に便利な関数です。但し、多くの処理を代わりに行う為、問題が正確にどこで起きたのかを見つけにくくなります。モデルをデバッグする時に役立つ方法の1つは、モデルにバッチを1つだけ渡し、その1バッチ分の出力を詳しく見ることです。もう1つの方法は、モデルがエラーを出す場合に、`run_eagerly=True` を指定して `compile()` することです。実行ははるかに遅くなりますが、エラーメッセージは格段に分かりやすくなります。モデルのコードの正確にどこで問題が起きたかを示すからです。

今のところ `run_eagerly` は必要ありません。先程取得した `batch` をモデルに通し、出力がどうなるかを見てみましょう。

```py
model(batch)
```

全てが `nan` です。ロジットまで全て `nan` になるのは奇妙なことです。`nan` は「数ではない（not a number）」を意味します。`nan` は、ゼロ除算のような許されない演算を行った時によく発生します。但し、機械学習で `nan` を扱う際に重要な点が1つあります。この値は_伝播_しがちだということです。数に `nan` を掛けると、出力も `nan` になります。

出力、損失、勾配のどこかに `nan` が入ると、モデル全体に急速に広がります。`nan` がネットワークを逆方向に伝播すると `nan` の勾配が得られます。その勾配で重みの更新を計算すると `nan` の重みが得られ、その重みは更に多くの `nan` の出力を計算します。やがて、ネットワーク全体が `nan` の塊になってしまいます。

こうなると、問題がどこから始まったのかは分かりにくくなります。`nan` が最初に紛れ込んだ場所を、どうやって切り分ければよいのでしょうか。

方法は、モデルを_再初期化_することです。学習を開始した時点で、どこかで `nan` が発生し、モデル全体にすばやく伝播したと考えられます。チェックポイントからモデルを読み込み直し、重みの更新を一切行わずに、どこで `nan` の値が得られるかを確認します。

```py
model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)
model(batch)
```

`nan` のサンプルは、全て同じラベルを持ちます。ラベル2です。これは強い手がかりです。ラベルが2の時にだけ損失が `nan` になるのであれば、モデルのラベルの数を確認すべきです。

```python
model.config.num_labels
```

```python out
2
```

問題が見えてきました。モデルはクラスが2つしかないと認識していますが、ラベルは2まであります。0もクラスなので、クラスは実際には3つです。存在しないクラスの損失を計算しようとした為に、`nan` が生まれました。この設定を変更し、もう一度モデルを学習させてみましょう。

```
model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint, num_labels=3)
model.compile(optimizer='adam')
model.fit(train_dataset)
```

```python out
  869/24543 [>.............................] - ETA: 15:29 - loss: 1.1032
```

学習が進んでいます。もう `nan` はなく、損失も下降しています。但し、下降は僅かです。しばらく見ていると、損失の値が高いまま下がらなくなります。ここで学習を止め、原因として何が考えられるかを検討します。この時点で、データとモデルはどちらも問題ないとかなり確信出来ます。それでもモデルはうまく学習していません。残っているのは何でしょう。今こそ……

### ハイパーパラメータを確認する[[check-your-hyperparameters]]

上のコードを見返しても、ハイパーパラメータらしいものは `batch_size` くらいしか見当たりません。それが原因とは考え難いところです。但し、ハイパーパラメータは常に存在します。見えない場合は、値が何に設定されているかを知らないだけです。

Keras について、重要な点を覚えておいてください。損失、オプティマイザ、活性化関数を文字列で設定すると、それらの_全ての引数がデフォルト値に設定_されます。文字列による指定は便利ですが、重要な設定が隠れてしまうことがあります。十分に注意してください（上の追加課題に取り組む場合は、この点を特によく覚えておいてください）。

このスクリプトでは、引数を文字列で設定しているのはどこでしょうか。当初は損失を文字列で設定していましたが、今はしていません。オプティマイザは文字列で設定しています。ここに何か隠れているかもしれません。[その引数](https://www.tensorflow.org/api_docs/python/tf/keras/optimizers/Adam)を見てみましょう。

目立つのは学習率です。文字列 `'adam'` を使うだけでは、学習率はデフォルトの 0.001、つまり 1e-3 になります。これは Transformer モデルには高過ぎます。一般に、学習率は 1e-5 から 1e-4 の間を試すことをお勧めします。実際に使っている値より10倍から100倍小さい値です。大きな問題と考えられるので、学習率を下げてみましょう。その為には、実際の `optimizer` オブジェクトをインポートする必要があります。ついでに、高い学習率での学習で重みが損傷している場合に備え、チェックポイントからモデルを再初期化します。

```python
from tensorflow.keras.optimizers import Adam

model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)
model.compile(optimizer=Adam(5e-5))
```

> [!TIP]
> 🤗 Transformers から `create_optimizer()` 関数をインポートする方法もあります。これを使えば、正しい重み減衰に加え、学習率のウォームアップと減衰を備えた AdamW オプティマイザが得られます。デフォルトの Adam オプティマイザより少しよい結果が得られることがよくあります。

では、新しい学習率でモデルを学習させてみましょう。

```python
model.fit(train_dataset)
```

```python out
319/24543 [..............................] - ETA: 16:07 - loss: 0.9718
```

今度は損失が着実に下がっています。学習がようやくうまくいっているようです。教訓は明確です。モデルは動作しているのに損失が下がらず、データに問題が無いと確信出来る場合は、学習率や重み減衰のようなハイパーパラメータを確認してください。どちらかを高く設定し過ぎると、学習が「停滞」し、損失が高い値にとどまる可能性が非常に高くなります。

## その他のよくある問題[[other-potential-issues]]

上のスクリプトの問題は一通り扱いました。但し、直面しうる一般的なエラーは他にもあります。（非常に不完全な）リストで見ていきます。

### メモリ不足エラーに対処する[[dealing-with-out-of-memory-errors]]

メモリ不足の分かり易い兆候は、"OOM when allocating tensor" のようなエラーです。OOM は "out of memory" の略です。大規模な言語モデルを扱う時によく起きる問題です。遭遇したら、バッチサイズを半分にして再試行するのがよい方法です。

但し、一部のモデルは_非常に_大きいことに留意してください。例えば、フルサイズの GPT-2 は15億個のパラメータを持ちます。モデルを格納するだけで6 GB のメモリが必要で、勾配用に更に6 GB が必要です。フルサイズの GPT-2 の学習には、使用するバッチサイズにかかわらず、通常20 GB を超える VRAM が必要になります。それだけの VRAM を持つ GPU は殆どありません。`distilbert-base-cased` のような軽量なモデルは、実行がはるかに簡単で、学習もはるかに速くなります。

> [!TIP]
> コースの次のパートでは、メモリ使用量を削減し、最大級のモデルをファインチューニングする為の、より高度なテクニックを扱います。

### Hungry Hungry TensorFlow[[hungry-hungry-tensorflow]]

TensorFlow には、知っておくべき特有の挙動があります。モデルを読み込んだり学習を開始したりすると、GPU メモリの_全て_を確保し、その後、必要に応じて分割して使用します。

これは、PyTorch のような他のフレームワークの動作とは異なります。PyTorch は GPU メモリを予め一括確保せず、CUDA を通じて必要な分だけ確保します。TensorFlow の方式の利点の1つは、メモリが不足した時に有益なエラーを出すことが多く、CUDA カーネル全体をクラッシュさせることなく、その状態から回復出来ることです。但し、重要な欠点もあります。2つの TensorFlow プロセスを同時に実行すると、**大変なことになります**。

Colab で実行している場合は心配いりませんが、ローカルで実行している場合は注意が必要です。特に、ノートブックのタブを閉じても、そのノートブックがシャットダウンするとは限りません。ディレクトリ一覧で実行中のノートブック（緑色のアイコンが付いたもの）を選択し、手動でシャットダウンする必要が有るかもしれません。TensorFlow を使っていたノートブックが実行中のままだと、GPU メモリの大部分を握ったままになります。その状態で新しいノートブックを始めると、非常に奇妙な問題に遭遇することがあります。

以前は動いていたコードで CUDA、BLAS、cuBLAS についてのエラーが出始めたら、この問題が原因であることが非常によくあります。`nvidia-smi` のようなコマンドで確認出来ます。現在のノートブックをシャットダウン又は再起動した時に、メモリの殆どは空いていますか、それともまだ使われていますか。まだ使われているなら、何か他のものがメモリを握っています。


### データを（もう一度！）確認する[[check-your-data-again]]

データから学べることが何もなければ、モデルは何も学習しません。データを壊すバグが有る場合や、ラベルがランダムに付けられている場合は、そのデータセットで学習しても成果は得られません。ここで役立つツールの1つが `tokenizer.decode()` です。`input_ids` を文字列に戻せるので、学習データが教えたいことを教えているかどうかを目で確認出来ます。例えば、上のように `tf.data.Dataset` から `batch` を取得したら、最初の要素を次のようにデコード出来ます。

```py
input_ids = batch["input_ids"].numpy()
tokenizer.decode(input_ids[0])
```

次に、それを最初のラベルと比較出来ます。

```py
labels = batch["labels"].numpy()
label = labels[0]
```

このようにデータを表示出来るようになったら、次の質問を自分に投げかけてみてください。

- デコードされたデータは理解出来ますか？
- ラベルに同意出来ますか？
- 他より一般的なラベルはありますか？
- モデルがランダムな答えや常に同じ答えを予測した場合、損失や指標はどうなりますか？

データを見た後は、モデルの予測もいくつか確認してください。モデルがトークンを出力する場合は、それらもデコードしてみましょう。モデルが常に同じものを予測している場合、データセットが或るカテゴリに偏っていることが原因かもしれません（分類問題の場合）。その場合は、まれなクラスのオーバーサンプリングのようなテクニックが役立ちます。ハイパーパラメータ設定の誤りのような、学習側の問題が原因である場合もあります。

学習前の初期モデルで得た損失や指標が、ランダムな予測に期待する値と大きく異なる場合は、損失や指標の計算方法を再確認してください。おそらくそこにバグが有ります。複数の損失を最後に加算している場合は、それらが同じスケールであるかも確認してください。

データが完璧だと確信したら、モデルがそのデータで学習出来るかどうかを、1つのシンプルなテストで確認出来ます。

### モデルを1つのバッチに過学習させる[[overfit-your-model-on-one-batch]]

過学習は、通常は学習時に避けるべきものです。モデルが、学習してほしい一般的な特徴を認識するのではなく、学習サンプルをただ記憶してしまう状態を指すからです。但し、モデルを同じ1つのバッチで何度も学習させる方法は、自分が組み立てた問題を、学習させようとしているモデルで解けるかどうかを確認するよいテストになります。初期の学習率が高過ぎないかを見る助けにもなります。

`model` を定義した後であれば、手順は簡単です。学習データのバッチを1つ取得し、その `batch` をデータセット全体として扱い、多数のエポックで学習させるだけです。

```py
for batch in train_dataset:
    break

# model.compile() を実行し、オプティマイザを設定済みであることを確認してください。
# 損失や指標を使う場合は、それらも設定してください

model.fit(batch, epochs=20)
```

> [!TIP]
> 学習データが不均衡な場合は、全てのラベルを含む学習データのバッチを必ず作ってください。

結果として、`batch` に対してほぼ完璧な結果が得られ、損失は0（又は使用している損失の最小値）に向かってすばやく下降するはずです。

このテストでモデルがほぼ完璧な結果を出せない場合は、問題の組み立て方かデータに問題が有ります。先にそちらを修正してください。過学習テストに合格して初めて、モデルが実際に何かを学習出来ると確信出来ます。

> [!WARNING]
> ⚠️ この過学習テストの後は、モデルを再作成し、再コンパイルする必要があります。テスト後のモデルは、おそらく回復出来ず、完全なデータセットで有益なものを学習することは出来ないでしょう。

### 最初のベースラインが出るまで何もチューニングしない[[dont-tune-anything-until-you-have-a-first-baseline]]

集中的なハイパーパラメータチューニングは、機械学習で最も難しい部分だとしばしば強調されます。実際には、評価指標を更に改善する為の、最後の調整作業に過ぎません。勿論、デフォルトの Adam の学習率 1e-3 を Transformer モデルに使うような_非常に_悪い値は、学習を非常に遅くしたり、完全に停滞させたりします。但し、殆どの場合、学習率が 1e-5 から 5e-5 のような「妥当な」値であれば、十分によい結果が得られます。データセットのベースラインを上回るものが得られるまでは、時間とコストのかかるハイパーパラメータ探索に乗り出さないでください。

十分によいモデルが得られたら、少しずつ調整を始められます。異なるハイパーパラメータで千回も実行するのではなく、1つのハイパーパラメータについて異なる値の実行をいくつか比較し、どれが最も影響が大きいかを確認してください。

モデル自体を調整する場合は、シンプルに保ち、合理的に正当化出来ないことは試さないでください。変更が意図しない結果を招いていないか確認する為に、過学習テストに常に戻ってください。
