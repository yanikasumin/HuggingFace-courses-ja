学習パイプラインをデバッグする

Chapter 7 のアドバイスにきちんと従って、あるタスク向けにモデルを学習・ファインチューニングするスクリプトを、見事に書き上げました。ところが、trainer.train() コマンドを実行すると、恐ろしいことが起こります。エラーが出るのです 😱。あるいはもっと悪いことに、すべて問題ないように見え、学習はエラーなく進むのに、できあがったモデルがひどい出来になります。このセクションでは、このような問題をデバッグするために何ができるかを示します。

学習パイプラインをデバッグする

trainer.train() でエラーに遭遇したときの問題は、その原因が複数ありうることです。Trainer は通常、データの読み込みから最適化まで、複数の処理をまとめて実行するからです。データセットをデータローダに変換するので、問題はデータセットの何かが間違っていることかもしれませんし、データセットの要素をバッチにまとめようとしたときの問題かもしれません。次に、データのバッチをモデルに投入するので、問題はモデルコードにあるかもしれません。その後、勾配を計算して最適化ステップを実行するので、問題はオプティマイザにあるかもしれません。さらに、学習がすべて順調に進んでも、指標に問題があれば評価の段階で何かがうまくいかないこともあります。

trainer.train() で発生したエラーをデバッグする最良の方法は、このパイプライン全体を手作業でたどり、どこで問題が起きたのかを突き止めることです。そうすれば、エラーはたいてい非常に簡単に解決できます。

これを示すために、MNLI データセットで DistilBERT モデルをファインチューニング（しようと）する次のスクリプトを使います。

from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)


trainer = Trainer(
    model,
    args,
    train_dataset=raw_datasets["train"],
    eval_dataset=raw_datasets["validation_matched"],
    compute_metrics=compute_metrics,
)
trainer.train()

### データを確認する

言うまでもありませんが、データが壊れていれば、`Trainer` はバッチを作ることなどできず、ましてやモデルを学習させることなどできません。ですから、まず最初に、学習セットの中身を見る必要があります。

バグの発生源ではないものを直そうとして何時間も無駄にするのを避けるため、確認には `trainer.train_dataset` だけを使うことをおすすめします。ここでもそうしましょう。

```py
trainer.train_dataset[0]

```python out {'hypothesis': 'Product and geography are what make cream skimming work. ', 'idx': 0, 'label': 1, 'premise': 'Conceptually cream skimming has two basic dimensions - product and geography.'}

何かおかしいことに気づきますか？`input_ids` が欠けているというエラーメッセージと合わせると、これはモデルが理解できる数ではなくテキストだと分かるはずです。ここでは、元のエラーが非常に誤解を招くものになっています。`Trainer` が、モデルのシグネチャ（つまり、モデルが期待する引数）に一致しない列を自動で削除するからです。つまり、ここではラベル以外のすべてが捨てられました。そのため、バッチを作ってモデルに送る段階では問題がなく、モデルが適切な入力を受け取っていないと文句を言ったのです。

なぜデータが処理されなかったのでしょう。データセットに `Dataset.map()` メソッドを使い、各サンプルにトークナイザを適用しました。しかし、コードをよく見ると、`Trainer` に学習セットと評価セットを渡すときに間違いをしていたことが分かります。ここで使うべきは `raw_datasets` ではなく `tokenized_datasets` でした 🤦。では、修正しましょう。

### データセットからデータローダへ

学習パイプラインで次にうまくいかなくなる可能性があるのは、`Trainer` が学習セットや検証セットからバッチを作ろうとするときです。`Trainer` のデータセットが正しいと確信できたら、次のコードを実行して手作業でバッチを作ってみることができます（検証データローダの場合は `train` を `eval` に置き換えます）。

```py
for batch in trainer.get_train_dataloader():
    break

このコードは学習データローダを作成し、反復して、最初の反復で停止します。コードがエラーなく実行されれば、検査できる最初の学習バッチが手に入ります。コードがエラーになれば、問題がデータローダにあることが確実に分かります。ここでのケースがそうです。

```python out ~/git/transformers/src/transformers/data/data_collator.py in torch_default_data_collator(features) 105 batch[k] = torch.stack([f[k] for f in features]) 106 else: --> 107 batch[k] = torch.tensor([f[k] for f in features]) 108 109 return batch

ValueError: expected sequence of length 45 at dim 1 (got 76)

トレースバックの最後のフレームを調べるだけで手がかりは得られるはずですが、もう少し掘り下げてみましょう。バッチ作成中の問題のほとんどは、複数のサンプルを1つのバッチにまとめる処理から生じるので、迷ったときに最初に確認すべきは、あなたの `DataLoader` が使っている `collate_fn` です。

```py
data_collator = trainer.get_train_dataloader().collate_fn
data_collator

```python out <function transformers.data.data_collator.default_data_collator(features: List[InputDataClass], return_tensors='pt') -> Dict[str, Any]>

これは `default_data_collator` ですが、今回のケースで望むものではありません。サンプルをバッチ内の最長の文に合わせてパディングしたいのですが、それを行うのは `DataCollatorWithPadding` コレータです。そしてこのデータコレータは、`Trainer` がデフォルトで使うことになっているはずです。では、なぜここでは使われていないのでしょう。

答えは、`Trainer` に `tokenizer` を渡さなかったため、望む `DataCollatorWithPadding` を作成できなかったからです。実際には、この種のエラーを確実に避けるため、使いたいデータコレータを明示的に渡すことをためらうべきではありません。コードを適応させて、まさにそれを行いましょう。

```py
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    DataCollatorWithPadding,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)


data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

trainer = Trainer(
    model,
    args,
    train_dataset=tokenized_datasets["train"],
    eval_dataset=tokenized_datasets["validation_matched"],
    compute_metrics=compute_metrics,
    data_collator=data_collator,
    tokenizer=tokenizer,
)
trainer.train()

よい知らせは、前と同じエラーは出ないことで、これは間違いなく進歩です。悪い知らせは、代わりに悪名高い CUDA エラーが出ることです。

``python out RuntimeError: CUDA error: CUBLAS_STATUS_ALLOC_FAILED when callingcublasCreate(handle)`

これは、CUDA エラーが一般にデバッグが非常に難しいため、悪いことです。その解決方法はすぐに見ますが、まずバッチ作成の分析を終わらせましょう。

データコレータが正しいものだと確信している場合は、データセットのいくつかのサンプルにそれを適用してみるべきです。

```py
data_collator = trainer.get_train_dataloader().collate_fn
batch = data_collator([trainer.train_dataset[i] for i in range(4)])

このコードは失敗します。train_dataset には文字列の列が含まれていて、通常 Trainer がそれらを削除するからです。手作業で削除することもできますし、Trainer が裏側でやっていることを正確に再現したい場合は、それを行う非公開メソッド Trainer._remove_unused_columns() を呼ぶことができます。

data_collator = trainer.get_train_dataloader().collate_fn
actual_train_set = trainer._remove_unused_columns(trainer.train_dataset)
batch = data_collator([actual_train_set[i] for i in range(4)])

そうすれば、エラーが続く場合に、データコレータの内部で何が起きているかを手作業でデバッグできるはずです。

バッチ作成プロセスをデバッグできたので、次はバッチをモデルに通してみましょう。

モデルに通してみる

次のコマンドを実行すれば、バッチが取得できるはずです。

for batch in trainer.get_train_dataloader():
    break

このコードをノートブックで実行している場合、先ほど見たものと似た CUDA エラーが出ることがあります。その場合は、ノートブックを再起動し、trainer.train() の行なしで最後のスニペットを再実行する必要があります。これが CUDA エラーの2番目に厄介な点です。CUDA エラーによって、カーネルが正常に動作しなくなることがあります。最も厄介な点は、デバッグが難しいという事実です。

なぜでしょう。それは GPU の動作方法に関係しています。GPU は大量の操作を並列に実行するのが非常に効率的ですが、その欠点は、それらの命令の1つがエラーになっても、すぐには分からないことです。プログラムが GPU 上の複数のプロセスの同期を呼んだときに初めて、何か問題が起きたことに気づくため、実際にエラーの原因となった処理とは無関係に見える場所で、エラーが報告されることがあります。たとえば、先ほどのトレースバックを見ると、エラーは逆伝播の最中に発生しましたが、実際にはフォワードパスの何かが原因だとすぐに分かります。

では、そのようなエラーをどうデバッグすればよいのでしょう。答えは簡単です。デバッグしません。CUDA エラーがメモリ不足エラー（GPU のメモリが足りないという意味）でない限り、デバッグは常に CPU に戻って行うべきです。

今回のケースでそれを行うには、モデルを CPU に戻し、バッチで呼び出すだけです。DataLoader が返すバッチは、まだ GPU に移されていません。

outputs = trainer.model.cpu()(**batch)

最適化ステップを1回実行する

バッチを作って実際にモデルに通せることが分かったので、学習パイプラインの次のステップ、つまり勾配の計算と最適化ステップの実行に進む準備ができました。

最初の部分は、損失に対して backward() メソッドを呼ぶだけのことです。

最適化ステップを実行するには、optimizer を作成し、その step() メソッドを呼ぶだけです。

繰り返しますが、Trainer のデフォルトのオプティマイザを使っている場合は、この段階でエラーは出ないはずですが、カスタムのオプティマイザがある場合は、ここでデバッグすべき問題があるかもしれません。この段階で奇妙な CUDA エラーが出たら、CPU に戻ることを忘れないでください。CUDA エラーと言えば、先ほど特殊なケースに触れました。次はそれを見てみましょう。

CUDA のメモリ不足エラーに対処する

RuntimeError: CUDA out of memory で始まるエラーメッセージが出たら、それは GPU メモリが不足していることを示しています。これはコードに直接関係するものではなく、完璧に動作するスクリプトでも起こりえます。GPU メモリの容量を超えるデータを確保しようとしたため、エラーが発生したという意味です。他の CUDA エラーと同様に、学習を再び実行できる状態にするために、カーネルを再起動する必要があります。

この問題を解決するには、GPU の使用量を減らすだけです。これは、言うのは簡単でも行うのは難しいことがよくあります。まず、GPU 上に2つのモデルが同時にある状態になっていないか確認してください（もちろん、問題にそれが必要な場合を除きます）。次に、おそらくバッチサイズを減らすべきです。バッチサイズは、モデルのすべての中間出力とその勾配のサイズに直接影響するからです。問題が続く場合は、モデルのより小さいバージョンの使用を検討してください。

💡 ヒント

コースの次のパートでは、メモリ使用量を削減し、最大級のモデルをファインチューニングできる、より高度なテクニックを見ていきます。

学習中のサイレントエラーをデバッグする

エラーなく完了するのに良い結果が得られない学習を、どうデバッグすればよいでしょう。ここではいくつかの手がかりを示しますが、この種のデバッグは機械学習で最も難しい部分であり、魔法のような答えはないことに注意してください。

データを（もう一度！）確認する

データから実際に何かを学ぶことが可能でなければ、モデルは何も学習しません。データを壊すバグがあったり、ラベルがランダムに付けられたりしている場合、そのデータセットで学習するモデルはおそらく何も得られません。ですから、常にデコードされた入力とラベルを再確認することから始め、次の質問を自分に投げかけてください。

  • デコードされたデータは理解できますか？
  • ラベルに同意できますか？
  • 他より一般的なラベルはありますか？
  • モデルがランダムな答えや常に同じ答えを予測した場合、損失や指標はどうなりますか？

⚠️ 注意

⚠️ 分散学習をしている場合は、データセットのサンプルを各プロセスで出力し、各プロセスで同じデータが得られることを念入りに確認してください。よくあるバグの1つは、データ作成に何らかのランダム性の源泉があり、各プロセスがデータセットの異なるバージョンを持つことです。

データを見た後は、モデルの予測をいくつかたどり、それらもデコードしてください。モデルが常に同じものを予測している場合、それはデータセットがあるカテゴリに偏っているためかもしれません（分類問題の場合）。まれなクラスのオーバーサンプリングのようなテクニックが役立つことがあります。

初期モデルの損失や指標が、ランダムな予測に期待する値と大きく異なる場合は、損失や指標の計算方法を再確認してください。おそらくそこにバグがあります。最後に加算する複数の損失を使っている場合は、それらが同じスケールであるか確認してください。

データが完璧だと確信したら、モデルがそのデータで学習できるかどうかを、1つのシンプルなテストで確認できます。

モデルを1つのバッチに過学習させる

過学習は、通常は学習時に避けようとするものです。モデルが、学習してほしい一般的な特徴を認識することを学ぶのではなく、学習サンプルをただ記憶してしまうことを意味するからです。しかし、モデルを同じ1つのバッチで何度も学習させてみるのは、自分が組み立てた問題を、学習させようとしているモデルで解けるかどうかを確認するよいテストです。初期の学習率が高すぎないかを見る助けにもなります。

Trainer を定義したら、これは本当に簡単です。学習データのバッチを1つ取得し、そのバッチだけを使って、20ステップ程度の小さな手作業の学習ループを実行するだけです。

for batch in trainer.get_train_dataloader():
    break

batch = {k: v.to(device) for k, v in batch.items()}
trainer.create_optimizer()

for _ in range(20):
    outputs = trainer.model(**batch)
    loss = outputs.loss
    loss.backward()
    trainer.optimizer.step()
    trainer.optimizer.zero_grad()

💡 ヒント

💡 学習データが不均衡な場合は、すべてのラベルを含む学習データのバッチを必ず作ってください。

結果のモデルは、同じ batch に対してほぼ完璧な結果を示すはずです。結果の予測について指標を計算してみましょう。

with torch.no_grad():
    outputs = trainer.model(**batch)
preds = outputs.logits
labels = batch["labels"]

compute_metrics((preds.cpu().numpy(), labels.cpu().numpy()))

python out {'accuracy': 1.0}

正解率100%。これは過学習の良い例です（つまり、モデルを他のどんな文で試しても、おそらく間違った答えが返ってくるでしょう）。

このテストでモデルがほぼ完璧な結果を出せない場合、それは問題の組み立て方かデータに何か問題があることを意味するので、それを修正すべきです。過学習テストに合格して初めて、モデルが実際に何かを学習できると確信できます。

⚠️ 注意

⚠️ このテストの後は、モデルと Trainer を再作成する必要があります。得られたモデルは、おそらく回復して、完全なデータセットで有益なものを学習することはできないでしょう。

最初のベースラインが出るまで何もチューニングしない

ハイパーパラメータチューニングは、機械学習で最も難しい部分だと常々強調されますが、それは評価指標をさらに改善するため、最後に取り組む調整作業にすぎません。ほとんどの場合、Trainer のデフォルトのハイパーパラメータで良い結果が十分に得られるので、データセットについて持っているベースラインを上回るものが得られるまで、時間とコストのかかるハイパーパラメータ探索に乗り出さないでください。

十分に良いモデルが得られたら、少しずつ調整を始めることができます。異なるハイパーパラメータで千回も実行しようとはせず、1つのハイパーパラメータについて異なる値の実行をいくつか比較して、どれが最も影響が大きいか感触をつかんでください。

モデル自体を調整する場合は、シンプルに保ち、合理的に正当化できないことは試さないでください。変更が意図しない結果を招いていないか確認するために、過学習テストに常に戻ってください。
