# Module 2：GitHub Actions 連携

## 静かな失敗の襲来

CodeCraft Studios での2週目。Module 1 の PR Agent は、既に開発者がより良いプルリクエストを書く手助けをしています。Sarah の最新の PR は明確な説明のお陰で、Mike の調査時間を20分節約しました。チームは大喜びです。

しかし、その時災難が襲います。

金曜の午後、重大なバグが本番環境に到達しました。決済システムがダウンし、顧客から苦情が寄せられ、チームは慌てて調査に乗り出します。緊張の続く2時間の調査を経て、根本原因が判明しました。火曜日の CI 実行でテストが失敗していたことに、誰も気づいていなかったのです。

「どうして見逃したんだ？」チームリーダーは GitHub Actions をスクロールしながら尋ねます。「テストが失敗していたのは明らかだ。でも47ものリポジトリと毎日数十のコミットが有る中で、全てのビルドを確認する時間なんて誰に有る？」

チームは、CI/CD パイプラインの状態をリアルタイムで把握する必要が有ると気づきます。しかし、全てのプロジェクトの GitHub Actions を手動で確認する方法では、プロジェクト数が増えると対応しきれません。問題を監視し、即座に知らせてくれる自動化が必要です。

**あなたのミッション**：MCP サーバーに webhook 機能を追加して GitHub Actions を監視し、二度と失敗を見逃さないようにすることです。

## 構築するもの

このモジュールは、静的なファイル分析（Module 1）と動的なチーム通知（Module 3）の橋渡しをします。PR Agent を包括的な開発モニタリングシステムへと変える、リアルタイム機能を追加します。

Module 1 で作った基盤の上に、以下を追加します。
- GitHub Actions イベントを受信する **Webhook サーバー**
- CI/CD ステータスを監視する**新しいツール**
- 一貫したワークフローパターンを提供する **MCP Prompts**
- GitHub リポジトリとの**リアルタイム連携**

**リアルタイムな MCP の魔法**：Claude は3つの重要なリクエストに応答します。
- **"What GitHub Actions events have we received?"**：Claude が新しいツールを使って最近のアクティビティを確認する
- **"Analyze CI Results"**：Claude がテストの失敗を掘り下げ、実用的な洞察を提供する様子を見る
- **"Create Deployment Summary"**：MCP Prompts が、チーム向けの分かり易い更新の作成を Claude に案内する様子を見る

**静かな失敗はもう終わり**：火曜日の失敗したテストにあった、あの重大なバグを覚えていますか？このシステムがあれば、Claude は即座に捕えていたはずです。スクリーンキャストでは、MCP サーバーが GitHub の生の webhook データを、明確で実用的なアラートに変換する様子をまさに示しています。

**何が特別なのか**：Module 1 の PR Agent は静的な仕組みで、依頼された時にだけコードを分析していました。

一方、Module 2 で追加する機能は動的です。CI/CD パイプラインを24時間体制で監視し、Claude がリアルタイムで状況を分析出来るようにします。金曜の午後になって突然、重大な問題が発覚するような事態も防げます。

## 主要概念

### MCP Prompts

Prompts は、Claude が複雑なワークフローに沿って作業出来るようにする、再利用可能なテンプレートです。Tools（Claude が自動的に呼び出す）とは異なり、Prompts はユーザーが呼び出すもので、作業を進める為の構造化された指示を提供します。

使用例：
- CI/CD の結果を一貫して分析する
- 標準化されたデプロイ要約を作成する
- 失敗を体系的にトラブルシューティングする

### Webhook 連携

MCP サーバーでは2つのサービスを実行します。
1. MCP サーバー（Claude と通信する）
2. ポート 8080 の webhook サーバー（GitHub イベントを受信する）

これにより、Claude はリアルタイムの CI/CD イベントに反応出来ます。

> [!TIP]
> **アーキテクチャの洞察**：MCP 通信と webhook 処理を別々のサービスに分けることで、それぞれの責務を明確に分離出来ます。webhook サーバーが複雑な HTTP 処理を担当し、MCP サーバーはデータ分析と Claude との連携に集中します。

## 実装ステップ

### ステップ1：Webhook サーバーをセットアップして実行する

既存のファイルを扱った Module 1 とは異なり、このモジュールではリアルタイムのイベント処理を導入します。スターターコードには以下が含まれています。
- **あなたの Module 1 の実装**：既存の PR 分析ツール全て
- **完全な webhook サーバー**（`webhook_server.py`）：GitHub イベントを受信する準備が出来ている

1. 依存関係をインストールする（Module 1 と同じ）：
   ```bash
   uv sync
   ```

2. webhook サーバーを起動する（別のターミナルで）：
   ```bash
   python webhook_server.py
   ```

このサーバーは GitHub の webhook を受信し、`github_events.json` に保存します。

**webhook イベントの保存の仕組み：**
- 受信した各 GitHub webhook（push、pull request、ワークフロー完了など）は JSON ファイルに追加される
- イベントはタイムスタンプ付きで保存され、最近のアクティビティを見つけ易い
- ファイルは、MCP ツールが読み取って分析出来るシンプルなイベントログとして機能する
- データベースは不要で、全てのイベントをシンプルで読み易い JSON 形式で保存する

### ステップ2：イベントストレージに接続する

次に、MCP サーバー（Module 1 のもの）を webhook データに接続します。これは HTTP リクエストを直接処理するよりもはるかに簡単です。webhook サーバーが面倒な処理を全て担い、イベントを JSON ファイルに保存してくれるからです。

webhook イベントを読み取る為のパスを追加します。

```python
# webhook サーバーがイベントを保存するファイル
EVENTS_FILE = Path(__file__).parent / "github_events.json"
```

webhook サーバーが HTTP の詳細を全て処理します。あなたは JSON ファイルを読むだけです。この関心の分離により、MCP サーバーは最も得意なことに集中出来ます。

> [!TIP]
> **開発のヒント**：HTTP リクエストの代わりにファイルを使うと、テストがはるかに簡単になります。webhook をセットアップしなくても、`github_events.json` に手動でイベントを追加してツールをテスト出来ます。

### ステップ3：GitHub Actions ツールを追加する

Module 1 ではファイル分析用のツールを作りましたが、今度は CI/CD 分析用のツールを作ります。これらのツールは既存の PR 分析ツールと連携して動作し、Claude がコードの変更内容とビルドの状態をまとめて把握出来るようにします。

> [!TIP]
> **注意**：スターターコードには Module 1 の出力制限の修正が既に含まれている為、トークン上限エラーには遭遇しません。このモジュールの新しい概念に集中してください！

2つの新しいツールを実装します。

1. **`get_recent_actions_events`**： 
   - `EVENTS_FILE` から読み取る
   - 新しいイベントから順に、指定された上限件数まで返す
   - ファイルが存在しない場合は空のリストを返す

2. **`get_workflow_status`**： 
   - ファイルから全てのイベントを読み取る
   - `workflow_run` イベントでフィルタする
   - ワークフロー名でグループ化し、最新のステータスを表示する

これらのツールにより、Claude は CI/CD パイプラインを分析出来ます。

### ステップ4：MCP Prompts を作成する

次に、初めての MCP Prompts を追加します。Tools（Claude が自動的に呼び出す）とは異なり、Prompts はユーザーが Claude と一貫してやり取りする為のテンプレートです。複雑なワークフローを Claude に案内する「会話のきっかけ」と考えてください。

Module 1 がデータアクセスの為の Tools に焦点を当てたのに対し、このモジュールではワークフローガイダンスの為の Prompts を導入します。

異なるワークフローパターンを示す、4つのプロンプトを実装します。

1. **`analyze_ci_results`**：包括的な CI/CD 分析
2. **`create_deployment_summary`**：チーム向けの分かり易い更新
3. **`generate_pr_status_report`**：コードと CI を組み合わせたレポート
4. **`troubleshoot_workflow_failure`**：体系的なデバッグ

各プロンプトは、Claude が従うべき明確な指示を含む文字列を返すようにします。

### ステップ5：Cloudflare Tunnel でテストする

いよいよ楽しい部分です。拡張した MCP サーバーを、実際の GitHub イベントでテストします。実際の開発環境と同じように、複数のサービスを同時に実行します。

1. MCP サーバーを起動する（Module 1 と同じコマンド）：
   ```bash
   uv run server.py
   ```

2. 別のターミナルで Cloudflare Tunnel を起動する：
   ```bash
   cloudflared tunnel --url http://localhost:8080
   ```

3. トンネル URL で GitHub の webhook を設定する

4. プロンプトを使って Claude Code でテストする

## よくある問題

### Webhook がイベントを受信しない
- Cloudflare Tunnel が動いているか確認する
- GitHub の webhook 設定を確認する（最近の配信が表示されるはず）
- ペイロード URL に `/webhook/github` が含まれているか確認する

### プロンプトが動作しない
- FastMCP のプロンプトは単に文字列を返すだけです
- 関数が `@mcp.prompt()` でデコレートされているか確認する

### Webhook サーバーの問題
- webhook_server.py が別のターミナルで動いているか確認する
- ポート 8080 が空いているか確認する：`lsof -i :8080`
- イベントファイルは、最初のイベントを受信した時に自動で作成される
