# 通信プロトコル

MCP は、クライアントとサーバーが一貫した予測可能な方法でメッセージを交換出来る、標準化された通信プロトコルを定義しています。この標準化は、コミュニティ全体の相互運用性にとって極めて重要です。この節では、MCP で使われるプロトコルの構造とトランスポート機構を探ります。

> [!WARNING]
> ここからは、MCP プロトコルの詳しい仕組みを説明します。MCP を使ってアプリケーションを開発する際に、全ての詳細を知っておく必要はありませんが、どのような仕組みがあるのかを理解しておくと役立ちます。

## JSON-RPC：基盤

MCP では、クライアントとサーバー間の全ての通信において、メッセージ形式として **JSON-RPC 2.0** を使用します。JSON-RPC は、JSON 形式でデータをやり取りする軽量なリモートプロシージャコール（RPC）プロトコルで、次の特徴があります。

- 人が読み易く、デバッグもし易い
- 特定のプログラミング言語に依存せず、様々な開発環境で実装出来る
- 仕様が明確に定められており、幅広く利用されている

![メッセージの種類](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/5.png)

プロトコルは3種類のメッセージを定義しています。

### 1. リクエスト（Requests）

操作を開始する為にクライアントからサーバーへ送信されます。リクエストメッセージには次が含まれます。
- 一意の識別子（`id`）
- 呼び出すメソッド名（例：`tools/call`）
- メソッドのパラメータ（有る場合）

リクエストの例：

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "tools/call",
  "params": {
    "name": "weather",
    "arguments": {
      "location": "San Francisco"
    }
  }
}
```

### 2. レスポンス（Responses）

リクエストへの返信としてサーバーからクライアントへ送信されます。レスポンスメッセージには次が含まれます。
- 対応するリクエストと同じ `id`
- `result`（成功の場合）又は `error`（失敗の場合）のいずれか

成功レスポンスの例：
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "result": {
    "temperature": 62,
    "conditions": "Partly cloudy"
  }
}
```

エラーレスポンスの例：
```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "error": {
    "code": -32602,
    "message": "Invalid location parameter"
  }
}
```

### 3. 通知（Notifications）

レスポンスを必要としない一方通行のメッセージです。通常、イベントに関する更新や通知を提供する為にサーバーからクライアントへ送信されます。

通知の例：
```json
{
  "jsonrpc": "2.0",
  "method": "progress",
  "params": {
    "message": "Processing data...",
    "percent": 50
  }
}
```

## トランスポート機構

JSON-RPC はメッセージフォーマットを定義しますが、MCP はこれらのメッセージをクライアントとサーバー間でどう運ぶかも規定しています。2つの主要なトランスポート機構がサポートされています。

### stdio（標準入出力）

stdio トランスポートは、クライアントとサーバーが同じマシン上で動作するローカル通信に使われます。

ホストアプリケーションはサーバーをサブプロセスとして起動し、その標準入力（stdin）に書き込み、標準出力（stdout）から読み取ることで通信します。

> [!TIP]
> このトランスポートの主な用途は、ファイルシステムへのアクセスやローカルスクリプトの実行など、ローカルツールの利用です。

このトランスポートの主な**利点**は、シンプルで、ネットワーク設定が不要であり、オペレーティングシステムによって安全にサンドボックス化されることです。

### HTTP + SSE（Server-Sent Events）と Streamable HTTP

HTTP+SSE トランスポートは、クライアントとサーバーが異なるマシン上にある可能性が有るリモート通信に使われます。

通信は HTTP で行われ、サーバーは Server-Sent Events（SSE）を使って永続的な接続越しにクライアントへ更新をプッシュします。

> [!TIP]
> このトランスポートの**ユースケース**は、リモート API、クラウドサービス、共有リソースへの接続です。

このトランスポートの主な**利点**は、ネットワーク越しに動作し、Web サービスとの統合を可能にし、サーバーレス環境と互換性が有ることです。

MCP 標準の最近のアップデートでは「Streamable HTTP」が導入・改良されています。これにより、サーバーは必要に応じて SSE によるストリーミングへ動的にアップグレード出来、サーバーレス環境との互換性を保ちながら、より柔軟な運用が可能になります。

## プロトコルの進化

MCP プロトコルは、拡張可能で適応性の有る設計になっています。初期化フェーズにはバージョンネゴシエーションが含まれており、プロトコルの進化に伴う後方互換性が確保されます。更に、機能の発見（capability discovery）により、クライアントは各サーバーが提供する具体的な機能に適応出来、同じエコシステム内で基本的なサーバーと高度なサーバーを混在させることが出来ます。
