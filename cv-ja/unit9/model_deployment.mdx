# モデルデプロイの検討事項

この章では、機械学習モデルをデプロイする時に考えるべきことを説明します。様々なデプロイ先の特徴や、シリアライゼーション、パッケージング、サービングといった重要な処理、適切なデプロイ戦略まで、幅広く取り上げます。

## 様々なデプロイプラットフォーム
- **クラウド**：AWS、Google Cloud、Azure などのクラウドプラットフォームを利用すると、規模の拡張に対応出来る堅牢なインフラ上に AI モデルをデプロイ出来ます。これらのプラットフォームはモデルをホスティングする為のマネージドサービスを提供しており、必要に応じて規模を拡張出来るほか、柔軟な運用や他のクラウドサービスとの連携も可能です。<br />
    - **利点**
        - クラウドデプロイは、高い計算能力、豊富なメモリリソース、マネージドサービスによるスケーラビリティを提供します。
        - クラウドエコシステムとの統合により、様々なクラウドサービスとシームレスに連携出来ます。

    - **検討事項**
        - インフラの利用にどれくらい費用がかかるかを評価する必要があります。
        - データのプライバシーを保護すると共に、リアルタイムアプリケーションではネットワークの遅延を適切に管理する必要があります。

- **エッジ**：IoT デバイス、エッジサーバー、組み込みシステムなどにモデルをデプロイすると、クラウドサービスに頼らず、デバイス側でモデルを実行出来ます。これにより、リアルタイム処理が可能になり、クラウドへ送信するデータも最小限に抑えられます。
    - **利点**
        - ローカルデプロイによる低レイテンシとリアルタイム処理能力。
        - データの送信量を減らし、オフラインでも動作出来る為、プライバシー保護と性能の向上につながります。

    - **課題**
        - 計算能力とメモリの面でリソースが限られていることが課題となります。
        - ハードウェアの制限を考慮し、制約のある環境向けに最適化することが重要です。

- エッジデプロイは、クラウドに関連する場面だけで使われるものではありません。ユーザーに近い場所や、ネットワーク接続が不安定な地域でモデルを実行出来るようにすることを重視しています。
- エッジデプロイでは、モデルを別の場所（クラウドなど）で訓練し、エッジデバイス向けに最適化します。その際、小さなデバイス向けにモデルパッケージのサイズを削減することがよくあります。

- **モバイル**：スマートフォンなどにモデルをデプロイする場合は、デバイスの性能やリソースの制約に合わせてモデルを最適化します。[Core ML](https://developer.apple.com/documentation/coreml)（iOS 向け）や [TensorFlow Mobile](https://www.tensorflow.org/mobile)（Android と iOS 向け）などのフレームワークを使うと、モバイル端末へのデプロイが容易になります。

## モデルのシリアライゼーションとパッケージング

- **シリアライゼーション**：シリアライゼーションとは、機械学習モデルのような複雑なオブジェクトを、保存や送信がし易い形式に変換することです。立体パズルを2次元の画像に変換するようなものです。変換したデータは、ディスクに保存したり、ネットワーク経由で送信したり、データベースに格納したり出来ます。
    - **ONNX（Open Neural Network Exchange）**：ONNX は、機械学習モデルの為の万能翻訳機のようなものです。TensorFlow、PyTorch、scikit-learn といった異なるフレームワークが、互いのモデルを理解し扱えるようにする形式です。全てのフレームワークが話せる共通言語を持つようなものです。
        - PyTorch の `torch.onnx.export()` 関数を使うと、PyTorch モデルを ONNX 形式に変換出来、異なるフレームワーク間でモデルを利用し易くなります。
        - TensorFlow は、グラフを固定（freeze）し、`tf2onnx` のようなツールを使って ONNX 形式に変換する方法を提供します。

- **パッケージング**：一方、パッケージングは、機械学習モデルに必要な全てのコンポーネントと依存関係を束ねることです。パズルのピースを全て箱に入れ、組み立て方の説明書も一緒に入れるようなものです。パッケージングには、シリアライズされたモデルファイル、前処理・後処理のコード、必要なライブラリや依存関係など、モデルの実行に必要な全てが含まれます。

- クラウド向けにモデルをパッケージングする場合、シリアライゼーション自体は特定のデバイスに依存しません。シリアライズしたモデルは、Docker などのコンテナにまとめたり、Flask や FastAPI などを使った Web サービスとしてデプロイしたりするのが一般的です。クラウドへのデプロイでは、オートスケーリングやロードバランシング、他のクラウドサービスとの連携も考慮します。

- 機械学習モデルをデプロイする比較的新しい方法として、🤗 [Inference Endpoints](https://huggingface.co/inference-endpoints) が提供する専用のフルマネージドインフラを利用する方法もあります。これを使えば、コンテナや GPU を直接管理しなくても、Transformers、Diffusers、その他のあらゆるモデルを簡単にデプロイ出来ます。セキュリティやコンプライアンスに対応した柔軟な本番運用環境が用意されており、数回のクリックでデプロイ出来ます。

## モデルのサービングと推論

- **モデルサービング**：訓練してパッケージングしたモデルを公開し、推論リクエストを受け付けられるようにすることです。
    - HTTP REST API：HTTP エンドポイント経由でモデルを公開すると、クライアントは入力データを添えてリクエストを送信し、予測結果を受け取れます。Flask、FastAPI、TensorFlow Serving などのフレームワークを使うと、この仕組みを簡単に実装出来ます。

    - gRPC（Remote Procedure Call）：gRPC は、機械学習モデルをサービングする為の、高性能で言語に依存しないフレームワークを提供します。クライアントとサーバー間の効率的な通信を可能にします。

    - クラウドベースのサービス：AWS、Azure、GCP などのクラウドプラットフォームは、機械学習モデルのデプロイやサービングに使えるマネージドサービスを提供しています。これらを利用すると、規模の拡張や保守が容易になります。
- **推論**：推論とは、デプロイ済みのモデルに新しいデータを入力し、予測結果などを生成することです。推論処理では、サービング用のインフラを利用してモデルを実行し、予測結果を提供します。

    - モデルの使用：推論システムは、サービングシステムから受け取ったデータをデプロイ済みのモデルに入力し、予測結果などを生成します。

    - クライアントとのやり取り：クライアントはサービングシステムに入力データを送り、予測結果や推論結果を受け取ります。これで、モデルを利用する一連の処理が完了します。


- **Kubernetes**：[Kubernetes](https://kubernetes.io/docs/home/) は、アプリケーションのデプロイと管理に広く使われるオープンソースのコンテナオーケストレーションプラットフォームです。Kubernetes を理解すると、モデルをスケーラブルで信頼性の高い方法でデプロイするのに役立ちます。

## 本番環境へのデプロイのベストプラクティス
- **MLOps** は、DevOps の考え方を機械学習プロジェクトに取り入れた、比較的新しい取り組みです。モデルを本番環境にデプロイする為のベストプラクティスとして、バージョン管理、継続的インテグレーション、継続的デプロイ、モニタリング、自動化などを扱います。
- **負荷テスト**：様々なワークロードをシミュレーションし、異なる条件下でのモデルの応答性を確認します。
- **異常検出**：モデルの振る舞いや性能の逸脱を検出するシステムを実装します。
    - 例：*分布シフト（Distribution shift）* は、新しく入力されるデータの統計的な性質が、モデルの訓練に使ったデータのものと大きく異なる状態を指します。分布シフトが起こると、モデルの精度や性能が低下することがあります。その為、こうした変化をリアルタイムで検出し、影響を抑える為の異常検出の仕組みが重要です。
- **リアルタイムモニタリング**：ツールを活用し、デプロイされたモデルの問題を即座に特定します。
    - リアルタイムモニタリングツールを使うと、予測エラーの急増や入力データの異常なパターンを検出し、原因の調査や迅速な対応につなげる為のアラートを出せます。

- **セキュリティとプライバシー**：推論中と送信中のデータを保護する為に暗号化手法を採用します。厳格なアクセス制御を確立し、モデルへのアクセスを制限してデータプライバシーを確保します。
- **A/B テスト**：本格的なデプロイの前に、A/B テストで新しいモデルのバージョンを既存のものと比較評価します。
    - A/B テストでは、モデルの2つのバージョンを同時にデプロイし、トラフィックの一部をそれぞれに振り向けます。精度やユーザーエンゲージメントといった性能指標を比較し、どちらのモデルバージョンが優れているかを判断します。
- **継続的な評価**：デプロイ後もモデルの性能を継続的に評価し、問題が発生した場合は迅速にロールバック出来るよう準備します。
- モデルのアーキテクチャ、依存関係、性能指標などを詳しく記録し、最新の状態に保ちます。
