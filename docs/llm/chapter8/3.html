フォーラムで助けを求める

Hugging Face フォーラムは、オープンソースチームや Hugging Face コミュニティ全体から助けを得るのに最適な場所です。メインページは、日によって多少の違いはありますが、次のような見た目をしています。

左側には、様々なトピックが分類されているカテゴリが全て表示され、右側には最新のトピックが表示されます。トピックとは、タイトル、カテゴリ、説明を含む投稿のことです。

Chapter 5 で自分のデータセットを作った時に見た GitHub の Issue の形式とよく似ています。名前の通り、Beginners カテゴリは主に、Hugging Face のライブラリやエコシステムを使い始めたばかりの人を対象としています。コードのデバッグであれ、何かのやり方を尋ねるのであれ、どのライブラリについての質問でも歓迎されます（但し、質問が特定のライブラリに関するものであれば、フォーラムの対応するライブラリカテゴリへ行くのがよいでしょう）。

同様に、Intermediate カテゴリと Research カテゴリは、ライブラリについての高度な質問や、議論したい面白い新しい NLP 研究など、より進んだ質問の為のものです。

そして勿論、Hugging Face コースについてなら、どんな質問でも投稿出来る Course カテゴリも紹介しておきましょう。

カテゴリを選んだら、最初のトピックを書く準備は完了です。書き方のガイドラインがフォーラムにあります。このセクションでは、よいトピックを構成するいくつかの特徴を見ていきます。

よいフォーラム投稿の書き方

題材として、カスタムの検索エンジンを作る為に、Wikipedia の記事から埋め込みを生成しようとしている場面を考えましょう。いつものように、トークナイザとモデルを次のように読み込みます。

from transformers import AutoTokenizer, AutoModel

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)
model = AutoModel.from_pretrained(model_checkpoint)

python output IndexError: index out of range in self

おっと、問題が発生しました。しかもエラーメッセージは、セクション2で見たものよりずっと不可解です。トレースバック全体を見てもさっぱり分からないので、Hugging Face フォーラムに助けを求めることにします。トピックはどう組み立てればよいでしょうか。

まず、右上隅に在る「New Topic」ボタンをクリックする必要があります（トピックを作成するにはログインが必要です）。

すると、トピックのタイトルを入力し、カテゴリを選択し、内容を作成出来る入力画面が表示されます。

エラーは 🤗 Transformers だけに関係しているようなので、カテゴリにはこれを選びます。問題を説明する最初の試みは、次のようなものになるかもしれません。

このトピックには助けが必要なエラーメッセージが含まれていますが、書き方にはいくつか問題があります。

  1. タイトルがあまり説明的ではない為、フォーラムを眺めている人は本文も読まなければトピックの内容が分かりません。
  2. 本文には、エラーが_どこから_来ているのか、_どうすれば_再現出来るのかの情報が不足しています。
  3. 何人かに直接タグ付けしていて、やや要求の強い口調になっています。

このようなトピックは、速い回答が得られそうにありません（そもそも回答が得られるかどうかも怪しいものです）。では、どうすれば改善出来るか見ていきましょう。最初の問題である、よいタイトル選びから始めます。

内容の分かるタイトルを付ける

コードのバグについて助けを求める時は、タイトルに十分な情報を含めて、他の人が「自分の答えられる質問かどうか」をすばやく判断出来るようにするのが、経験則としてよい方法です。今回の例では、発生している例外の名前が分かっており、モデルを呼び出す model(**inputs) のフォワードパスで発生しているらしいという手がかりもあります。これを伝えるタイトルとしては、例えば次のようなものが考えられます。

AutoModel のフォワードパスで発生する IndexError の原因は？

このタイトルは、バグがどこから来ていると思うかを読み手に伝え、IndexError に遭遇したことがある人なら、デバッグ方法を知っている可能性が高いでしょう。勿論タイトルは自由に付けられますし、次のようなバリエーションでも問題ありません。

何故モデルの実行時に IndexError が発生するのか？

説明的なタイトルが決まったので、次は本文の改善を見ていきましょう。

コードスニペットを整形する

ソースコードを読むのは IDE の中でも十分に大変ですが、プレーンテキストとしてコピー＆ペーストされたものを読むのは更に大変です。幸い、Hugging Face フォーラムは Markdown をサポートしているので、コードを掲載する時は、必ず3つのバッククォートで囲んでコードブロックとして整形してください。エラーメッセージをこの方法出来れいに整形してみましょう。ついでに、本文を最初のバージョンよりも少し丁寧な文面にします。

スクリーンショットで分かるように、コードブロックをバッククォートで囲むと、生のテキストが色付けまでされた整形済みコードに変換されます。単一のバッククォートを使えば、distilbert-base-uncased のようにインラインの変数を整形することも出来ます。このトピックはずいぶんよくなりました。

運がよければ、エラーの内容を推測出来る人がコミュニティにいるかもしれません。ただ、運に頼るのではなく、トレースバックを省略せず、詳細を全て掲載して、相手の作業を楽にしましょう。

トレースバックを全部載せる

トレースバックの最後の行だけで自分のコードをデバッグ出来ることが多い為、スペースを「節約」しようとしてトピックにその行だけを載せたくなるものです。善意からではありますが、トレースバックの上部に在る情報も非常に役立つ為、実際には他の人が問題をデバッグするのを_難しく_してしまいます。

ですから、トレースバックは_全文_をコピー＆ペーストし、読みやすく整形して掲載するのがよい方法です。トレースバックはかなり長くなることがあるので、ソースコードを説明した後に載せる人もいます。ここでもそうしてみましょう。これでフォーラムトピックは次のようになります。

但し、エラーを引き起こした実際のコードを示せば、相手は更に楽になります。次はそれをやってみましょう。

再現可能な例を用意する

他人のコードをデバッグしたことがある人なら、たいてい最初に、報告された問題を再現しようとして、トレースバックをたどってエラーの箇所を特定する所から始めたはずです。フォーラムで支援を受ける（あるいは提供する）場合も同じことなので、エラーを再現する小さな例を用意出来ると本当に助かります。

このように再現例を作る過程で、半数程のケースでは問題の原因を自分で発見出来ます。いずれにせよ、この例で欠けているのは、モデルに渡した_入力_を示すことです。それを示すと、次のような完成した例になります。
