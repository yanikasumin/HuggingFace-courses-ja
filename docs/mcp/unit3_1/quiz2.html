クイズ2: プルリクエストエージェントの統合

MCP クライアントの統合と Webhook の処理を含む、プルリクエストエージェントのシステム全体についての知識をテストしましょう。

Q1: プルリクエストエージェントのアーキテクチャにおいて、Webhook リスナーの主な目的は何ですか？

Webhook リスナーが扱うのは GitHub のイベントであり、ユーザーインターフェースではありません。
正解です！ Webhook リスナーは Hub のディスカッションイベントに応答して、エージェントのアクションを起動します。
PR データを処理することはあっても、主な役割はイベント処理であり、保存ではありません。
Webhook リスナーが扱うのはイベントであり、ユーザー認証ではありません。

Q2: エージェントベースの MCP クライアントの実装では、クライアントはどのように MCP サーバーに接続しますか？

Agent が使うのはサブプロセス通信であり、直接の関数呼び出しではありません。
正解です！ Agent は 'python mcp_server.py' で MCP サーバーを起動し、stdin/stdout を通じて通信します。
MCP はリアルタイム通信を使い、ファイルベースの通信は使いません。
stdio 接続タイプは HTTP を使わず、標準入出力ストリームを使います。

Q3: Webhook ハンドラーは、なぜリクエストを同期的に処理せず FastAPI の background_tasks.add_task() を使うのですか？

バックグラウンドタスクがメモリ使用量を減らすとは限りません。
Hub は迅速な応答を期待しますが、これは Hub 固有の要件ではありません。
正解です！ Webhook エンドポイントは素早く応答しなければ、送信側プラットフォームに失敗とみなされます。
並行処理も可能になりますが、主な理由は応答時間の要件です。

Q4: Webhook ハンドラーで X-Webhook-Secret ヘッダーを検証する目的は何ですか？

リポジトリの情報は Webhook のペイロードから得られるもので、シークレットヘッダーからではありません。
正解です！ 共有シークレットは、Hugging Face とアプリケーションの間の認証として機能します。
シークレットは認証のためのもので、ペイロードデータのデコードのためではありません。
ツールの選択は Webhook の内容に基づくもので、シークレットヘッダーに基づくものではありません。

Q5: Agent の実装では、await agent_instance.load_tools() が呼ばれると何が起きますか？

ツールはローカルの MCP サーバーのものであり、Hub からダウンロードされるものではありません。
正解です！ MCP サーバーが提供するツールを発見し、エージェントの推論エンジンから使えるようにします。
load_tools() は MCP ツールの発見専用のもので、Web サーバーの起動とは関係ありません。
認証はエージェントの作成時に行われるもので、ツールの読み込み時ではありません。

Q6: 自然言語の指示を処理するとき、Agent はどのように MCP ツールを賢く使いますか？

Agent は推論を使って、どのツールをどの順序で呼ぶかを判断します。
よくあるパターンではありますが、Agent は指示に基づいて使うツールを推論します。
正解です！ Agent は複雑な指示を理解し、ツールの実行計画を自動で立てられます。
Agent は、明示的な関数の指定がない自然言語の指示でも動作します。

Q7: Webhook イベントがタグ処理を起動すべきかどうかは、どんなフィルタリングロジックで決まりますか？

ハンドラーはイベントをフィルタリングし、関連するものだけを処理します。
正解です！ これにより、新しいディスカッションコメントだけを処理し、他の Hub イベントは無視できます。
フィルタリングはイベントの種類に基づくもので、ユーザーの検証ステータスに基づくものではありません。
イベントのフィルタリングは内容の分析より前に行われます。まずイベントの種類で絞り込みます。
