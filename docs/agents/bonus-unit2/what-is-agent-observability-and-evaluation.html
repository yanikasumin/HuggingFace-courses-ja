AI エージェントのオブザーバビリティと評価

🔎 オブザーバビリティとは？

オブザーバビリティとは、ログ、メトリクス、トレースといった外部のシグナルを見ることで、AI エージェントの内部で何が起きているかを理解することです。AI エージェントにおいては、アクション、ツールの使用、モデル呼び出し、レスポンスを追跡し、デバッグやパフォーマンス改善に役立てることを意味します。

🔭 エージェントのオブザーバビリティが重要な理由

オブザーバビリティがなければ、AI エージェントの内部動作は「ブラックボックス」のままです。オブザーバビリティツールを使うと、エージェントの内部動作が見えるようになり、次のことができるようになります。

  • コストと精度のトレードオフを理解する
  • レイテンシを測定する
  • 有害な言語やプロンプトインジェクションを検出する
  • ユーザーフィードバックを監視する

言い換えれば、デモ用のエージェントを本番運用に耐えるものにするのがオブザーバビリティです！

🔨 オブザーバビリティツール

AI エージェント向けの代表的なオブザーバビリティツールには、Langfuse や Arize といったプラットフォームがあります。これらのツールは詳細なトレースを収集し、メトリクスをリアルタイムに監視できるダッシュボードを提供するため、問題の検出やパフォーマンスの最適化が容易になります。

オブザーバビリティツールの機能や特徴は、製品によって異なります。オープンソースのツールには、大きな開発コミュニティが開発方針を決めるうえで重要な役割を果たし、ほかのサービスとの連携機能も豊富なものがあります。また、オブザーバビリティ、評価、プロンプト管理など、LLMOps の特定の機能に特化したツールもあれば、LLMOps の作業全体をカバーするツールもあります。それぞれのドキュメントを確認し、自分の用途に合ったものを選んでください。

smolagents などの多くのエージェントフレームワークは、OpenTelemetry の標準仕様を使って、オブザーバビリティツールにメタデータを提供しています。また、オブザーバビリティツール側でも、LLM 技術の急速な進歩に柔軟に対応できるよう、独自の計装（インストルメンテーション）機能を用意しています。どの機能に対応しているかは、使用するツールのドキュメントで確認してください。

🔬 トレースとスパン

オブザーバビリティツールは通常、エージェントの実行をトレースとスパンで表します。

  • トレース は、エージェントのタスク全体を最初から最後まで表します（ユーザーのクエリへの対応など）。
  • スパン は、トレース内の個々のステップです（言語モデルの呼び出しやデータの取得など）。

📊 監視すべき主要メトリクス

オブザーバビリティツールが監視する、代表的なメトリクスを紹介します。

レイテンシ： エージェントはどれくらい速く応答するか？待ち時間が長いと、ユーザー体験に悪影響を与えます。エージェントの実行をトレースして、タスク単位・ステップ単位のレイテンシを測定しましょう。たとえば、モデル呼び出し全体で 20 秒かかっているエージェントは、より高速なモデルを使ったり、モデル呼び出しを並列実行したりすることで高速化できるかもしれません。

コスト： エージェントの実行 1 回あたりの費用はいくらか？AI エージェントは、トークン単位で課金される LLM 呼び出しや外部 API に依存します。ツールやプロンプトを頻繁に使うと、コストは急速に膨らみます。たとえば、エージェントがわずかな品質向上のために LLM を 5 回呼び出している場合、そのコストに見合うかどうか、呼び出し回数を減らせないか、より安いモデルで代用できないかを検討する必要があります。リアルタイム監視は、予期しない急増（API 呼び出しの無限ループを引き起こすバグなど）の発見にも役立ちます。

リクエストエラー： エージェントが処理に失敗したリクエストは何件あるでしょうか？これには、API エラーやツール呼び出しの失敗などが含まれます。本番環境でこうしたエラーに対処するには、代替手段への切り替え（フォールバック）や再試行（リトライ）の仕組みを用意しておくとよいでしょう。たとえば、LLM プロバイダ A が停止した場合に、バックアップの LLM プロバイダ B に切り替える方法があります。

ユーザーフィードバック： ユーザーが直接評価できるようにすると、貴重なインサイトが得られます。明示的な評価（👍いいね／👎よくない、星1〜5個の評価）やテキストコメントが含まれます。否定的なフィードバックが続くようなら、エージェントが期待どおりに動作していないサインなので、注意が必要です。

暗黙のユーザーフィードバック： 明示的な評価がなくても、ユーザーの行動から間接的なフィードバックが得られます。質問をすぐに言い換える、同じ質問を繰り返す、リトライボタンをクリックする、といった行動です。たとえば、ユーザーが同じ質問を繰り返しているなら、エージェントが期待どおりに動作していないサインです。

精度： エージェントはどれくらいの頻度で、正しい、あるいは望ましい出力を生成しているか？精度の定義はさまざまです（問題解決の正確さ、情報検索の精度、ユーザー満足度など）。まず、自分のエージェントにとっての「成功」が何かを定義することから始めます。精度は、自動チェック、評価スコア、タスク完了のラベルなどで追跡できます。たとえば、トレースに「成功」や「失敗」の印を付ける方法があります。

自動評価メトリクス： 自動評価（eval）を設定することもできます。たとえば、LLM を使ってエージェントの出力を採点し、役に立つか、正確かなどを判定させる方法があります。エージェントのさまざまな側面を採点するのに役立つオープンソースライブラリもいくつかあります。たとえば、RAG エージェント向けの RAGAS や、有害な言語やプロンプトインジェクションを検出する LLM Guard などです。

実際には、これらのメトリクスを組み合わせることで、AI エージェントの動作状況を幅広く把握できます。この章のサンプルノートブックでは、実際の例を使って各メトリクスの確認方法を紹介します。その前に、まずは一般的な評価の進め方を学びましょう。

👍 AI エージェントの評価

オブザーバビリティによってさまざまなメトリクスが得られます。一方、評価とは、こうしたデータを分析したり、テストを実施したりして、AI エージェントがどの程度うまく動作しているか、どうすれば改善できるかを判断することです。つまり、得られたトレースやメトリクスを使ってエージェントの性能を評価し、その結果を改善のための判断につなげるのです。

AI エージェントは、同じ入力でも毎回同じ結果を返すとは限りません。また、アップデートやモデルの動作の変化によって、性能が変わることもあります。そのため、定期的な評価が重要です。評価しなければ、エージェントが期待どおりに仕事をこなしているのか、以前より性能が低下しているのかを判断できません。

AI エージェントの評価には、オンライン評価 と オフライン評価 の 2 つのカテゴリーがあります。どちらも価値があり、互いを補完します。通常は、オフライン評価から始めます。これは、エージェントをデプロイする前に最低限必要なステップだからです。

🥷 オフライン評価

オフライン評価とは、実際のユーザーからの質問ではなく、通常はテストデータセットを使って、管理された環境でエージェントを評価する方法です。期待される出力や正しい動作があらかじめ分かっているデータセットを用意し、それを使ってエージェントを実行します。

たとえば、数学の文章題エージェントを作った場合、既知の答えを持つ 100 問のテストデータセット が使えます。オフライン評価は開発中に行われることが多く（CI/CD パイプラインに組み込むこともできます）、改善の確認やリグレッションの防止に役立ちます。利点は、正解（グラウンドトゥルース）があるため、再現可能で、明確な精度メトリクスが得られることです。ユーザークエリをシミュレーションして、エージェントの応答を理想の答えと比較したり、前述の自動メトリクスを使ったりすることもできます。

オフライン評価の主な課題は、テストデータセットが十分な範囲をカバーし、実際の用途に合った内容であり続けるようにすることです。エージェントは、決まったテスト問題では良い成績を出せても、本番環境ではまったく異なる質問を受けるかもしれません。そのため、実際の利用状況を反映した新しい例や例外的なケース（エッジケース）を、テストデータセットに追加し続ける必要があります。また、小規模な「スモークテスト」と大規模な評価用データセットを組み合わせると効果的です。小規模なテストは動作の素早い確認に、大規模なテストは幅広い性能指標の測定に使います。

🔄 オンライン評価

オンライン評価とは、エージェントが実際に使われている本番環境で評価を行うことです。実際のユーザーとのやり取りを通じてエージェントの性能を監視し、その結果を継続的に分析します。

たとえば、成功率、ユーザー満足度スコア、その他のメトリクスをライブトラフィックで追跡します。オンライン評価の利点は、ラボ環境では予想できない事柄を捉えられることです。時間の経過によるモデルのドリフト（入力パターンの変化に伴いエージェントの有効性が低下すること）を観測したり、テストデータに無かった予期しないクエリや状況に気づいたりできます。本番環境でのエージェントの振る舞いを、ありのままに把握できるのです。

オンライン評価では、前述のように暗黙的・明示的なユーザーフィードバックを収集することが多く、シャドーテストや A/B テスト（新しいバージョンのエージェントを並行して実行し、旧バージョンと比較する）を実施する場合もあります。課題は、ライブのやり取りに対して信頼できるラベルやスコアを得るのが難しい点です。ユーザーフィードバックや下流のメトリクス（ユーザーが結果をクリックしたかどうかなど）に頼ることになるかもしれません。

🤝 2 つを組み合わせる

実際には、AI エージェントを適切に評価するために、オンライン と オフライン の両方の方法を組み合わせます。定期的にオフラインのベンチマークを実行して、決められたタスクに対するエージェントの性能を数値で評価します。同時に、実際の利用状況を継続的に監視し、ベンチマークだけでは分からない問題を見つけます。たとえば、オフラインのテストでは、コード生成エージェントが既知の問題を解く成功率が向上しているか確認できます。一方、オンラインでの監視では、エージェントが苦手とする新しい種類の質問をユーザーがするようになったことに気づけるかもしれません。両方を組み合わせることで、エージェントの性能をより幅広く、確実に把握できます。

実際、多くのチームが 「オフライン評価 → 新しいバージョンのエージェントをデプロイ → オンラインメトリクスを監視し、新しい失敗例を収集 → その例をオフラインのテストセットに追加 → 繰り返す」 というループを採用しています。これにより、評価を継続的に行い、改善を重ねることができます。
