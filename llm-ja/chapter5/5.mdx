NLP アプリケーションを構築するのに必要なデータセットが存在しない場合もあり、その場合は自分で作成する必要があります。このセクションでは、GitHub リポジトリのバグや機能を追跡するためによく使われる [GitHub issues](https://github.com/features/issues/) のコーパスの作り方を紹介します。このコーパスは、次のようなさまざまな用途に使えます。

* オープンな issue やプルリクエストをクローズするのにかかる時間を調べる
* issue の説明に基づいてメタデータ（例: "bug"、"enhancement"、"question"）で issue にタグ付けできるマルチラベル分類器を訓練する
* ユーザーのクエリに一致する issue を探すセマンティック検索エンジンを作る

ここではコーパスの作成に焦点を当て、次のセクションでセマンティック検索アプリケーションに取り組みます。メタな趣向として、人気のオープンソースプロジェクトである 🤗 Datasets 自身の GitHub issues を使います。データの取得方法と、これらの issue に含まれる情報の探索方法を見ていきましょう。

GitHub の[ドキュメント](https://docs.github.com/en/rest/overview/resources-in-the-rest-api#rate-limiting)に記載されているように、認証されていないリクエストは1時間あたり60リクエストに制限されます。`per_page` クエリパラメータを増やしてリクエスト回数を減らすことはできますが、数千件を超える issue を持つリポジトリでは、それでもレート制限に引っかかります。そのため、代わりに GitHub の[手順](https://docs.github.com/en/github/authenticating-to-github/creating-a-personal-access-token)に従って個人アクセストークンを作成し、レート制限を1時間あたり5,000リクエストまで引き上げるべきです。トークンが用意できたら、リクエストヘッダの一部として含めることができます。

```py
GITHUB_TOKEN = xxx  # ここに自分の GitHub トークンを貼り付けます
headers = {"Authorization": f"token {GITHUB_TOKEN}"}
```

> [!WARNING]
> ⚠️ `GITHUB_TOKEN` を貼り付けたノートブックを共有しないでください。誤ってこの情報を漏らさないよう、実行後は最後のセルを削除することをおすすめします。さらに良いのは、トークンを *.env* ファイルに保存し、[`python-dotenv` ライブラリ](https://github.com/theskumar/python-dotenv)を使って環境変数として自動的に読み込む方法です。

アクセストークンが用意できたので、GitHub リポジトリからすべての issue をダウンロードできる関数を作りましょう。

```py
import time
import math
from pathlib import Path
import pandas as pd
from tqdm.notebook import tqdm


def fetch_issues(
    owner="huggingface",
    repo="datasets",
    num_issues=10_000,
    rate_limit=5_000,
    issues_path=Path("."),
):
    if not issues_path.is_dir():
        issues_path.mkdir(exist_ok=True)

    batch = []
    all_issues = []
    per_page = 100  # 1ページあたりに返す issue の数
    num_pages = math.ceil(num_issues / per_page)
    base_url = "https://api.github.com/repos"

    for page in tqdm(range(num_pages)):
        # state=all でクエリし、オープンとクローズの両方の issue を取得します
        query = f"issues?page={page}&per_page={per_page}&state=all"
        issues = requests.get(f"{base_url}/{owner}/{repo}/{query}", headers=headers)
        batch.extend(issues.json())

        if len(batch) > rate_limit and len(all_issues) < num_issues:
            all_issues.extend(batch)
            batch = []  # 次の期間のためにバッチを空にします
            print(f"Reached GitHub rate limit. Sleeping for one hour ...")
            time.sleep(60 * 60 + 1)

    all_issues.extend(batch)
    df = pd.DataFrame.from_records(all_issues)
    df.to_json(f"{issues_path}/{repo}-issues.jsonl", orient="records", lines=True)
    print(
        f"Downloaded all the issues for {repo}! Dataset stored at {issues_path}/{repo}-issues.jsonl"
    )
```

`fetch_issues()` を呼び出すと、GitHub の1時間あたりのリクエスト数の上限を超えないよう、すべての issue がバッチ単位でダウンロードされます。結果は _リポジトリ名-issues.jsonl_ ファイルに保存され、各行が issue を表す JSON オブジェクトになります。この関数を使って、🤗 Datasets のすべての issue を取得しましょう。

```py
# インターネット接続によっては、実行に数分かかることがあります...
fetch_issues()
```

素晴らしい。これで初めてのデータセットをゼロから作れました！しかし、🤗 Datasets リポジトリの [Issues タブ](https://github.com/huggingface/datasets/issues)には合計で約1,000件の issue しか表示されないのに、なぜ数千件もの issue があるのでしょうか 🤔？GitHub の[ドキュメント](https://docs.github.com/en/rest/reference/issues#list-issues-assigned-to-the-authenticated-user)に記載されているように、これはプルリクエストもすべてダウンロードしているためです。

> GitHub の REST API v3 は、すべてのプルリクエストを issue とみなしますが、すべての issue がプルリクエストであるとは限りません。このため、「Issues」エンドポイントはレスポンスに issue とプルリクエストの両方を返すことがあります。プルリクエストは `pull_request` キーで識別できます。「Issues」エンドポイントから返されるプルリクエストの `id` は issue の id になることに注意してください。

issue とプルリクエストの内容はかなり異なるため、両者を区別できるよう、軽い前処理を行いましょう。

## データのクリーニング[[cleaning-up-the-data]]

GitHub ドキュメントの上記の抜粋によれば、`pull_request` 列を使って issue とプルリクエストを区別できます。ランダムサンプルを見て、違いを確認してみましょう。[セクション3](/course/chapter5/3) で行ったように、`Dataset.shuffle()` と `Dataset.select()` をつないでランダムサンプルを作り、`html_url` 列と `pull_request` 列を zip して、さまざまな URL を比較できるようにします。

```py
sample = issues_dataset.shuffle(seed=666).select(range(3))

# URL とプルリクエストのエントリを表示します
for url, pr in zip(sample["html_url"], sample["pull_request"]):
    print(f">> URL: {url}")
    print(f">> Pull request: {pr}\n")
```


> ✏️ **やってみよう！** 🤗 Datasets の issue がクローズされるまでの平均時間を計算してみましょう。プルリクエストとオープンな issue を除外するには `Dataset.filter()` 関数が役立ちます。また、`Dataset.set_format()` 関数を使ってデータセットを `DataFrame` に変換すれば、`created_at` と `closed_at` のタイムスタンプを簡単に操作できます。おまけとして、プルリクエストがクローズされるまでの平均時間も計算してみましょう。

```py
def get_comments(issue_number):
    url = f"https://api.github.com/repos/huggingface/datasets/issues/{issue_number}/comments"
    response = requests.get(url, headers=headers)
    return [r["body"] for r in response.json()]
```

## データセットカードの作成[[creating-a-dataset-card]]

よくドキュメント化されたデータセットは、他の人（そして未来の自分！）にとって有用である可能性が高くなります。データセットが自分のタスクに関連するかどうかをユーザーが判断したり、データセットの使用に伴う潜在的なバイアスやリスクを評価したりするための文脈を提供してくれるからです。

Hugging Face Hub では、この情報は各データセットリポジトリの *README.md* ファイルに保存されます。このファイルを作成する前に、主に次の2つのステップを行うべきです。

1. [`datasets-tagging` アプリケーション](https://huggingface.co/datasets/tagging/)を使って、YAML 形式のメタデータタグを作成します。これらのタグは Hugging Face Hub のさまざまな検索機能に使われ、データセットがコミュニティのメンバーに簡単に見つけてもらえるようにします。ここではカスタムデータセットを作成したため、`datasets-tagging` リポジトリをクローンして、アプリケーションをローカルで実行する必要があります。インターフェースは次のようになっています。

<div class="flex justify-center">
<img src="https://huggingface.co/datasets/huggingface-course/documentation-images/resolve/main/en/chapter5/datasets-tagger.png" alt="`datasets-tagging` のインターフェース。" width="80%"/>
</div>

2. データセットカードの作成に関する [🤗 Datasets ガイド](https://github.com/huggingface/datasets/blob/master/templates/README_guide.md)を読み、テンプレートとして使います。

*README.md* ファイルは Hub 上で直接作成できます。記入済みのデータセットカードのテンプレートは、`lewtun/github-issues` データセットリポジトリにあります。記入されたデータセットカードのスクリーンショットを下に示します。
