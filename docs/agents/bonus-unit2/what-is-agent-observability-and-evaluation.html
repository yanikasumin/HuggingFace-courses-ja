AI エージェントのオブザーバビリティと評価

🔎 オブザーバビリティとは？

オブザーバビリティとは、ログ、メトリクス、トレースといった外部のシグナルを見ることで、AI エージェントの内部で何が起きているかを理解することです。AI エージェントにおいては、アクション、ツールの使用、モデル呼び出し、レスポンスを追跡し、デバッグやパフォーマンス改善に役立てることを意味します。

🔭 エージェントのオブザーバビリティが重要な理由

オブザーバビリティがなければ、AI エージェントは「ブラックボックス」です。オブザーバビリティツールによってエージェントが透明になり、次のことができるようになります。

  • コストと精度のトレードオフを理解する
  • レイテンシを測定する
  • 有害な言語やプロンプトインジェクションを検出する
  • ユーザーフィードバックを監視する

言い換えれば、デモ用のエージェントを本番運用に耐えるものにするのがオブザーバビリティです！

🔨 オブザーバビリティツール

AI エージェント向けの代表的なオブザーバビリティツールには、Langfuse や Arize といったプラットフォームがあります。これらのツールは詳細なトレースを収集し、メトリクスをリアルタイムに監視できるダッシュボードを提供するため、問題の検出やパフォーマンスの最適化が容易になります。

オブザーバビリティツールは、機能も能力もさまざまです。オープンソースで、大規模なコミュニティがロードマップを形作り、豊富なインテグレーションを持つツールもあります。また、オブザーバビリティ、評価、プロンプト管理といった LLMOps の特定の側面に特化したツールもあれば、LLMOps のワークフロー全体をカバーするよう設計されたツールもあります。各選択肢のドキュメントを確認して、自分に合ったソリューションを選んでください。

smolagents のような多くのエージェントフレームワークは、OpenTelemetry 標準を使って、オブザーバビリティツールへメタデータを公開します。これに加えて、オブザーバビリティツール側でも、動きの速い LLM の世界で柔軟に対応できるよう、カスタムの計装（インストルメンテーション）を用意しています。使用するツールのドキュメントで、何がサポートされているか確認してください。

🔬トレースとスパン

オブザーバビリティツールは通常、エージェントの実行をトレースとスパンで表します。

  • トレース は、エージェントのタスク全体を最初から最後まで表します（ユーザーのクエリへの対応など）。
  • スパン は、トレース内の個々のステップです（言語モデルの呼び出しやデータの取得など）。

📊 監視すべき主要メトリクス

オブザーバビリティツールが監視する、代表的なメトリクスを紹介します。

レイテンシ: エージェントはどれくらい速く応答するか？待ち時間が長いと、ユーザー体験に悪影響を与えます。エージェントの実行をトレースして、タスク単位・ステップ単位のレイテンシを測定しましょう。たとえば、モデル呼び出し全体で 20 秒かかっているエージェントは、より高速なモデルを使ったり、モデル呼び出しを並列実行したりすることで高速化できるかもしれません。

コスト: エージェントの実行 1 回あたりの費用はいくらか？AI エージェントは、トークン単位で課金される LLM 呼び出しや外部 API に依存します。ツールやプロンプトを頻繁に使うと、コストは急速に膨らみます。たとえば、エージェントがわずかな品質向上のために LLM を 5 回呼び出している場合、そのコストに見合うかどうか、呼び出し回数を減らせないか、より安いモデルで代用できないかを検討する必要があります。リアルタイム監視は、予期しない急増（API 呼び出しの無限ループを引き起こすバグなど）の発見にも役立ちます。

リクエストエラー: エージェントが失敗したリクエストはいくつあるか？API エラーや失敗したツール呼び出しが含まれます。本番環境でこうした事態に強くするには、フォールバックやリトライを用意しておくとよいでしょう。たとえば、LLM プロバイダ A がダウンしたら、バックアップとして LLM プロバイダ B に切り替える、といった具合です。

ユーザーフィードバック: ユーザーが直接評価できるようにすると、貴重なインサイトが得られます。明示的な評価（👍いいね／👎よくない、⭐1〜5 つ星）やテキストコメントが含まれます。否定的なフィードバックが続くようなら、エージェントが期待どおりに動作していないサインなので、注意が必要です。

暗黙のユーザーフィードバック: 明示的な評価がなくても、ユーザーの行動から間接的なフィードバックが得られます。質問をすぐに言い換える、同じ質問を繰り返す、リトライボタンをクリックする、といった行動です。たとえば、ユーザーが同じ質問を繰り返しているなら、エージェントが期待どおりに動作していないサインです。

精度: エージェントはどれくらいの頻度で、正しい、あるいは望ましい出力を生成しているか？精度の定義はさまざまです（問題解決の正確さ、情報検索の精度、ユーザー満足度など）。まず、自分のエージェントにとっての「成功」が何かを定義することから始めます。精度は、自動チェック、評価スコア、タスク完了のラベルなどで追跡できます。たとえば、トレースに「成功」や「失敗」の印を付ける方法があります。

自動評価メトリクス: 自動評価（eval）を設定することもできます。たとえば、LLM を使ってエージェントの出力を採点し、役に立つか、正確かなどを判定させる方法があります。エージェントのさまざまな側面を採点するのに役立つオープンソースライブラリもいくつかあります。たとえば、RAG エージェント向けの RAGAS や、有害な言語やプロンプトインジェクションを検出する LLM Guard などです。

実際には、これらのメトリクスを組み合わせることで、AI エージェントの健全性を最も幅広く把握できます。この章のサンプルノートブックでは、これらのメトリクスが実際の例でどう見えるかを示しますが、その前に、典型的な評価ワークフローがどのようなものか学びましょう。

👍 AI エージェントの評価

オブザーバビリティによってメトリクスは得られますが、評価とは、そのデータ（とテスト結果）を分析し、AI エージェントがどれくらい上手く動作しているか、どう改善できるかを判断するプロセスです。つまり、トレースとメトリクスが手に入ったとして、それを使ってエージェントをどう評価し、意思決定につなげるか、ということです。

定期的な評価が重要なのは、AI エージェントはしばしば非決定的であり、（アップデートやモデルの振る舞いのドリフトによって）変化しうるからです。評価をしなければ、「賢いエージェント」が実際に仕事をこなしているのか、それとも劣化してしまったのか、分かりません。

AI エージェントの評価には、オンライン評価 と オフライン評価 の 2 つのカテゴリーがあります。どちらも価値があり、互いを補完します。通常は、オフライン評価から始めます。これは、エージェントをデプロイする前に最低限必要なステップだからです。

🥷 オフライン評価

オフライン評価は、管理された環境で、通常はテストデータセットを使い、実際のユーザークエリではなくエージェントを評価する方法です。期待される出力や正しい振る舞いが分かっている、厳選されたデータセットを使い、エージェントを実行します。

たとえば、数学の文章題エージェントを作った場合、既知の答えを持つ 100 問のテストデータセット が使えます。オフライン評価は開発中に行われることが多く（CI/CD パイプラインに組み込むこともできます）、改善の確認やリグレッションの防止に役立ちます。利点は、正解（グラウンドトゥルース）があるため、再現可能で、明確な精度メトリクスが得られることです。ユーザークエリをシミュレーションして、エージェントの応答を理想の答えと比較したり、前述の自動メトリクスを使ったりすることもできます。

オフライン評価における主な課題は、テストデータセットが包括的で、常に関連性を保っていることをどう保証するかです。エージェントは固定のテストセットでは良い成績でも、本番ではまったく異なるクエリに遭遇する可能性があります。そのため、現実のシナリオを反映した新しいエッジケースや例で、テストセットを更新し続けるべきです。小規模な「スモークテスト」ケースと大規模な評価セットを組み合わせるのが有効です。小規模セットは素早い確認に、大規模セットは幅広いパフォーマンスメトリクスの測定に使います。

🔄 オンライン評価

オンライン評価とは、稼働中の実環境、つまり本番での実際の使用の中でエージェントを評価することです。オンライン評価では、実際のユーザーとのやり取りにおけるエージェントのパフォーマンスを監視し、結果を継続的に分析します。

たとえば、成功率、ユーザー満足度スコア、その他のメトリクスをライブトラフィックで追跡します。オンライン評価の利点は、ラボ環境では予想できない事柄を捉えられることです。時間の経過によるモデルのドリフト（入力パターンの変化に伴いエージェントの有効性が低下すること）を観測したり、テストデータに無かった予期しないクエリや状況に気づいたりできます。本番環境でのエージェントの振る舞いを、ありのままに把握できるのです。

オンライン評価では、前述のように暗黙的・明示的なユーザーフィードバックを収集することが多く、シャドーテストや A/B テスト（新しいバージョンのエージェントを並行して実行し、旧バージョンと比較する）を実施する場合もあります。課題は、ライブのやり取りに対して信頼できるラベルやスコアを得るのが難しい点です。ユーザーフィードバックや下流のメトリクス（ユーザーが結果をクリックしたかどうかなど）に頼ることになるかもしれません。

🤝 2 つを組み合わせる

実際には、AI エージェントの評価が上手くいっているケースでは、オンライン と オフライン の両手法が組み合わされています。定期的にオフラインのベンチマークを実行して、定義されたタスクにおけるエージェントを定量的に採点しつつ、ライブの使用状況を継続的に監視して、ベンチマークでは捉えられない事柄を拾います。たとえば、オフラインのテストでコード生成エージェントの既知の問題集合における成功率が向上しているかを確認できます。一方で、オンラインモニタリングによって、ユーザーがエージェントの苦手とする新しいカテゴリーの質問をし始めたことに気づけるかもしれません。両方を組み合わせることで、より堅牢な全体像が得られます。

実際、多くのチームが オフライン評価 → 新しいバージョンのエージェントをデプロイ → オンラインメトリクスを監視し、新しい失敗例を収集 → その例をオフラインのテストセットに追加 → 繰り返す というループを採用しています。これにより、評価が継続的になり、常に改善されていきます。
