必要なデータセットが存在しない場合もあります。NLP アプリケーションを作ろうとしても、材料になるデータセットが無ければ、自分で作成するしかありません。このセクションでは、その作成方法を扱います。題材は [GitHub issues](https://github.com/features/issues/) です。GitHub issues は、GitHub リポジトリでバグや機能追加の対応状況を追跡する為に広く使われています。作成したコーパスには、次のような使い道があります。

* オープンな issue やプルリクエストをクローズするのにかかる時間を調べる
* issue の説明文に基づいて、"bug"、"enhancement"、"question" などのメタデータ（ラベル）を付けるマルチラベル分類器を訓練する
* ユーザーのクエリに一致する issue を探すセマンティック検索エンジンを作る

ここではコーパスの作成までを扱い、セマンティック検索アプリケーションは次のセクションで取り組みます。題材には、人気のオープンソースプロジェクトである 🤗 Datasets 自身の GitHub issues を使います。少し趣向を凝らした選択です。まず、データの取得方法と、issue に含まれる情報の内容を確認します。

GitHub の[ドキュメント](https://docs.github.com/en/rest/overview/resources-in-the-rest-api#rate-limiting)によると、認証されていないリクエストは1時間あたり60件までに制限されます。`per_page` クエリパラメータを増やせばリクエスト回数は減らせますが、issue が数千件を超えるリポジトリでは、それでも制限に到達します。対策として、個人アクセストークンを作成します。GitHub の[手順](https://docs.github.com/en/github/authenticating-to-github/creating-a-personal-access-token)に従って作成すれば、制限は1時間あたり5,000リクエストまで引き上がります。トークンは、リクエストヘッダに含めて送ります。

```py
GITHUB_TOKEN = xxx  # ここに自分の GitHub トークンを貼り付けます
headers = {"Authorization": f"token {GITHUB_TOKEN}"}
```

> [!WARNING]
> ⚠️ `GITHUB_TOKEN` を貼り付けたノートブックを共有しないでください。誤ってこの情報を漏らさないよう、実行後は最後のセルを削除することをお勧めします。更に良いのは、トークンを *.env* ファイルに保存し、[`python-dotenv` ライブラリ](https://github.com/theskumar/python-dotenv)を使って環境変数として自動的に読み込む方法です。

アクセストークンの準備が出来ました。次に、GitHub リポジトリから全ての issue をダウンロードする関数を作成します。

```py
import time
import math
from pathlib import Path
import pandas as pd
from tqdm.notebook import tqdm


def fetch_issues(
    owner="huggingface",
    repo="datasets",
    num_issues=10_000,
    rate_limit=5_000,
    issues_path=Path("."),
):
    if not issues_path.is_dir():
        issues_path.mkdir(exist_ok=True)

    batch = []
    all_issues = []
    per_page = 100  # 1ページあたりに返す issue の数
    num_pages = math.ceil(num_issues / per_page)
    base_url = "https://api.github.com/repos"

    for page in tqdm(range(num_pages)):
        # state=all でクエリし、オープンとクローズの両方の issue を取得します
        query = f"issues?page={page}&per_page={per_page}&state=all"
        issues = requests.get(f"{base_url}/{owner}/{repo}/{query}", headers=headers)
        batch.extend(issues.json())

        if len(batch) > rate_limit and len(all_issues) < num_issues:
            all_issues.extend(batch)
            batch = []  # 次の期間のためにバッチを空にします
            print(f"GitHub API のレート制限に達しました。1時間待機します...")
            time.sleep(60 * 60 + 1)

    all_issues.extend(batch)
    df = pd.DataFrame.from_records(all_issues)
    df.to_json(f"{issues_path}/{repo}-issues.jsonl", orient="records", lines=True)
    print(
        f"{repo} のすべての issue をダウンロードしました。データセットの保存先: {issues_path}/{repo}-issues.jsonl"
    )
```

`fetch_issues()` を呼び出すと、全ての issue がバッチ単位でダウンロードされます。バッチに分けるのは、GitHub の1時間あたりのリクエスト数の上限を超えない為です。結果は _リポジトリ名-issues.jsonl_ ファイルに保存されます。各行が、issue を表す JSON オブジェクトです。この関数で 🤗 Datasets の全ての issue を取得します。

```py
# インターネット接続によっては、実行に数分かかることがあります...

```

初めてのデータセットをゼロから作成出来ました。但し、件数に疑問が残ります。🤗 Datasets リポジトリの [Issues タブ](https://github.com/huggingface/datasets/issues)に表示される issue は合計で約1,000件です。それなのに、取得した件数は数千件に上ります。理由は、GitHub の[ドキュメント](https://docs.github.com/en/rest/reference/issues#list-issues-assigned-to-the-authenticated-user)に記載されている通りです。プルリクエストも全てダウンロードしている為です。

> GitHub の REST API v3 では、全てのプルリクエストを issue とみなしますが、全ての issue がプルリクエストであるとは限りません。その為、「Issues」エンドポイントは issue とプルリクエストの両方を返すことがあります。プルリクエストは `pull_request` キーで識別出来ます。なお、「Issues」エンドポイントから取得したプルリクエストの `id` は、プルリクエスト自身の ID ではなく、issue としての ID であることに注意してください。

issue とプルリクエストでは内容がかなり異なります。区別出来るように、軽い前処理を行います。

## データのクリーニング[[cleaning-up-the-data]]

区別の手がかりは、上で引用した GitHub のドキュメントにあります。`pull_request` 列で区別出来るという内容です。ランダムに選んだデータで、実際の違いを確認しましょう。[セクション3](/course/chapter5/3) と同様に、`Dataset.shuffle()` と `Dataset.select()` を続けて呼び出し、ランダムサンプルを作ります。その上で、`zip()` を使って `html_url` 列と `pull_request` 列の値を組み合わせ、URL を比較します。

```py
sample = issues_dataset.shuffle(seed=666).select(range(3))

# URL とプルリクエストのエントリを表示します
for url, pr in zip(sample["html_url"], sample["pull_request"]):
    print(f">> URL: {url}")
    print(f">> プルリクエスト: {pr}\n")
```

> ✏️ **やってみよう！** Datasets の issue がクローズされるまでの平均時間を計算してみましょう。プルリクエストとオープンな issue を除外するには `Dataset.filter()` 関数が役立ちます。また、`Dataset.set_format()` 関数を使ってデータセットを `DataFrame` に変換すれば、`created_at` と `closed_at` のタイムスタンプを簡単に操作出来ます。おまけとして、プルリクエストがクローズされるまでの平均時間も計算してみましょう。

def get_comments(issue_number):
    url = f"https://api.github.com/repos/huggingface/datasets/issues/{issue_number}/comments"
    response = requests.get(url, headers=headers)
    return [r["body"] for r in response.json()]

## データセットを Hugging Face Hub にアップロードする[[uploading-the-dataset-to-the-hugging-face-hub]]

<Youtube id="HaN6qCr_Afc"/>

拡張したデータセットが用意出来ました。コミュニティと共有する為、Hub にプッシュします。アップロードは非常に簡単です。Transformers のモデルやトークナイザと同様に、`push_to_hub()` メソッドでプッシュ出来ます。

プッシュには認証トークンが必要です。認証トークンは、`notebook_login()` 関数で Hugging Face Hub にログインすると取得出来ます。

```py
from huggingface_hub import notebook_login

notebook_login()
```

実行すると、ユーザー名とパスワードを入力するウィジェットが表示され、認証トークンが *~/.huggingface/token* に保存されます。ターミナルでコードを実行している場合は、代わりに CLI でログイン出来ます。

```bash
huggingface-cli login
```

ログイン出来たら、次のように実行してデータセットをアップロード出来ます。

```py
issues_with_comments_dataset.push_to_hub("github-issues")
```

これ以降、データセットのダウンロードは簡単です。リポジトリ ID を `load_dataset()` の `path` 引数に渡すだけです。

```py
remote_dataset = load_dataset("lewtun/github-issues", split="train")
remote_dataset
```

```python out
Dataset({
    features: ['url', 'repository_url', 'labels_url', 'comments_url', 'events_url', 'html_url', 'id', 'node_id', 'number', 'title', 'user', 'labels', 'state', 'locked', 'assignee', 'assignees', 'milestone', 'comments', 'created_at', 'updated_at', 'closed_at', 'author_association', 'active_lock_reason', 'pull_request', 'body', 'performed_via_github_app', 'is_pull_request'],
    num_rows: 2855
})
```

データセットを Hub にプッシュ出来ました。他の人も使える状態です。残る重要な作業は1つです。データセットカードの追加です。データセットカードには、コーパスの作成方法と、コミュニティにとって有用な情報を記載します。

> [!TIP]
> 💡 データセットは、`huggingface-cli` と少しの Git の工夫を使って、ターミナルから直接 Hugging Face Hub にアップロードすることも出来ます。方法の詳細は [Datasets ガイド](https://huggingface.co/docs/datasets/share#share-a-dataset-using-the-cli)を参照してください。

## データセットカードの作成[[creating-a-dataset-card]]

十分にドキュメントが整備されたデータセットは、他の人にとって役立つ可能性が高くなります。未来の自分にとっても同様です。利用者はドキュメントを手がかりに、そのデータセットが自分のタスクに適しているかを判断出来ます。使用に伴うバイアスやリスクの評価も行えます。

Hugging Face Hub では、この情報は各データセットリポジトリの *README.md* ファイルに保存されます。ファイルの作成前に、主に次の2つのステップを行います。

1. [`datasets-tagging` アプリケーション](https://huggingface.co/datasets/tagging/)を使い、YAML 形式のメタデータタグを作成します。タグは Hugging Face Hub の様々な検索機能で使われます。タグがあることで、コミュニティのメンバーがデータセットを見つけやすくなります。今回はカスタムデータセットを作成した為、`datasets-tagging` リポジトリをクローンし、アプリケーションをローカルで実行する必要があります。インターフェースは次の通りです。

<div class="flex justify-center">
<img src="https://huggingface.co/datasets/huggingface-course/documentation-images/resolve/main/en/chapter5/datasets-tagger.png" alt="`datasets-tagging` のインターフェース。" width="80%"/>
</div>

2. データセットカードの作成に関する [Datasets ガイド](https://github.com/huggingface/datasets/blob/master/templates/README_guide.md)を読み、テンプレートとして使います。

*README.md* ファイルは、Hub 上で直接作成出来ます。記入例として、`lewtun/github-issues` データセットリポジトリのデータセットカードが参考になります。下のスクリーンショットは、その記入済みのデータセットカードです。

> [!TIP]
> ✏️ **やってみよう！** `dataset-tagging` アプリケーションと [Datasets ガイド](https://github.com/huggingface/datasets/blob/master/templates/README_guide.md)を使って、自分の GitHub issues データセットの *README.md* ファイルを完成させてみましょう。

以上です。良いデータセットの作成には、かなりの手間がかかります。一方、アップロードとコミュニティへの共有は難しくありません。次のセクションでは、この新しいデータセットを使い、Datasets でセマンティック検索エンジンを作成します。検索エンジンは、質問に最も関連性の高い issue とコメントを見つけます。

> [!TIP]
> ✏️ **やってみよう！** このセクションと同じ手順で、好きなオープンソースライブラリ（勿論 Datasets 以外のものを選んでください！）の GitHub issues のデータセットを作成してみましょう。おまけとして、`labels` フィールドに在るタグを予測するマルチラベル分類器をファインチューニングしてみましょう。
