# 主要な概念と用語

Model Context Protocol をより深く学ぶ前に、MCP の基盤となる主要な概念と用語を理解しておくことが重要です。この節では、プロトコルを支える基本的な考え方を紹介します。また、コース全体を通じて MCP の実装について説明する際に使う用語も整理します。

MCP は「AI アプリケーションのための USB-C」とよく説明されます。USB-C がさまざまな周辺機器をコンピューターに接続するための標準化された物理的・論理的インターフェースを提供するように、MCP は AI モデルを外部の機能に接続するための一貫したプロトコルを提供します。この標準化はエコシステム全体に利益をもたらします。

- **ユーザー**は、異なる AI アプリケーションでも、よりシンプルで一貫した操作体験を得られます
- **AI アプリケーション開発者**は、拡大を続けるツールやデータソースのエコシステムと、アプリケーションを簡単に連携させられます
- **ツールやデータの提供者**は、複数の AI アプリケーションで動作する実装を1つ作るだけで済みます
- エコシステム全体として、相互運用性が高まり、イノベーションが促進され、断片化が減ります

## 統合問題

**M×N 統合問題**とは、標準化されたアプローチなしに、M 種類の AI アプリケーションを N 種類の外部ツールやデータソースに接続する際の課題を指します。 

### MCP がない場合（M×N 問題）

MCP のようなプロトコルがなければ、開発者は M×N 通りのカスタム統合、つまり AI アプリケーションと外部機能のありうる組み合わせごとに1つずつ統合を作らなければなりません。 

![MCP がない場合](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/1.png)

各 AI アプリケーションは、それぞれのツールやデータソースと個別に連携させる必要があります。この作業は非常に複雑で費用もかかるため、開発者にとって大きな負担となり、保守コストも高くなります。

モデルが複数、ツールも複数になると、統合の数は管理しきれないほど膨れ上がり、それぞれが独自のインターフェースを持つことになります。

![複数のモデルとツール](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/1a.png)

### MCP がある場合（M+N の解決策）

MCP は標準インターフェースを提供することで、これを M+N 問題に変えます。各 AI アプリケーションは MCP のクライアント側を一度だけ実装し、各ツールやデータソースはサーバー側を一度だけ実装します。これにより、統合の複雑さとメンテナンスの負担が劇的に減ります。

![MCP がある場合](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/2.png)

## MCP のコア用語

MCP が解決する問題を理解したところで、次は MCP プロトコルを構成する基本的な用語と概念を詳しく見ていきましょう。

> [!TIP]
> MCP は HTTP や USB-C のような標準であり、AI アプリケーションを外部のツールやデータソースに接続するためのプロトコルです。そのため、MCP を効果的に機能させるには、標準的な用語を使うことが不可欠です。 
>
> アプリケーションを文書化したりコミュニティとやり取りしたりする際には、次の用語を使いましょう。

### コンポーネント

HTTP におけるクライアントとサーバーの関係と同様に、MCP にもクライアントとサーバーがあります。

![MCP のコンポーネント](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/3.png)

- **ホスト（Host）**：エンドユーザーが直接操作する AI アプリケーションです。例として、Anthropic の Claude Desktop、Cursor のように AI 機能を備えた IDE、Hugging Face Python SDK のような推論ライブラリ、LangChain や smolagents のようなライブラリで構築されたカスタムアプリケーションがあります。ホストは MCP サーバーへの接続を開始し、ユーザーのリクエスト、LLM の処理、外部ツールの間の全体的な流れを管理します。

- **クライアント（Client）**：ホストアプリケーション内のコンポーネントで、特定の MCP サーバーとの通信を管理します。各クライアントは単一のサーバーと 1:1 の接続を維持し、MCP 通信のプロトコルレベルの詳細を処理しながら、ホストのロジックと外部サーバーの間の仲介役として動作します。

- **サーバー（Server）**：MCP プロトコルを通じて機能（ツール、リソース、プロンプト）を公開する外部のプログラムまたはサービスです。

> [!WARNING]
> 多くのコンテンツでは「クライアント」と「ホスト」が同じ意味で使われています。厳密には、ホストはユーザー向けのアプリケーションであり、クライアントはホストアプリケーション内のコンポーネントで、特定の MCP サーバーとの通信を管理します。

### 機能（Capabilities）

アプリケーションの価値は、どのような機能を提供できるかによって決まります。そのため、機能はアプリケーションを構成する重要な要素です。MCP はさまざまなソフトウェアサービスと接続できますが、多くの AI アプリケーションで共通して使われる機能がいくつかあります。

| 機能 | 説明 | 例 |
| ---------- | ----------- | ------- |
| **ツール（Tools）** | AI モデルが呼び出してアクションを実行したり、計算されたデータを取得したりできる実行可能な関数です。通常、アプリケーションのユースケースに関連します。 | 天気アプリケーションのツールは、特定の場所の天気を返す関数かもしれません。 |
| **リソース（Resources）** | 大きな計算を伴わずにコンテキストを提供する読み取り専用データソースです。 | 研究者アシスタントには、科学論文のリソースがあるかもしれません。 |
| **プロンプト（Prompts）** | ユーザー、AI モデル、利用可能な機能の間のやり取りをガイドする、事前に定義されたテンプレートやワークフローです。 | 要約プロンプトなどです。 |
| **サンプリング（Sampling）** | サーバーがクライアントを介してホストアプリケーションに、LLM とのやり取りを依頼する仕組みです。LLM が自ら生成した内容を確認し、それを踏まえて次の判断を行うような、再帰的な処理を可能にします。 | 文章作成アプリケーションが自身の出力を見直し、さらに推敲する必要があるかを判断する場合などです。 |

次の図は、コードエージェントでこれらの機能を組み合わせて使う例を示しています。

![統合図](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/8.png)

このアプリケーションでは、MCP の各機能を次のように利用できます。

| 機能の種類 | 名前 | 説明 |
| --- | --- | --- |
| ツール | コードインタープリター | LLM が書いたコードを実行できるツールです。 |
| リソース | ドキュメント | アプリケーションのドキュメントを含むリソースです。 |
| プロンプト | コードスタイル | LLM がコードを生成する際のガイドとなるプロンプトです。 |
| サンプリング | コードレビュー | LLM がコードをレビューし、さらなる判断を行えるようにするサンプリングです。 |

### まとめ

これらの主要な概念と用語を理解することが、MCP を効果的に扱うための基盤となります。次節以降では、この基盤の上に、Model Context Protocol を構成するアーキテクチャコンポーネント、通信プロトコル、機能を探っていきます。
