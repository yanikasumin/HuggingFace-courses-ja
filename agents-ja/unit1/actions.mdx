# アクション（Actions）：エージェントが環境と関わる為の手段

> [!TIP]
> このセクションでは、AI エージェントが環境とやり取りする為に取る具体的なステップを探ります。
>
> アクションの表現方法（JSON やコードの使用）、stop and parse アプローチの重要性を扱い、様々なタイプのエージェントを紹介します。

アクションは、**AI エージェントが環境とやり取りする為に取る具体的なステップ** です。

情報を得る為に Web を閲覧するにせよ、物理デバイスを制御するにせよ、各アクションはエージェントが実行する意図的な操作です。

例えば、カスタマーサービスを支援するエージェントは、顧客データを取得したり、サポート記事を提示したり、課題を人間の担当者に転送したりすることが有ります。

## エージェントのアクションのタイプ

エージェントにはいくつかの種類が有り、それぞれアクションの実行方法が異なります。

| エージェントのタイプ          | 説明                                                                                      |
|------------------------|--------------------------------------------------------------------------------------------------|
| JSON Agent             | 取るべきアクションが JSON 形式で指定される。                                                  |
| Code Agent             | エージェントがコードブロックを書き、それが外部で解釈される。                                    |
| Function-calling Agent | JSON Agent のサブカテゴリであり、各アクションごとに新しいメッセージを生成するようファインチューニングされている。 |

アクション自体も多くの目的に役立ちます。

| アクションのタイプ           | 説明                                                                              |
|--------------------------|------------------------------------------------------------------------------------------|
| 情報収集（Information Gathering）    | Web 検索の実行、データベースへのクエリ、ドキュメントの取得を行う。                    |
| ツールの使用（Tool Usage）               | API 呼び出し、計算の実行、コードの実行を行う。                              |
| 環境とのやり取り（Environment Interaction）  | デジタルインターフェースの操作や物理デバイスの制御を行う。                         |
| コミュニケーション（Communication）            | チャットでユーザーと関わったり、他のエージェントと協働したりする。                         |

LLM が扱うのはテキストだけです。そのテキストを使って、実行したいアクションとツールに渡すパラメータを記述します。エージェントが正しく動作するには、アクションの記述に必要なトークンを全て出力した時点で、LLM は新しいトークンの生成を止めなければなりません。これにより、制御が LLM からエージェントに戻り、エージェントは意図した形式（JSON、コード、function calling のいずれか）でアクションの記述を解析出来ます。


## Stop and Parse アプローチ

アクションを実装する重要な手法の1つが **stop and parse アプローチ** です。この手法により、エージェントの出力が構造化され、予測可能になります。

1. **構造化された形式での生成**：

エージェントは、意図するアクションを明確で事前に決められた形式（JSON 又はコード）で出力します。

2. **それ以上の生成の停止**：

アクションを定義するテキストが出力されたら、**LLM は追加のトークンの生成を停止します**。これにより、余分な出力や誤った出力を防ぎます。

3. **出力の解析**：

外部パーサーが形式化されたアクションを読み取り、呼び出すツールを判別し、必要なパラメータを抽出します。

例えば、天気を確認する必要が有るエージェントは、次のように出力することが有ります。


```json
Thought: I need to check the current weather for New York.
Action :
{
  "action": "get_weather",
  "action_input": {"location": "New York"}
}
```

（Thought の訳：ニューヨークの現在の天気を確認する必要が有ります）

するとフレームワークは、呼び出す関数の名前と適用する引数を簡単に解析出来ます。

この明確で機械可読な形式により、エラーが最小化され、外部ツールがエージェントの命令を正確に処理出来るようになります。

注意：Function-calling エージェントも同様の仕組みで動作します。各アクションは、指定された関数を正しい引数で呼び出せるように構造化されます。これらのタイプのエージェントについては、今後のユニットで更に深く掘り下げます。

## Code Agent

別のアプローチとして、*Code Agent* の使用が有ります。考え方はこうです。**単純な JSON オブジェクトを出力する代わりに**、Code Agent は **実行可能なコードブロック（通常は Python のような高水準言語）を生成します**。

<img src="https://huggingface.co/datasets/agents-course/course-images/resolve/main/en/unit1/code-vs-json-actions.png" alt="Code Agent" />

このアプローチにはいくつかの利点が有ります。

- **表現力：**コードはループ、条件分岐、ネストした関数を含む複雑な論理を自然に表現出来、JSON よりも柔軟性が高い。
- **モジュール性と再利用性：**生成されたコードには、異なるアクションやタスクで再利用出来る関数やモジュールを含めることが出来る。
- **デバッグのしやすさの向上：**明確に定義されたプログラミング構文により、コードのエラーは検出と修正が容易なことが多い。
- **直接的な統合：**Code Agent は外部ライブラリや API と直接統合出来、データ処理やリアルタイムの意思決定といった、より複雑な操作が可能になる。

LLM が生成したコードの実行は、プロンプトインジェクションから有害なコードの実行まで、セキュリティリスクを伴う可能性があることに留意しなければなりません。その為、デフォルトの安全対策を統合した `smolagents` のような AI エージェントフレームワークの使用が推奨されます。

リスクとその軽減方法について詳しく知りたい場合は、[こちらの専用セクションをご覧下さい](https://huggingface.co/docs/smolagents/tutorials/secure_code_execution)。

例えば、天気を取得するタスクを与えられた Code Agent は、次のような Python スニペットを生成することが有ります。

```python
# Code Agent の例: 天気情報を取得する
def get_weather(city):
    import requests
    api_url = f"https://api.weather.com/v1/location/{city}?apiKey=YOUR_API_KEY"
    response = requests.get(api_url)
    if response.status_code == 200:
        data = response.json()
        return data.get("weather", "No weather information available")
    else:
        return "Error: Unable to fetch weather data."

# 関数を実行し、最終回答を準備する
result = get_weather("New York")
final_answer = f"The current weather in New York is: {result}"
print(final_answer)
```

（コード中の文の訳：デフォルトの戻り値は「利用出来る天気情報が有りません」という意味です。最終回答の文は「ニューヨークの現在の天気は：{result}」という形式です）

この例では、Code Agent は次のことを行います。

- **API 呼び出し経由で** 天気データを取得し、
- レスポンスを処理し、
- print() 関数を使って最終回答を出力します。

この方法も、コードブロックの範囲を明確にし、実行が完了したことを示すことで、**stop and parse アプローチに従っています**。この例では、final_answer の出力が完了を示す役割を果たします。

このセクションでは、アクションがエージェントの内部推論と現実世界でのやり取りをつなぐ役割を果たすことを学びました。JSON、コード、関数呼び出しのいずれを使う場合でも、明確に構造化されたタスクを実行することが、その橋渡しとなります。

アクションをこのように意図的に実行することで、それぞれの処理を正確に記述し、stop and parse アプローチに従って外部で処理出来るようになります。次のセクションでは、エージェントが環境からのフィードバックをどう捉えて統合するかを見ていきます。
