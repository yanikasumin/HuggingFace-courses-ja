## データを準備する[[preparing-the-data]]

抽出型質問応答の学術ベンチマークとして最もよく使われるデータセットは [SQuAD](https://rajpurkar.github.io/SQuAD-explorer/) なので、ここでもそれを使います。答えのない質問を含む、より難しい [SQuAD v2](https://huggingface.co/datasets/squad_v2) ベンチマークもあります。自分のデータセットに、コンテキストの列、質問の列、答えの列が含まれていれば、以下の手順を応用できるはずです。

### 学習データを処理する[[processing-the-training-data]]

<Youtube id="qgaM0weJHpA"/>

学習データの前処理から始めましょう。難しいのは、質問への答えに対するラベルの生成です。ラベルは、コンテキスト内で答えに対応するトークンの開始位置と終了位置になります。

先を急ぎすぎないようにしましょう。まず、トークナイザを使って入力のテキストを、モデルが理解できる ID に変換する必要があります。

```py
from transformers import AutoTokenizer

model_checkpoint = "bert-base-cased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)
```

前に述べたように、BERT モデルをファインチューニングしますが、高速トークナイザが実装されているモデルタイプであれば、ほかのものも使えます。高速版が用意されているすべてのアーキテクチャは[この大きな表](https://huggingface.co/transformers/#supported-frameworks)で確認できます。また、使っている `tokenizer` オブジェクトが実際に 🤗 Tokenizers に基づいているかは、その `is_fast` 属性を見れば確認できます。

```py
tokenizer.is_fast
```

```python out
True
```

この例ではコンテキストはそれほど長くありませんが、データセットには、設定した最大長（この場合は384）を超える非常に長いコンテキストを持つサンプルもあります。[Chapter 6](/course/chapter6/4) で `question-answering` pipeline の内部を調べたときに見たように、長いコンテキストには、データセットの1つのサンプルから、スライディングウィンドウで複数の学習用特徴量を作成することで対処します。

現在の例でこれがどう動くかを見るために、長さを100に制限し、50トークンのスライディングウィンドウを使います。おさらいすると、使用するのは次のものです。

- 最大長を設定する `max_length`（ここでは100）
- 質問とコンテキストが長すぎる場合に（2番目の位置にある）コンテキストを切り捨てる `truncation="only_second"`
- 連続する2つのチャンク間で重なるトークン数を設定する `stride`（ここでは50）
- あふれたトークンが欲しいことをトークナイザに伝える `return_overflowing_tokens=True`

```py
inputs = tokenizer(
    question,
    context,
    max_length=100,
    truncation="only_second",
    stride=50,
    return_overflowing_tokens=True,
)

for ids in inputs["input_ids"]:
    print(tokenizer.decode(ids))
```

見てのとおり、この例は4つの入力に分割され、それぞれに質問とコンテキストの一部が含まれています。質問への答え（"Bernadette Soubirous"）は3番目と最後の入力にしか現れない点に注意してください。長いコンテキストをこの方法で扱うと、答えがコンテキストに含まれていない学習サンプルも生成されます。そうしたサンプルでは、ラベルは `start_position = end_position = 0` となります（つまり `[CLS]` トークンを予測します）。答えが切り捨てられて開始部分（または終了部分）しか残っていないという不運な場合も、これらのラベルを設定します。答えが完全にコンテキスト内に含まれるサンプルでは、ラベルは答えが始まるトークンのインデックスと、答えが終わるトークンのインデックスになります。

データセットは、コンテキスト内での答えの開始文字を提供してくれます。答えの長さを加えると、コンテキスト内での終了文字がわかります。これらをトークンのインデックスに対応付けるには、[Chapter 6](/course/chapter6/4) で学んだオフセットマッピングを使う必要があります。`return_offsets_mapping=True` を渡すことで、トークナイザにこれらを返させることができます。

```py
inputs = tokenizer(
    question,
    context,
    max_length=100,
    truncation="only_second",
    stride=50,
    return_overflowing_tokens=True,
    return_offsets_mapping=True,
)
inputs.keys()
```

見てのとおり、通常の入力 ID、トークンタイプ ID、アテンションマスクに加え、要求したオフセットマッピングと、追加のキー `overflow_to_sample_mapping` が返ってきます。対応する値は、複数のテキストを同時にトークン化するときに役立ちます（トークナイザが Rust に基づいている恩恵を受けるためにも、そうすべきです）。1つのサンプルから複数の特徴量が生まれることがあるため、これは各特徴量を、それが由来するサンプルに対応付けます。ここでは1つのサンプルだけをトークン化したので、`0` のリストが得られます。

```py

    raw_datasets["train"][2:6]["context"],

print(f"Here is where each comes from: {inputs['overflow_to_sample_mapping']}.")
```


見てのとおり、最初の3つのサンプル（学習セットのインデックス2、3、4）はそれぞれ4つの特徴量を生み、最後のサンプル（学習セットのインデックス5）は7つの特徴量を生みました。

この情報は、得られた各特徴量を対応するラベルに対応付けるのに役立ちます。前述のとおり、それらのラベルは次のとおりです。

- 答えがコンテキストの対応する範囲にない場合は `(0, 0)`
- 答えがコンテキストの対応する範囲にある場合は `(start_position, end_position)`。ここで `start_position` は答えの開始位置にあるトークンの（入力 ID における）インデックス、`end_position` は答えが終わるトークンのインデックスです

どちらのケースか、該当する場合はトークンの位置を特定するために、まず入力 ID の中でコンテキストが始まるインデックスと終わるインデックスを見つけます。これにはトークンタイプ ID を使うこともできますが、すべてのモデルに存在するとは限らないため（たとえば DistilBERT はそれらを必要としません）、代わりにトークナイザが返す `BatchEncoding` の `sequence_ids()` メソッドを使います。

それらのトークンのインデックスが得られたら、対応するオフセットを見ます。オフセットは、元のコンテキスト内での文字範囲を表す2つの整数のタプルです。これにより、この特徴量のコンテキストのチャンクが答えより後から始まっているか、答えが始まる前に終わっているか（その場合、ラベルは `(0, 0)` です）を検出できます。そうでない場合は、ループして答えの最初と最後のトークンを見つけます。

```py
answers = raw_datasets["train"][2:6]["answers"]
start_positions = []
end_positions = []

for i, offset in enumerate(inputs["offset_mapping"]):
    sample_idx = inputs["overflow_to_sample_mapping"][i]
    answer = answers[sample_idx]
    start_char = answer["answer_start"][0]
    end_char = answer["answer_start"][0] + len(answer["text"][0])
    sequence_ids = inputs.sequence_ids(i)

    # コンテキストの開始と終了を見つける
    idx = 0
    while sequence_ids[idx] != 1:
        idx += 1
    context_start = idx
    while sequence_ids[idx] == 1:
        idx += 1
    context_end = idx - 1

    # 答えがコンテキスト内に完全には含まれない場合、ラベルは (0, 0)
    if offset[context_start][0] > start_char or offset[context_end][1] < end_char:
        start_positions.append(0)
        end_positions.append(0)
    else:
        # そうでない場合は、開始と終了のトークン位置
        idx = context_start
        while idx <= context_end and offset[idx][0] <= start_char:
            idx += 1
        start_positions.append(idx - 1)

        idx = context_end
        while idx >= context_start and offset[idx][1] >= end_char:
            idx -= 1
        end_positions.append(idx + 1)

start_positions, end_positions
```

```python out
 [85, 53, 21, 0, 0, 70, 33, 0, 40, 0, 0, 0, 68, 35, 0, 0, 0, 0, 0])
```

アプローチが正しいことを確認するために、いくつかの結果を見てみましょう。最初の特徴量では `(83, 85)` がラベルとして得られたので、理論上の答えと、83から85（両端を含む）までのトークンをデコードした範囲を比較します。

```py

answer = answers[sample_idx]["text"][0]

start = start_positions[idx]
end = end_positions[idx]

print(f"Theoretical answer: {answer}, labels give: {labeled_answer}")
```

> [!TIP]
> ✏️ **やってみましょう！** XLNet アーキテクチャを使う場合、パディングは左側に適用され、質問とコンテキストが入れ替わります。先ほど見たコードをすべて XLNet アーキテクチャに合わせて変更してください（`padding=True` も追加します）。パディングを適用すると `[CLS]` トークンが位置0にない場合があることに注意してください。

学習データの前処理を段階的に見てきたので、それを関数にまとめ、学習データセット全体に適用できます。ほとんどのコンテキストは長く（対応するサンプルは複数の特徴量に分割されます）、動的パディングを適用する実質的な利点はないため、すべての特徴量を設定した最大長までパディングします。

```py
max_length = 384
stride = 128


def preprocess_training_examples(examples):
    questions = [q.strip() for q in examples["question"]]
    inputs = tokenizer(
        questions,
        examples["context"],
        max_length=max_length,
        truncation="only_second",
        stride=stride,
        return_overflowing_tokens=True,
        return_offsets_mapping=True,
        padding="max_length",
    )

    offset_mapping = inputs.pop("offset_mapping")
    sample_map = inputs.pop("overflow_to_sample_mapping")
    answers = examples["answers"]
    start_positions = []
    end_positions = []

    for i, offset in enumerate(offset_mapping):
        sample_idx = sample_map[i]
        answer = answers[sample_idx]
        start_char = answer["answer_start"][0]
        end_char = answer["answer_start"][0] + len(answer["text"][0])
        sequence_ids = inputs.sequence_ids(i)

        # コンテキストの開始と終了を見つける
        idx = 0
        while sequence_ids[idx] != 1:
            idx += 1
        context_start = idx
        while sequence_ids[idx] == 1:
            idx += 1
        context_end = idx - 1

        # 答えがコンテキスト内に完全には含まれない場合、ラベルは (0, 0)
        if offset[context_start][0] > start_char or offset[context_end][1] < end_char:
            start_positions.append(0)
            end_positions.append(0)
        else:
            # そうでない場合は、開始と終了のトークン位置
            idx = context_start
            while idx <= context_end and offset[idx][0] <= start_char:
                idx += 1
            start_positions.append(idx - 1)

            idx = context_end
            while idx >= context_start and offset[idx][1] >= end_char:
                idx -= 1
            end_positions.append(idx + 1)

    inputs["start_positions"] = start_positions
    inputs["end_positions"] = end_positions
    return inputs
```

使用する最大長とスライディングウィンドウの長さを決める2つの定数を定義したこと、そしてトークン化の前に少しだけクリーンアップを加えたことに注意してください。SQuAD データセットの一部の質問には、冒頭と末尾に余分な空白があります。これらは何の意味も持ちません（RoBERTa のようなモデルでトークン化すると場所を取るだけです）。そこで、余分な空白を取り除きました。

### 検証データを処理する[[processing-the-validation-data]]

検証データの前処理は、ラベルを生成する必要がない分、少し簡単です（検証の損失を計算したい場合は別ですが、その数値がモデルの良し悪しの理解にあまり役立つことはありません）。面白いのは、モデルの予測を元のコンテキストの範囲として解釈する部分です。そのためには、オフセットマッピングと、作成された各特徴量をそれが由来する元のサンプルに対応付ける方法の両方を保存しておく必要があります。元のデータセットには ID 列があるので、その ID を使います。

ここで加えるのは、オフセットマッピングの少しのクリーンアップだけです。オフセットマッピングには質問とコンテキストの両方のオフセットが含まれますが、後処理の段階に入ると、入力 ID のどの部分がコンテキストでどの部分が質問だったかを知る方法がなくなります（使用した `sequence_ids()` メソッドはトークナイザの出力に対してのみ利用できます）。そこで、質問に対応するオフセットを `None` に設定します。

```py
def preprocess_validation_examples(examples):
    questions = [q.strip() for q in examples["question"]]
    inputs = tokenizer(
        questions,
        examples["context"],
        max_length=max_length,
        truncation="only_second",
        stride=stride,
        return_overflowing_tokens=True,
        return_offsets_mapping=True,
        padding="max_length",
    )

    sample_map = inputs.pop("overflow_to_sample_mapping")
    example_ids = []

    for i in range(len(inputs["input_ids"])):
        sample_idx = sample_map[i]
        example_ids.append(examples["id"][sample_idx])

        sequence_ids = inputs.sequence_ids(i)
        offset = inputs["offset_mapping"][i]
        inputs["offset_mapping"][i] = [
            o if sequence_ids[k] == 1 else None for k, o in enumerate(offset)
        ]

    inputs["example_id"] = example_ids
    return inputs
```

モデルは、[`question-answering` pipeline](/course/chapter6/3b) の内部を調べたときに見たように、入力 ID における答えの開始位置と終了位置のロジットを出力します。後処理のステップはそこで行ったものと似ているので、行った操作を簡単に振り返っておきましょう。

- コンテキスト外のトークンに対応する開始と終了のロジットをマスクしました。
- 次に、ソフトマックスを使って開始と終了のロジットを確率に変換しました。
- 対応する2つの確率の積を取ることで、各 `(start_token, end_token)` ペアにスコアを与えました。
- 有効な答えが得られる（例: `start_token` が `end_token` より小さい）ペアの中で、スコアが最大のものを探しました。

ここでは、実際のスコアを計算する必要がない（必要なのは予測された答えだけである）ため、この処理を少し変更します。つまり、ソフトマックスのステップを省略できます。高速化のため、可能なすべての `(start_token, end_token)` ペアにスコアを付けるのではなく、上位の `n_best` 個のロジット（`n_best=20`）に対応するペアだけにスコアを付けます。ソフトマックスを省略するので、これらのスコアはロジットのスコアとなり、開始と終了のロジットの合計を取ることで得られます（規則 \\(\log(ab) = \log(a) + \log(b)\\)).

これらすべてを示すには、何らかの予測が必要です。まだモデルを学習していないので、QA pipeline のデフォルトモデルを使って、検証セットの一部について予測を生成します。前と同じ処理関数が使えます。この関数はグローバル定数 `tokenizer` に依存しているので、一時的に使いたいモデルのトークナイザにそのオブジェクトを差し替えるだけです。

これが手に入れば、本格的に作業できます。すべてのサンプルをループし、各サンプルについて関連するすべての特徴量をループします。前述のとおり、開始と終了の上位 `n_best` 個のロジットについてロジットスコアを見ますが、次のような位置は除外します。

- 答えがコンテキストの中に入らないもの
- 答えの長さが負になるもの
- 答えが長すぎるもの（可能性を `max_answer_length=30` に制限します）

```python
import numpy as np

n_best = 20
max_answer_length = 30
predicted_answers = []

for example in small_eval_set:
    example_id = example["id"]
    context = example["context"]
    answers = []

    for feature_index in example_to_features[example_id]:
        start_logit = start_logits[feature_index]
        end_logit = end_logits[feature_index]
        offsets = eval_set["offset_mapping"][feature_index]

        start_indexes = np.argsort(start_logit)[-1 : -n_best - 1 : -1].tolist()
        end_indexes = np.argsort(end_logit)[-1 : -n_best - 1 : -1].tolist()
        for start_index in start_indexes:
            for end_index in end_indexes:
                # 答えがコンテキスト内に完全には含まれないものはスキップする
                if offsets[start_index] is None or offsets[end_index] is None:
                    continue
                # 長さが 0 未満、または max_answer_length を超える答えはスキップする
                if (
                    end_index < start_index
                    or end_index - start_index + 1 > max_answer_length
                ):
                    continue

                answers.append(
                    {
                        "text": context[offsets[start_index][0] : offsets[end_index][1]],
                        "logit_score": start_logit[start_index] + end_logit[end_index],
                    }
                )

    best_answer = max(answers, key=lambda x: x["logit_score"])
    predicted_answers.append({"id": example_id, "prediction_text": best_answer["text"]})
```

ここまで行ったことを、すべて `Trainer` で使う `compute_metrics()` 関数にまとめましょう。通常、この `compute_metrics()` 関数は、ロジットとラベルを持つタプル `eval_preds` を受け取るだけです。しかしここではもう少し情報が必要です。特徴量のデータセットでオフセットを、サンプルのデータセットで元のコンテキストを参照しなければならないため、この関数で学習中の通常の評価結果を得ることはできません。学習の最後に結果を確認するためだけに使います。

`compute_metrics()` 関数は、前に行ったのと同じステップをまとめたものです。有効な答えが1つも得られなかった場合（その場合は空文字列を予測します）に備えて、小さなチェックを加えているだけです。

```python
from tqdm.auto import tqdm


def compute_metrics(start_logits, end_logits, features, examples):
    example_to_features = collections.defaultdict(list)
    for idx, feature in enumerate(features):
        example_to_features[feature["example_id"]].append(idx)

    predicted_answers = []
    for example in tqdm(examples):
        example_id = example["id"]
        context = example["context"]
        answers = []

        # そのサンプルに関連付けられたすべての特徴量をループする
        for feature_index in example_to_features[example_id]:
            start_logit = start_logits[feature_index]
            end_logit = end_logits[feature_index]
            offsets = features[feature_index]["offset_mapping"]

            start_indexes = np.argsort(start_logit)[-1 : -n_best - 1 : -1].tolist()
            end_indexes = np.argsort(end_logit)[-1 : -n_best - 1 : -1].tolist()
            for start_index in start_indexes:
                for end_index in end_indexes:
                    # 答えがコンテキスト内に完全には含まれないものはスキップする
                    if offsets[start_index] is None or offsets[end_index] is None:
                        continue
                    # 長さが 0 未満、または max_answer_length を超える答えはスキップする
                    if (
                        end_index < start_index
                        or end_index - start_index + 1 > max_answer_length
                    ):
                        continue

                    answer = {
                        "text": context[offsets[start_index][0] : offsets[end_index][1]],
                        "logit_score": start_logit[start_index] + end_logit[end_index],
                    }
                    answers.append(answer)

        # 最もスコアの良い答えを選択する
        if len(answers) > 0:
            best_answer = max(answers, key=lambda x: x["logit_score"])
            predicted_answers.append(
                {"id": example_id, "prediction_text": best_answer["text"]}
            )
        else:
            predicted_answers.append({"id": example_id, "prediction_text": ""})

    theoretical_answers = [{"id": ex["id"], "answers": ex["answers"]} for ex in examples]
    return metric.compute(predictions=predicted_answers, references=theoretical_answers)
```

```python
    "bert-finetuned-squad",
    evaluation_strategy="no",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
    fp16=True,
    push_to_hub=True,
)
```

これらのほとんどは以前にも見たものです。いくつかのハイパーパラメータ（学習率、学習するエポック数、重み減衰など）を設定し、各エポックの終了時にモデルを保存すること、評価をスキップすること、結果を Model Hub にアップロードすることを指定します。また、`fp16=True` で混合精度の学習を有効にします。最近の GPU では学習をかなり高速化できるためです。

{:else}

それが終わったら、TF データセットを作成できます。今回はシンプルなデフォルトのデータコレータが使えます。


```python
from transformers import create_optimizer
from transformers.keras_callbacks import PushToHubCallback
import tensorflow as tf

# 学習ステップ数は、データセットのサンプル数をバッチサイズで割ってから
# 総エポック数を掛けたものです。ここでの tf_train_dataset はバッチ化された tf.data.Dataset であり、
# 元の Hugging Face Dataset ではないため、その len() はすでに num_samples // batch_size です。

    num_warmup_steps=0,
```

## カスタム学習ループ[[a-custom-training-loop]]

完全な学習ループを見ていきましょう。必要な部分を簡単にカスタマイズできるようになります。評価ループを除いて、[Chapter 3](/course/chapter3/4) の学習ループとよく似たものになります。`Trainer` クラスの制約を受けなくなったので、モデルを定期的に評価できます。

### 学習のための準備をする[[preparing-everything-for-training]]

まず、データセットから `DataLoader` を構築する必要があります。それらのデータセットの形式を `"torch"` に設定し、検証セットの、モデルが使わない列を取り除きます。次に、Transformers が提供する `default_data_collator` を `collate_fn` として使い、学習セットはシャッフルしますが、検証セットはシャッフルしません。

```py
from torch.utils.data import DataLoader
from transformers import default_data_collator

train_dataset.set_format("torch")
validation_set = validation_dataset.remove_columns(["example_id", "offset_mapping"])
validation_set.set_format("torch")

train_dataloader = DataLoader(
    train_dataset,
    shuffle=True,
    collate_fn=default_data_collator,
    batch_size=8,
)
eval_dataloader = DataLoader(
    validation_set, collate_fn=default_data_collator, batch_size=8
)
```

次に、モデルを再インスタンス化します。前のファインチューニングを続けるのではなく、BERT の事前学習済みモデルから再び始めることを確実にするためです。

```py
model = AutoModelForQuestionAnswering.from_pretrained(model_checkpoint)
```

次に、オプティマイザが必要です。いつものように古典的な `AdamW` を使います。これは Adam のようなものですが、重み減衰の適用方法に修正が加えられています。

```py
from torch.optim import AdamW

optimizer = AdamW(model.parameters(), lr=2e-5)
```

これらのオブジェクトがすべて揃ったら、`accelerator.prepare()` メソッドに送ることができます。Colab ノートブックで TPU を使って学習したい場合は、このコードをすべて学習関数の中に移動する必要があり、`Accelerator` をインスタンス化するセルは一切実行すべきではないことを覚えておいてください。混合精度の学習は、`Accelerator` に `fp16=True` を渡すことで強制できます（スクリプトとしてコードを実行している場合は、🤗 Accelerate の `config` を適切に設定してください）。

```py
from accelerate import Accelerator

accelerator = Accelerator(fp16=True)
model, optimizer, train_dataloader, eval_dataloader = accelerator.prepare(
    model, optimizer, train_dataloader, eval_dataloader
)
```

前のセクションで知ったとおり、`train_dataloader` の長さを使って学習ステップ数を計算できるのは、それが `accelerator.prepare()` メソッドを経た後だけです。前のセクションと同じ線形スケジュールを使います。

```py
from transformers import get_scheduler

num_train_epochs = 3
num_update_steps_per_epoch = len(train_dataloader)
num_training_steps = num_train_epochs * num_update_steps_per_epoch

lr_scheduler = get_scheduler(
    "linear",
    optimizer=optimizer,
    num_warmup_steps=0,
    num_training_steps=num_training_steps,
)
```

モデルを Hub にプッシュするために、作業フォルダ内に `Repository` オブジェクトを作成する必要があります。まだログインしていない場合は、まず Hugging Face Hub にログインしてください。リポジトリ名は、モデルに付けたいモデル ID から決めます（`repo_name` は自由に置き換えてかまいません。ユーザー名を含む必要があり、`get_full_repo_name()` 関数はまさにそれを行います）。

```py

repo_name = get_full_repo_name(model_name)
repo_name
```

```python out

```

次に、そのリポジトリをローカルフォルダにクローンできます。すでに存在する場合は、そのローカルフォルダは作業対象リポジトリのクローンである必要があります。

```py

repo = Repository(output_dir, clone_from=repo_name)
```

`repo.push_to_hub()` メソッドを呼ぶことで、`output_dir` に保存したものを何でもアップロードできるようになりました。これにより、各エポックの終了時に中間モデルをアップロードできます。

## 学習ループ[[training-loop]]

完全な学習ループを書く準備が整いました。学習の進み具合を追うプログレスバーを定義した後、ループは3つの部分から構成されます。

- 学習そのもの。`train_dataloader` に対する古典的な反復、モデルを通じた順伝播、それに続く逆伝播とオプティマイザのステップです。
- 評価。`start_logits` と `end_logits` の値をすべて集めてから、NumPy 配列に変換します。評価ループが終わったら、すべての結果を連結します。`Accelerator` が、各プロセスでサンプル数が同じになるよう末尾にいくつかのサンプルを追加している場合があるため、切り捨てる必要がある点に注意してください。
- 保存とアップロード。まずモデルとトークナイザを保存し、次に `repo.push_to_hub()` を呼びます。前と同様に、引数 `blocking=False` を使って、🤗 Hub ライブラリに非同期プロセスでプッシュするよう伝えます。こうすると、学習は通常どおり続き、この（長い）命令はバックグラウンドで実行されます。

学習ループの完全なコードは次のとおりです。

```py
from tqdm.auto import tqdm
import torch

progress_bar = tqdm(range(num_training_steps))

for epoch in range(num_train_epochs):
    # 学習
    model.train()
    for step, batch in enumerate(train_dataloader):
        outputs = model(**batch)
        loss = outputs.loss
        accelerator.backward(loss)

        optimizer.step()
        lr_scheduler.step()
        optimizer.zero_grad()
        progress_bar.update(1)

    # 評価
    model.eval()
    start_logits = []
    end_logits = []
    accelerator.print("Evaluation!")
    for batch in tqdm(eval_dataloader):
        with torch.no_grad():
            outputs = model(**batch)

        start_logits.append(accelerator.gather(outputs.start_logits).cpu().numpy())
        end_logits.append(accelerator.gather(outputs.end_logits).cpu().numpy())

    start_logits = np.concatenate(start_logits)
    end_logits = np.concatenate(end_logits)
    start_logits = start_logits[: len(validation_dataset)]
    end_logits = end_logits[: len(validation_dataset)]

    metrics = compute_metrics(
        start_logits, end_logits, validation_dataset, raw_datasets["validation"]
    )
    print(f"epoch {epoch}:", metrics)

    # 保存とアップロード
    accelerator.wait_for_everyone()
    unwrapped_model = accelerator.unwrap_model(model)
    unwrapped_model.save_pretrained(output_dir, save_function=accelerator.save)
    if accelerator.is_main_process:
        tokenizer.save_pretrained(output_dir)
        repo.push_to_hub(
            commit_message=f"Training in progress epoch {epoch}", blocking=False
        )
```

🤗 Accelerate で保存されたモデルを見るのが初めての場合のために、それに伴う3行のコードを少し見てみましょう。

```py
accelerator.wait_for_everyone()
unwrapped_model = accelerator.unwrap_model(model)
unwrapped_model.save_pretrained(output_dir, save_function=accelerator.save)
```

最初の行は自明です。すべてのプロセスに、全員がその段階に到達するまで待ってから続行するよう伝えます。これは、保存前にすべてのプロセスで同じモデルを持つことを確実にするためです。次に、定義したベースモデルである `unwrapped_model` を取得します。`accelerator.prepare()` メソッドはモデルを分散学習用に変更するため、`save_pretrained()` メソッドはもう存在しません。`accelerator.unwrap_model()` メソッドがそのステップを元に戻します。最後に、`save_pretrained()` を呼びますが、そのメソッドに `torch.save()` の代わりに `accelerator.save()` を使うよう伝えます。

これが終わると、`Trainer` で学習したモデルとかなり似た結果を出すモデルが得られるはずです。このコードで学習したモデルは [*huggingface-course/bert-finetuned-squad-accelerate*](https://huggingface.co/huggingface-course/bert-finetuned-squad-accelerate) で確認できます。学習ループへの調整を試したい場合は、上のコードを編集して直接実装できます！
