推論デプロイの最適化

このセクションでは、LLM のデプロイメントを最適化する為の高度なフレームワーク、Text Generation Inference（TGI）、vLLM、llama.cpp を取り上げます。これらのアプリケーションは主に本番環境で使われ、LLM をユーザーに提供する役割を担います。ここでは、1台のマシンで推論を実行する方法ではなく、本番環境へこれらのフレームワークをデプロイする方法に焦点を当てます。

これらのツールを使って推論を出来るだけ効率よく実行し、大規模言語モデルを本番環境へ簡単にデプロイする方法を見ていきます。

フレームワークの選び方

TGI、vLLM、llama.cpp は似た目的を持ちますが、それぞれ異なる特徴があり、用途によって向き不向きがあります。性能と連携の観点から、主な違いを見ていきます。

メモリ管理と性能

TGI は本番環境で安定して予測可能に動作するよう設計されており、固定したシーケンス長を使うことでメモリ使用量を一定に保ちます。メモリ管理には Flash Attention 2 と継続的バッチングの手法を使います。これにより、アテンションの計算を非常に効率よく処理出来、GPU の稼働率を高く維持出来ます。必要に応じてモデルの一部を CPU と GPU の間で移動出来る為、より大きなモデルも扱えます。

💡 Flash Attention の仕組み

Flash Attention は、メモリ帯域のボトルネックに対処して、Transformer モデルのアテンション機構を最適化する技術です。第1章第8節 で見たように、アテンション機構は計算量とメモリ使用量が二乗オーダーになる為、長いシーケンスでは非効率です。

鍵となる工夫は、High Bandwidth Memory（HBM）と、より高速な SRAM キャッシュの間で、メモリ転送をどう管理するかにあります。従来のアテンションは HBM と SRAM の間でデータ転送を繰り返し、GPU を待たせるボトルネックを生んでいました。Flash Attention はデータを一度だけ SRAM に読み込み、全ての計算をそこで行う為、高コストなメモリ転送を最小限に抑えられます。

効果が最も大きいのは学習時ですが、VRAM 使用量の削減と効率の向上は推論でも有効で、より高速でスケーラブルな LLM サービングを可能にします。

vLLM は、PagedAttention を使った別の方法でメモリを管理します。コンピュータがメモリをページ単位で管理するのと同じように、vLLM はモデルのメモリを小さなブロックに分割します。この仕組みにより、長さの異なるリクエストにも柔軟に対応出来、メモリの無駄を抑えられます。異なるリクエスト間でのメモリ共有が特に得意で、メモリの断片化も減らせる為、システム全体の効率が上がります。

💡 PagedAttention の仕組み

PagedAttention は、LLM の推論でボトルネックになり易い KVキャッシュのメモリ管理を改善する技術です。第1章第8節 で見たように、テキスト生成の際、モデルは冗長な計算を減らす為、生成したトークンごとにアテンションのキーとバリュー（KVキャッシュ）を保存します。KVキャッシュは、特に長いシーケンスや複数のリクエストを同時に処理する場合に、膨大な大きさになることがあります。

vLLM の鍵となる工夫は、このキャッシュの管理方法にあります。

  1. メモリページング：KVキャッシュを1つの大きなブロックとして扱うのではなく、固定サイズの「ページ」に分割します（オペレーティングシステムの仮想メモリと似た考え方です）。
  2. 非連続な配置：ページは GPU メモリ上に連続して配置する必要がない為、メモリの割り当てを柔軟に行えます。
  3. ページテーブルの管理：ページテーブルが、どのページがどのシーケンスに属するかを記録し、効率的な検索とアクセスを可能にします。
  4. メモリ共有：並列サンプリングのような処理では、プロンプトの KVキャッシュを保存したページを、複数のシーケンスで共有出来ます。

PagedAttention のアプローチは、従来の手法と比べて最大で24倍のスループットを実現出来、本番環境への LLM デプロイを大きく変えるものです。PagedAttention の仕組みを更に深く知りたい場合は、vLLM ドキュメントのガイド を読んでみてください。

llama.cpp は、元々コンシューマー向けハードウェアで LLaMA モデルを動かす為に設計された、高度に最適化された C/C++ 実装です。CPU の効率を重視し、任意で GPU アクセラレーションも使えます。リソースに制約の有る環境に最適です。llama.cpp は量子化の手法を使って、良好な性能を保ちながらモデルのサイズとメモリ要件を削減します。各種 CPU アーキテクチャ向けに最適化されたカーネルを実装し、効率的なトークン生成の為の基本的な KVキャッシュ管理も備えています。

💡 llama.cpp の量子化の仕組み

llama.cpp の量子化では、モデルの重みを 32 ビットや 16 ビットの浮動小数点形式から、8 ビット整数（INT8）や 4 ビット、あるいはそれ以下のビット幅の低精度形式に変換します。これにより、品質の低下を最小限に抑えながら、メモリ使用量を大幅に削減し、推論速度を向上させます。

llama.cpp の量子化の主な特徴は次の通りです。 1. 複数の量子化レベル：8 ビット、4 ビット、3 ビット、更には 2 ビットの量子化に対応します 2. GGML/GGUF フォーマット：量子化した推論向けに最適化された独自のテンソルフォーマットを使います 3. 混合精度：モデルの部位ごとに異なる量子化レベルを適用出来ます 4. ハードウェア固有の最適化：各種 CPU アーキテクチャ（AVX2、AVX-512、NEON）向けに最適化されたコードパスを含みます

このアプローチにより、メモリの限られたコンシューマー向けハードウェアでも数十億パラメータのモデルを動かせる為、ローカルデプロイやエッジデバイスに最適です。

デプロイと連携

次に、フレームワークごとにデプロイと連携がどう違うかを見ていきます。

TGI は、本番運用に必要な機能を備えており、企業向けの大規模なシステムへの導入にも適しています。Kubernetes に対応しているほか、Prometheus や Grafana による監視、自動スケーリング、包括的な安全機能も利用出来ます。企業向けの詳細なログ記録に加え、コンテンツフィルタリングやレート制限などの保護機能も備えている為、安全で安定した運用が可能です。

vLLM は、柔軟性が高く、開発者が扱い易いデプロイ方法を提供します。中核は Python で構築されており、既存のアプリケーションで OpenAI の API を簡単に置き換えられます。性能を最大限に引き出すことを重視しており、用途に合わせて設定をカスタマイズ出来ます。クラスタ管理では Ray との相性が特に良く、高い性能と適応性が必要な場合に適した選択肢です。

llama.cpp はシンプルさと移植性を優先します。サーバー実装は軽量で、高性能なサーバーからコンシューマー向けノートパソコン、更には一部のハイエンドモバイルデバイスまで、幅広いハードウェアで動作します。依存関係が最小限で、中核はシンプルな C/C++ なので、Python フレームワークのインストールが難しい環境でもデプロイし易いのが特徴です。サーバーは OpenAI 互換の API を提供しながら、他のソリューションに比べてリソース使用量を大幅に抑えています。

はじめ方

これらのフレームワークを使って LLM をデプロイする方法を、インストールと基本設定から見ていきます。

インストールと基本設定

TGI はインストールも使い方も簡単で、Hugging Face のエコシステムと深く統合されています。 まず、Docker を使って TGI サーバーを起動します。 
docker run --gpus all \
    --shm-size 1g \
    -p 8080:80 \
    -v ~/.cache/huggingface:/data \
    ghcr.io/huggingface/text-generation-inference:latest \
    --model-id HuggingFaceTB/SmolLM2-360M-Instruct
次に、Hugging Face の InferenceClient を使ってアクセスします。 
from huggingface_hub import InferenceClient

# TGI エンドポイントを指すクライアントを初期化
client = InferenceClient(
    model="http://localhost:8080",  # TGI サーバーへの URL
)

# テキスト生成
response = client.text_generation(
    "Tell me a story",
    max_new_tokens=100,
    temperature=0.7,
    top_p=0.95,
    details=True,
    stop_sequences=[],
)
print(response.generated_text)

# チャット形式の場合
response = client.chat_completion(
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Tell me a story"},
    ],
    max_tokens=100,
    temperature=0.7,
    top_p=0.95,
)
print(response.choices[0].message.content)
（プロンプトの訳：システムプロンプトは「あなたは親切なアシスタントです」、ユーザーの文は「物語を聞かせてください」です） 代わりに、OpenAI クライアントを使うことも出来ます。 
from openai import OpenAI

# TGI エンドポイントを指すクライアントを初期化
client = OpenAI(
    base_url="http://localhost:8080/v1",  # /v1 を必ず含める
    api_key="not-needed",  # TGI はデフォルトでは API キーを必要としない
)

# チャット補完
response = client.chat.completions.create(
    model="HuggingFaceTB/SmolLM2-360M-Instruct",
    messages=[
        {"role": "system", "content": "You are a helpful assistant."},
        {"role": "user", "content": "Tell me a story"},
    ],
    max_tokens=100,
    temperature=0.7,
    top_p=0.95,
)
print(response.choices[0].message.content)

基本的なテキスト生成

各フレームワークでのテキスト生成の例を見ていきます。

まず、詳細なパラメータを指定して TGI をデプロイします。 
docker run --gpus all \
    --shm-size 1g \
    -p 8080:80 \
    -v ~/.cache/huggingface:/data \
    ghcr.io/huggingface/text-generation-inference:latest \
    --model-id HuggingFaceTB/SmolLM2-360M-Instruct \
    --max-total-tokens 4096 \
    --max-input-length 3072 \
    --max-batch-total-tokens 8192 \
    --waiting-served-ratio 1.2
InferenceClient を使うと、柔軟なテキスト生成が出来ます。 
from huggingface_hub import InferenceClient

client = InferenceClient(model="http://localhost:8080")

# 詳細パラメータの例
response = client.chat_completion(
    messages=[
        {"role": "system", "content": "You are a creative storyteller."},
        {"role": "user", "content": "Write a creative story"},
    ],
    temperature=0.8,
    max_tokens=200,
    top_p=0.95,
)
print(response.choices[0].message.content)

# 生のテキスト生成
response = client.text_generation(
    "Write a creative story about space exploration",
    max_new_tokens=200,
    temperature=0.8,
    top_p=0.95,
    repetition_penalty=1.1,
    do_sample=True,
    details=True,

vLLM には、細かな制御が出来るネイティブな Python インターフェースもあります。 
from vllm import LLM, SamplingParams

# 詳細パラメータを指定してモデルを初期化
llm = LLM(
    model="HuggingFaceTB/SmolLM2-360M-Instruct",
    gpu_memory_utilization=0.85,
    max_num_batched_tokens=8192,
    max_num_seqs=256,
    block_size=16,
)

# サンプリングパラメータを設定
sampling_params = SamplingParams(
    temperature=0.8,  # 高いほど創造的になる
    top_p=0.95,  # 確率の累積が上位 95% までのトークンを対象にする
    max_tokens=100,  # 最大長
    presence_penalty=1.1,  # 繰り返しを抑える
    frequency_penalty=1.1,  # 繰り返しを抑える
    stop=["\n\n", "###"],  # 停止シーケンス
)

# テキストを生成
prompt = "Write a creative story"
outputs = llm.generate(prompt, sampling_params)
print(outputs[0].outputs[0].text)

# チャット形式のやり取りの場合
chat_prompt = [
    {"role": "system", "content": "You are a creative storyteller."},
    {"role": "user", "content": "Write a creative story"},
]
formatted_prompt = llm.get_chat_template()(chat_prompt)  # モデルのチャットテンプレートを使う
outputs = llm.generate(formatted_prompt, sampling_params)
print(outputs[0].outputs[0].text)

生成の高度な制御

トークンの選択とサンプリング

テキスト生成では、次のトークンを1つずつ選んでいきます。どのトークンを選ぶかは、様々なパラメータで制御出来ます。

  1. 生のロジット：各トークンについて最初に出力される確率
  2. 温度（Temperature）：選択のランダムさを制御します（高い程創造的になります）
  3. Top-p（Nucleus）サンプリング：確率の累積が X% に達するまでの上位トークンに絞り込みます
  4. Top-k フィルタリング：選択肢を最も確率の高い k 個のトークンに制限します

これらのパラメータの設定方法は次の通りです。

client.generate(
    "Write a creative story",
    temperature=0.8,  # 高いほど創造的になる
    top_p=0.95,  # 確率の累積が上位 95% までのトークンを対象にする
    top_k=50,  # 上位 50 トークンを対象にする
    max_new_tokens=100,  # 最大長
    repetition_penalty=1.1,  # 繰り返しを抑える
)

# OpenAI API 互換経由
response = client.completions.create(
    model="smollm2-1.7b-instruct",  # モデル名（llama.cpp サーバーでは任意の文字列でよい）
    prompt="Write a creative story",
    temperature=0.8,  # 高いほど創造的になる
    top_p=0.95,  # 確率の累積が上位 95% までのトークンを対象にする
    frequency_penalty=1.1,  # 繰り返しを抑える
    presence_penalty=0.1,  # 繰り返しを抑える
    max_tokens=100,  # 最大長
)

# llama-cpp-python で直接アクセス
output = llm(
    "Write a creative story",
    temperature=0.8,
    top_p=0.95,
    top_k=50,
    max_tokens=100,
    repeat_penalty=1.1,
)

params = SamplingParams(
    temperature=0.8,  # 高いほど創造的になる
    top_p=0.95,  # 確率の累積が上位 95% までのトークンを対象にする
    top_k=50,  # 上位 50 トークンを対象にする
    max_tokens=100,  # 最大長
    presence_penalty=0.1,  # 繰り返しを抑える
)
llm.generate("Write a creative story", sampling_params=params)

繰り返しの制御

各フレームワークには、生成テキストで同じ表現が繰り返されるのを抑える機能があります。

client.generate(
    "Write a varied text",
    repetition_penalty=1.1,  # 繰り返されたトークンにペナルティを与える
    no_repeat_ngram_size=3,  # 3-gram の繰り返しを防ぐ
)

# OpenAI API 経由
response = client.completions.create(
    model="smollm2-1.7b-instruct",
    prompt="Write a varied text",
    frequency_penalty=1.1,  # 頻出トークンにペナルティを与える
    presence_penalty=0.8,  # すでに出現したトークンにペナルティを与える
)

# ライブラリで直接アクセス
output = llm(
    "Write a varied text",
    repeat_penalty=1.1,  # 繰り返されたトークンにペナルティを与える
    frequency_penalty=0.5,  # 追加の頻出ペナルティ
    presence_penalty=0.5,  # 追加の出現ペナルティ

params = SamplingParams(
    presence_penalty=0.1,  # トークンの出現にペナルティを与える
    frequency_penalty=0.1,  # トークンの頻出にペナルティを与える
)

メモリ管理

各フレームワークは、効率的な推論の為に高度なメモリ管理の手法を実装しています。

TGI は Flash Attention 2 と継続的バッチングを使います。 
# メモリ最適化を施した Docker デプロイ
docker run --gpus all -p 8080:80 \
    --shm-size 1g \
    ghcr.io/huggingface/text-generation-inference:latest \
    --model-id HuggingFaceTB/SmolLM2-1.7B-Instruct \
    --max-batch-total-tokens 8192 \
    --max-input-length 4096
llama.cpp は量子化と最適化されたメモリレイアウトを使います。 
# メモリ最適化を施したサーバー
./server \
    -m smollm2-1.7b-instruct.Q4_K_M.gguf \
    --host 0.0.0.0 \
    --port 8080 \
    -c 2048 \               # コンテキストサイズ
    --threads 4 \           # CPU スレッド数
    --n-gpu-layers 32 \     # 大きなモデルでは GPU レイヤーを増やす
    --mlock \               # メモリをロックしてスワップを防ぐ
    --cont-batching         # 継続的バッチングを有効化
GPU に収まらない大きなモデルには、CPU オフロードが使えます。 
./server \
    -m smollm2-1.7b-instruct.Q4_K_M.gguf \
    --n-gpu-layers 20 \     # 最初の 20 層を GPU に置く
    --threads 8             # CPU レイヤーには CPU スレッドを多めに使う
vLLM は最適なメモリ管理の為に PagedAttention を使います。 
from vllm.engine.arg_utils import AsyncEngineArgs

engine_args = AsyncEngineArgs(
    model="HuggingFaceTB/SmolLM2-1.7B-Instruct",
    gpu_memory_utilization=0.85,
    max_num_batched_tokens=8192,
    block_size=16,
)

llm = LLM(engine_args=engine_args)
