このセクションでは、🤗 Transformers のトークナイザに備わる機能を詳しく見ていきます。トークナイザは、これまで使ってきた入力のトークン化や、ID からテキストへのデコードだけに使うものではありません。特に 🤗 Tokenizers を土台とするトークナイザには、更に多くの機能があります。ここではその追加機能を説明する為に、[Chapter 1](/course/chapter1) で初めて使った `token-classification`（当時は `ner` と呼んでいました）と `question-answering` の各パイプラインについて、結果を再現する方法を確かめます。

<Youtube id="g8quOxoqhHQ"/>

以降の説明では、トークナイザを「低速」と「高速」に区別することが度々あります。低速トークナイザは、🤗 Transformers ライブラリの中で Python により実装されたものです。高速トークナイザは、Rust で書かれた 🤗 Tokenizers が提供します。[Chapter 5](/course/chapter5/3) には、Drug Review Dataset のトークン化に要した時間を、高速トークナイザと低速トークナイザで比べた表がありました。その表を覚えていれば、高速・低速と呼ぶ理由が分かります。

|               | 高速トークナイザ | 低速トークナイザ
:--------------:|:--------------:|:-------------:
`batched=True`  | 10.8s          | 4min41s
`batched=False` | 59.2s          | 5min3s

> [!WARNING]
> ⚠️ 1つの文をトークン化するだけでは、低速版と高速版の速度差は常には現れません。高速版の方が遅い場合すらあります。多数のテキストを並列にまとめてトークン化して初めて、違いがはっきりします。

## バッチエンコーディング[[batch-encoding]]

<Youtube id="3umI3tm27Vw"/>

トークナイザの出力は、単なる Python の辞書ではありません。得られるのは、特別な `BatchEncoding` オブジェクトです。これは辞書のサブクラスです。その為、これまでも結果にインデックスでアクセスして問題がありませんでした。更に、主に高速トークナイザで使う追加のメソッドも備えています。

高速トークナイザの重要な機能は、並列化だけではありません。各トークンが元のテキストのどの範囲から生まれたかを、常に記録し続けます。この機能を*オフセットマッピング*と呼びます。オフセットマッピングがあると、単語と、その単語から生成されたトークンとを対応付けられます。元のテキストの各文字についても、その文字を含むトークンとの対応付けが出来ます。逆方向の対応付けも可能です。

例を見てみましょう。

```py
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained("bert-base-cased")
example = "My name is Sylvain and I work at Hugging Face in Brooklyn."
encoding = tokenizer(example)
print(type(encoding))
```

前述の通り、トークナイザの出力は `BatchEncoding` オブジェクトです。

```python out
<class 'transformers.tokenization_utils_base.BatchEncoding'>
```

デフォルトでは、`AutoTokenizer` クラスは高速トークナイザを選びます。その為、この `BatchEncoding` オブジェクトが備える追加のメソッドを使えます。トークナイザが高速か低速かを確認する方法は2つあります。まず、`tokenizer` の `is_fast` 属性を確認する方法です。

```python
tokenizer.is_fast
```

```python out
True
```

もう1つは、`encoding` の同じ属性を確認する方法です。

```python
encoding.is_fast
```

```python out
True
```

高速トークナイザで何が出来るかを見ていきます。まず、ID からトークンへ変換し直さなくても、トークンそのものにアクセス出来ます。

```py
encoding.tokens()
```

```python out
['[CLS]', 'My', 'name', 'is', 'S', '##yl', '##va', '##in', 'and', 'I', 'work', 'at', 'Hu', '##gging', 'Face', 'in',
 'Brooklyn', '.', '[SEP]']
```

この例では、インデックス5のトークンが `##yl` です。これは元の文の "Sylvain" という単語の一部に当たります。`word_ids()` メソッドを使うと、各トークンがどの単語に由来するか、その単語のインデックスも取得出来ます。

```py
encoding.word_ids()
```

```python out
[None, 0, 1, 2, 3, 3, 3, 3, 4, 5, 6, 7, 8, 8, 9, 10, 11, 12, None]
```

特殊トークンの `[CLS]` と `[SEP]` は `None` に対応し、それ以外の各トークンは、由来となった単語に対応していることが分かります。この対応は、トークンが単語の先頭にあるかどうか、2つのトークンが同じ単語の中にあるかどうかの判定に役立ちます。判定には `##` 接頭辞も使えますが、使えるのは BERT 系のトークナイザだけです。

これに対してこのメソッドは、高速トークナイザであれば種類を問いません。次の章では、この対応付けを使って、固有表現認識（NER）や品詞タグ付け（POS tagging）といったタスクで、単語ごとのラベルをトークンへ適切に適用する方法を見ます。マスク言語モデリングで、同じ単語に由来するトークンをまとめてマスクする手法（単語全体マスキング、whole word masking）にも使えます。

> [!TIP]
> 「単語」の定義は単純ではありません。例えば、"I'll"（"I will" の短縮形）は、1つの単語でしょうか、2つの単語でしょうか。答えは、トークナイザと、そのトークナイザが行う事前トークン化の内容によって変わります。空白だけで分割するトークナイザは1つの単語と見なします。空白に加えて句読点でも分割するトークナイザは、2つの単語と見なします。
>
> **試してみましょう！** `bert-base-cased` と `roberta-base` のチェックポイントからトークナイザを作成し、"81s" をトークン化してみてください。何が観察出来ますか。単語 ID はどうなっていますか。

トークンと文との対応付けには、`sentence_ids()` メソッドを使います。但し、この情報はトークナイザが返す `token_type_ids` からも得られます。

単語やトークンと、元のテキストの文字との対応付けには、`word_to_chars()`、`token_to_chars()`、`char_to_word()`、`char_to_token()` の各メソッドを使います。対応付けは双方向にたどれます。例えば、`word_ids()` メソッドからは、`##yl` がインデックス3の単語の一部であることが分かりました。その単語が文中のどれかは、次のようにして確かめられます。

```py
start, end = encoding.word_to_chars(3)
example[start:end]
```

```python out
Sylvain
```

これらの対応付けは全て、高速トークナイザが、各トークンの由来となったテキストの範囲を*オフセット*のリストとして記録しているからこそ可能です。次に、このオフセットの使い方を示す為、`token-classification` パイプラインの結果を手作業で再現します。

> [!TIP]
> **試してみましょう！** 自分で例文を作り、どのトークンがどの単語 ID に関連付けられているか、また1つの単語の文字範囲を抽出するにはどうすればよいか理解してみてください。ボーナスとして、2つの文を入力に使って、文 ID が妥当かどうか確認してみましょう。

## `token-classification` パイプラインの内部[[inside-the-token-classification-pipeline]]

### パイプラインで基本的な結果を得る[[getting-the-base-results-with-the-pipeline]]

まず、トークン分類パイプラインを用意し、後で手作業の結果と比べる為の基準にします。このパイプラインがデフォルトで使うモデルは [`dbmdz/bert-large-cased-finetuned-conll03-english`](https://huggingface.co/dbmdz/bert-large-cased-finetuned-conll03-english) で、文に対して NER を実行するモデルです。

```py
from transformers import pipeline

token_classifier = pipeline("token-classification")
token_classifier("My name is Sylvain and I work at Hugging Face in Brooklyn.")
```

```python out
[{'entity': 'I-PER', 'score': 0.9993828, 'index': 4, 'word': 'S', 'start': 11, 'end': 12},
 {'entity': 'I-PER', 'score': 0.99815476, 'index': 5, 'word': '##yl', 'start': 12, 'end': 14},
 {'entity': 'I-PER', 'score': 0.99590725, 'index': 6, 'word': '##va', 'start': 14, 'end': 16},
 {'entity': 'I-PER', 'score': 0.9992327, 'index': 7, 'word': '##in', 'start': 16, 'end': 18},
 {'entity': 'I-ORG', 'score': 0.97389334, 'index': 12, 'word': 'Hu', 'start': 33, 'end': 35},
 {'entity': 'I-ORG', 'score': 0.976115, 'index': 13, 'word': '##gging', 'start': 35, 'end': 40},
 {'entity': 'I-ORG', 'score': 0.98879766, 'index': 14, 'word': 'Face', 'start': 41, 'end': 45},
 {'entity': 'I-LOC', 'score': 0.99321055, 'index': 16, 'word': 'Brooklyn', 'start': 49, 'end': 57}]
```

モデルは、"Sylvain" の各トークンを人物、"Hugging Face" の各トークンを組織、"Brooklyn" を場所と、正しく特定しています。パイプラインには、同じエンティティに対応するトークンをまとめてグループ化させることも出来ます。

```py
from transformers import pipeline

token_classifier = pipeline("token-classification", aggregation_strategy="simple")
token_classifier("My name is Sylvain and I work at Hugging Face in Brooklyn.")
```

```python out
[{'entity_group': 'PER', 'score': 0.9981694, 'word': 'Sylvain', 'start': 11, 'end': 18},
 {'entity_group': 'ORG', 'score': 0.97960204, 'word': 'Hugging Face', 'start': 33, 'end': 45},
 {'entity_group': 'LOC', 'score': 0.99321055, 'word': 'Brooklyn', 'start': 49, 'end': 57}]
```

`aggregation_strategy` の選択によって、グループ化したエンティティのスコアの計算方法が変わります。`"simple"` では、エンティティに含まれる各トークンのスコアの平均を、そのエンティティのスコアとします。例えば、"Sylvain" のスコアは、前の例のトークン `S`、`##yl`、`##va`、`##in` のスコアの平均です。他の戦略には次のものがあります。

- `"first"`：エンティティの最初のトークンのスコアを、そのエンティティのスコアとします（"Sylvain" であれば、トークン `S` のスコア 0.993828 です）
- `"max"`：エンティティ内のトークンのスコアの最大値を取ります（"Hugging Face" であれば、"Face" のスコア 0.98879766 です）
- `"average"`：エンティティを構成する単語ごとのスコアの平均を取ります（"Sylvain" では `"simple"` と変わりませんが、"Hugging Face" では、"Hugging" の 0.975 と "Face" の 0.98879 の平均である 0.9819 になります）

次に、`pipeline()` 関数を使わずに同じ結果を得る方法を見ます。

### 入力から予測へ[[from-inputs-to-predictions]]

{#if fw === 'pt'}

まず、入力をトークン化し、モデルに通します。手順は [Chapter 2](/course/chapter2) と全く同じです。`AutoXxx` クラスでトークナイザとモデルを用意し、例文に適用します。

```py
from transformers import AutoTokenizer, AutoModelForTokenClassification

model_checkpoint = "dbmdz/bert-large-cased-finetuned-conll03-english"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)
model = AutoModelForTokenClassification.from_pretrained(model_checkpoint)

example = "My name is Sylvain and I work at Hugging Face in Brooklyn."
inputs = tokenizer(example, return_tensors="pt")
outputs = model(**inputs)
```

ここで使うのは `AutoModelForTokenClassification` です。出力には、入力シーケンスのトークンごとに1組のロジットが含まれます。

```py
print(inputs["input_ids"].shape)

```

```python out

```

バッチは、19トークンのシーケンス1つだけです。ラベルは9種類ある為、モデルの出力の shape は 1 x 19 x 9 になります。テキスト分類パイプラインと同様に、softmax 関数でロジットを確率に変換し、argmax を取って予測とします。softmax は順序を変えない為、argmax はロジットに対して直接取ることが出来ます。

{#if fw === 'pt'}

```py

probabilities = torch.nn.functional.softmax(outputs.logits, dim=-1)[0].tolist()
predictions = outputs.logits.argmax(dim=-1)[0].tolist()
print(predictions)
```

{:else}

```py
import tensorflow as tf

probabilities = tf.math.softmax(outputs.logits, axis=-1)[0]
probabilities = probabilities.numpy().tolist()
predictions = tf.math.argmax(outputs.logits, axis=-1)[0]
predictions = predictions.numpy().tolist()
print(predictions)
```

{/if}

```python out
[0, 0, 0, 0, 4, 4, 4, 4, 0, 0, 0, 0, 6, 6, 6, 0, 8, 0, 0]
```

インデックスとラベルの対応は、`model.config.id2label` 属性に含まれています。予測の解釈にはこの対応を使います。

```py
model.config.id2label
```

```python out
{0: 'O',
 1: 'B-MISC',
 2: 'I-MISC',
 3: 'B-PER',
 4: 'I-PER',
 5: 'B-ORG',
 6: 'I-ORG',
 7: 'B-LOC',
 8: 'I-LOC'}
```

ラベルは、先に見た通り9つあります。どの固有表現にも属さないトークンには `O`（"outside" の略）が付きます。残りは、エンティティの種類（その他、人物、組織、場所）ごとに2つずつのラベルです。`B-XXX` は、トークンがエンティティ `XXX` の先頭であることを示します。`I-XXX` は、トークンがエンティティ `XXX` の内部にあることを示します。この例では、モデルはトークン `S` を `B-PER`（人物エンティティの開始）に、トークン `##yl`、`##va`、`##in` を `I-PER`（人物エンティティの内部）に分類すると予想されます。

モデルは、この4つのトークン全てに `I-PER` を付けました。一見すると誤りに見えますが、そうとは言い切れません。`B-` と `I-` のラベルには、*IOB1* と *IOB2* という2つの形式がある為です。ここまで紹介してきたのは IOB2 形式（下図のピンク）です。IOB1 形式（下図の青）では、`B-` で始まるラベルは、同じ種類のエンティティが2つ隣接する場合に、その区切りにだけ使われます。今回のモデルは、その形式を使ったデータセットでファインチューニングされている為、トークン `S` にも `I-PER` を割り当てます。


結果は以前のものとほぼ同じですが、1つだけ足りない情報があります。パイプラインの結果には、元の文における各エンティティの `start` と `end` も含まれていました。ここで必要になるのがオフセットマッピングです。オフセットは、トークナイザを入力に適用する際に `return_offsets_mapping=True` を設定すれば取得出来ます。

```py
inputs_with_offsets = tokenizer(example, return_offsets_mapping=True)
inputs_with_offsets["offset_mapping"]
```

```python out
[(0, 0), (0, 2), (3, 7), (8, 10), (11, 12), (12, 14), (14, 16), (16, 18), (19, 22), (23, 24), (25, 29), (30, 32),
 (33, 35), (35, 40), (41, 45), (46, 48), (49, 57), (57, 58), (0, 0)]
```

各タプルが、トークンに対応するテキストの範囲です。`(0, 0)` は特殊トークン専用です。インデックス5のトークン `##yl` のオフセットは `(12, 14)` でした。例文から対応する範囲を切り取ると、次のようになります。

```py
example[12:14]
```

`##` を除いた、元のテキストの範囲が得られます。

```python out
yl
```

これを使えば、先ほどの結果を完成させられます。

```py
results = []
inputs_with_offsets = tokenizer(example, return_offsets_mapping=True)
tokens = inputs_with_offsets.tokens()
offsets = inputs_with_offsets["offset_mapping"]

for idx, pred in enumerate(predictions):
    label = model.config.id2label[pred]
    if label != "O":
        start, end = offsets[idx]
        results.append(
            {
                "entity": label,
                "score": probabilities[idx][pred],
                "word": tokens[idx],
                "start": start,
                "end": end,
            }
        )

print(results)
```

### エンティティのグループ化[[grouping-entities]]

各エンティティの start と end をオフセットから決める方法は便利ですが、この情報自体は必須ではありません。オフセットが真価を発揮するのは、エンティティをグループ化する場合です。煩雑なコードを書かずに済みます。

例えば、トークン `Hu`、`##gging`、`Face` をまとめたいとします。オフセットがなければ、最初の2つは `##` を取り除いて連結し、`Face` は `##` で始まらないので空白を入れてつなげる、といった個別のルールを用意しなければなりません。しかも、そのルールが通用するのはこの種類のトークナイザだけです。SentencePiece や Byte-Pair-Encoding のトークナイザ（この章の後半で説明します）では、別のルールが要ります。

オフセットを使えば、このような個別のコードは不要です。元のテキストから、最初のトークンの開始位置から最後のトークンの終了位置までの範囲を切り取るだけで済みます。トークン `Hu`、`##gging`、`Face` の場合は、文字33（`Hu` の開始位置）から文字45（`Face` の終了位置）までの範囲です。

```py
example[33:45]
```

```python out
Hugging Face
```

予測を後処理してエンティティをグループ化するコードでは、連続する `I-XXX` を同じエンティティとしてまとめます。先頭のトークンだけは、`B-XXX` でも `I-XXX` でも構いません。グループ化は、`O` が現れた場合、新しい種類のエンティティが始まった場合、又は同じ種類のエンティティの開始を示す `B-XXX` が現れた場合に終了します。

```py
import numpy as np

results = []
inputs_with_offsets = tokenizer(example, return_offsets_mapping=True)
tokens = inputs_with_offsets.tokens()
offsets = inputs_with_offsets["offset_mapping"]

idx = 0
while idx < len(predictions):
    pred = predictions[idx]
    label = model.config.id2label[pred]
    if label != "O":
        # B- または I- を取り除く
        label = label[2:]
        start, _ = offsets[idx]

        # I-label とラベル付けされたすべてのトークンを取得する
        all_scores = []
        while (
            idx < len(predictions)
            and model.config.id2label[predictions[idx]] == f"I-{label}"
        ):
            all_scores.append(probabilities[idx][pred])
            _, end = offsets[idx]
            idx += 1

        # スコアは、グループ化されたエンティティ内のすべてのトークンのスコアの平均
        score = np.mean(all_scores).item()
        word = example[start:end]
        results.append(
            {
                "entity_group": label,
                "score": score,
                "word": word,
                "start": start,
                "end": end,
            }
        )
    idx += 1

print(results)
```
