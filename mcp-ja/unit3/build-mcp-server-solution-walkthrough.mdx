# Unit 3 ソリューション解説：MCP でプルリクエストエージェントを構築する

## 概要

この解説では、Unit 3 のプルリクエストエージェントの完全なソリューションを案内します。これは、コード変更の分析、CI/CD パイプラインの監視、チームコミュニケーションの自動化により、開発者がより良いプルリクエストを作成出来るよう支援する MCP サーバーです。このソリューションは、3つの MCP プリミティブ（Tools、Resources、Prompts）が実世界のワークフローで連携する様子を示します。

## アーキテクチャ概要

PR Agent は、完全な自動化システムを段階的に構築する、相互接続されたモジュールで構成されています。

1. **MCP サーバーの構築**：PR テンプレート提案用 Tools を備えた基本サーバー
2. **スマートなファイル分析**：Resources を使ってプロジェクトの情報を参照する、高度なファイル分析
3. **GitHub Actions 連携**：標準化された Prompts による CI/CD モニタリング
4. **Hugging Face Hub 連携**：モデルのデプロイとデータセット PR のワークフロー
5. **Slack 通知**：全 MCP プリミティブを連携させたチームコミュニケーション

## Module 1：MCP サーバーの構築

### 構築するもの
ファイル変更を分析し、MCP Tools を使って適切な PR テンプレートを提案する、最小限の MCP サーバーです。

### 主要コンポーネント

#### 1. サーバーの初期化（`server.py`）
```python
# サーバーは3つの必須ツールを登録します：
# - analyze_file_changes: 変更されたファイルに関する構造化データを返す
# - get_pr_templates: メタデータ付きで利用可能なテンプレートを一覧表示する
# - suggest_template: インテリジェントなテンプレート推奨を提供する
```

サーバーは MCP SDK を使ってこれらのツールを Claude Code に公開し、Claude Code が情報を集め、どの PR テンプレートを使うか賢い判断を下せるようにします。

#### 2. ファイル分析ツール
`analyze_file_changes` ツールは git diff を調べて、以下を特定します。
- ファイルの種類と拡張子
- 変更されたファイルの数
- 追加／削除された行数
- よくあるパターン（テスト、設定、ドキュメント）

この構造化データにより、Claude は判断ロジックをハードコードすることなく、変更の性質を理解出来ます。

#### 3. テンプレート管理
テンプレートは `templates/` ディレクトリに Markdown ファイルとして保存されます。
- `bug.md` - バグ修正用
- `feature.md` - 新機能用
- `docs.md` - ドキュメント更新用
- `refactor.md` - コードリファクタリング用

各テンプレートには、分析に基づいて Claude が埋められるプレースホルダーが含まれています。

### Claude がこれらのツールを使う方法

1. Claude が `analyze_file_changes` を呼び出し、何が変更されたかを把握する
2. `get_pr_templates` で利用可能な選択肢を確認する
3. 分析データを渡して `suggest_template` を呼び出す
4. 理由付きの推奨を受け取る
5. 具体的な変更に基づいてテンプレートをカスタマイズ出来る

### 学習成果
- ツールの登録とスキーマの理解
- 構造化データで Claude に判断させること
- データ収集と判断ロジックの分離

## Module 2：スマートなファイル分析

### 構築するもの
MCP Resources を使い、プロジェクトの情報やチームのガイドラインを参照出来るようにしたファイル分析機能です。

### 主要コンポーネント

#### 1. リソースの登録
サーバーは4種類のリソースを公開します。
```python
# リソースは以下への読み取り専用アクセスを提供します：
# - file://templates/ - PR テンプレートファイル
# - file://project-context/ - コーディング規約と慣習
# - git://recent-changes/ - コミット履歴とパターン
# - team://guidelines/ - レビュープロセスと基準
```

#### 2. プロジェクト文脈リソース
`project-context/` ディレクトリには以下が含まれます。
- `coding-standards.md` - 言語固有の慣習
- `review-guidelines.md` - レビュアーが注目するポイント
- `architecture.md` - システム設計パターン
- `dependencies.md` - サードパーティライブラリの方針

Claude はこれらを読んで、プロジェクト固有の要件を理解出来ます。

#### 3. Git 履歴分析
`git://recent-changes/` リソースは以下を提供します。
- 最近のコミットメッセージとパターン
- よくある PR のタイトルと説明
- チームメンバーの貢献パターン
- 過去のテンプレート使用状況

これにより、Claude はチームの慣行に沿ったテンプレートを提案出来ます。

### Claude がリソースを使う方法

1. `team://guidelines/review-process.md` を読み、PR の要件を理解する
2. コーディング規約を確認する為、`file://project-context/coding-standards.md` にアクセスする
3. `git://recent-changes/` を分析し、チームのパターンに合わせる
4. この文脈とファイル分析を組み合わせ、より良い提案を行う

### 強化された意思決定
リソースにより、Claude は次のことが出来るようになります。
- チームの慣習に合ったテンプレートを提案する
- プロジェクト固有の要件を PR に含める
- 説明の中でコーディング規約に言及する
- 過去のチームの慣行に合わせる

### 学習成果
- リソース URI の設計とスキーマ
- プロジェクトの情報に AI がアクセス出来るようにすること
- 文脈を意識した意思決定
- 自動化とチーム基準のバランス

## Module 3：GitHub Actions 連携

### 構築するもの
webhook と標準化されたプロンプトを使い、CI/CD をリアルタイムで監視します。これにより、チームへの情報共有を一貫した方法で行えるようにします。

### 主要コンポーネント

#### 1. Webhook サーバー
Cloudflare Tunnel を使って GitHub Actions イベントを受信します。
```python
# Webhook エンドポイントが処理するもの：
# - workflow_run イベント
# - check_run イベント  
# - pull_request のステータス更新
# - デプロイ通知
```

#### 2. プロンプトテンプレート
4つの標準化されたプロンプトが一貫性を保証します。
- **「Analyze CI Results」**：テストの失敗とビルドエラーを処理する
- **「Generate Status Summary」**：人が読み易い形式でステータスの更新情報を作成する
- **「Create Follow-up Tasks」**：結果に基づいて次のステップを提案する
- **「Draft Team Notification」**：対象読者ごとに更新を整形する

#### 3. イベント処理パイプライン
1. GitHub から webhook を受信する
2. イベントデータを解析し、関連情報を抽出する
3. イベントタイプに応じた適切なプロンプトを使う
4. 標準化されたレスポンスを生成する
5. チーム通知用に保存する

### Claude がプロンプトを使う方法

プロンプト使用例：
```python
# テストが失敗すると、Claude は「Analyze CI Results」プロンプトを使います：
prompt_data = {
    "event_type": "workflow_run",
    "status": "failure",
    "failed_jobs": ["unit-tests", "lint"],
    "error_logs": "...",
    "pr_context": {...}
}

# Claude が生成するもの：
# - 根本原因分析
# - 修正案
# - 影響評価
# - 次のステップ
```

### 標準化されたワークフロー
プロンプトにより、担当者が誰であっても次のことが保証されます。
- CI の失敗が一貫して分析される
- ステータス更新がチームの形式に従う
- フォローアップアクションがプロセスに沿う
- 通知に必要な情報が含まれる

### 学習成果
- webhook 連携パターン
- 一貫性の為のプロンプトエンジニアリング
- イベント駆動アーキテクチャ
- チームワークフローの標準化

## Module 4：Hugging Face Hub 連携

### 構築するもの
LLM とデータセットの PR の為の Hugging Face Hub 連携です。言語モデルを扱うチーム向けの専用ワークフローを追加します。

### 主要コンポーネント

#### 1. Hub 固有のツール
```python
# Hugging Face ワークフロー用ツール：
# - analyze_model_changes: LLM ファイルの変更を検出する
# - validate_dataset_format: 訓練データの準拠をチェックする
# - generate_model_card: モデルのドキュメントを作成／更新する
# - suggest_hub_template: LLM／データセット用の PR テンプレート
```

#### 2. Hub リソース
```python
# Hub の文脈用リソース：
# - hub://model-cards/ - LLM カードのテンプレートと例
# - hub://dataset-formats/ - 訓練データの仕様
# - hub://community-standards/ - Hub コミュニティガイドライン
# - hub://license-info/ - ライセンス互換性チェック
```

#### 3. LLM 固有のプロンプト
```python
# LLM ワークフロー用プロンプト：
# - 「Analyze Model Changes」 - LLM の更新を理解する
# - 「Generate Benchmark Summary」 - 評価指標を作成する
# - 「Check Dataset Quality」 - 訓練データを検証する
# - 「Draft Model Card Update」 - ドキュメントを更新する
```

### Hub 固有のワークフロー

PR が LLM ファイルを変更した場合：
1. **Tool**：`analyze_model_changes` がモデルアーキテクチャの変更を検出する
2. **Resource**：`hub://model-cards/llm-template.md` を読む
3. **Prompt**：「Generate Benchmark Summary」が評価セクションを作成する
4. **Tool**：`generate_model_card` がドキュメントを更新する
5. **Resource**：`hub://license-info/` を参照し、ライセンスの互換性を確認する

### データセット PR の処理
訓練データの更新では：
- 形式の一貫性を検証する
- データ品質の指標をチェックする
- データセットカードを更新する
- 適切なレビュアーを提案する

### 学習成果
- Hugging Face Hub API 連携
- LLM 固有の PR ワークフロー
- モデルとデータセットのドキュメント
- コミュニティ基準への準拠

## Module 5：Slack 通知

### 構築するもの
Tools、Resources、Prompts を組み合わせた自動チーム通知により、ワークフローの完全自動化を実現します。

### 主要コンポーネント

#### 1. コミュニケーションツール
```python
# チーム更新用の3つのツール：
# - send_slack_message: チームチャンネルへ投稿する
# - get_team_members: 通知先を特定する
# - track_notification_status: 配信状況を監視する
```

#### 2. チームリソース
```python
# チームデータ用リソース：
# - team://members/ - 開発者のプロフィールと設定
# - slack://channels/ - チャンネルの設定
# - notification://templates/ - メッセージの形式
```

#### 3. 通知プロンプト
```python
# コミュニケーション用プロンプト：
# - 「Format Team Update」 - メッセージを適切に整形する
# - 「Choose Communication Channel」 - 適切な宛先を選ぶ
# - 「Escalate if Critical」 - 緊急の問題に対応する
```

### 連携の例

重大な PR で CI が失敗した場合：
1. **Tool**：`get_team_members` が PR の作成者とレビュアーを特定する
2. **Resource**：`team://members/{user}/preferences` が通知設定を確認する
3. **Prompt**：「Format Team Update」が適切なメッセージを作成する
4. **Tool**：`send_slack_message` が適切なチャンネルへ配信する
5. **Resource**：`notification://templates/ci-failure` が一貫した形式を保証する
6. **Prompt**：「Escalate if Critical」が、追加のアラートが必要かどうかを判断する

### インテリジェントなルーティング
システムは以下を考慮します。
- チームメンバーの空き状況（カレンダーリソースから）
- 通知の好み（メールか Slack か）
- メッセージの緊急度（PR のラベルに基づく）
- タイムゾーンと勤務時間

### 学習成果
- プリミティブの連携パターン
- 複雑なワークフローのオーケストレーション
- 自動化と人間のニーズのバランス
- 本番対応のエラーハンドリング

## 完全なワークフローの例

典型的な PR に対して、全てのコンポーネントがどのように連携するかを見てみましょう。

1. **開発者が PR を作成する**
   - GitHub の webhook がサーバーを起動する
   - Tool：`analyze_file_changes` が diff を調べる
   - Resource：チームのガイドラインとプロジェクトの文脈を読む
   - Prompt：最適な PR テンプレートを提案する

2. **CI/CD パイプラインが実行される**
   - Webhook がワークフローイベントを受信する
   - Prompt：「Analyze CI Results」が結果を処理する
   - Resource：チームのエスカレーションポリシーを確認する
   - Tool：GitHub の PR ステータスを更新する

3. **Hugging Face Hub 連携**
   - Tool：LLM／データセットの変更を検出する
   - Resource：Hub のガイドラインを読む
   - Prompt：モデルカードの更新を生成する
   - Tool：Hub の基準に照らして検証する

4. **チーム通知**
   - Tool：関係するチームメンバーを特定する
   - Resource：通知設定を読む
   - Prompt：適切なメッセージを整形する
   - Tool：Slack チャンネル経由で送信する

5. **フォローアップアクション**
   - Prompt：「Create Follow-up Tasks」が次のステップを生成する
   - Tool：必要に応じて GitHub の Issue を作成する
   - Resource：ドキュメントへのリンク
   - 全てのプリミティブがシームレスに連携する

## ソリューションの実行

### ローカル開発セットアップ
1. **MCP サーバーを起動する**：`python server.py`
2. **Claude Code を設定する**：MCP 設定にサーバーを追加する
3. **Cloudflare Tunnel をセットアップする**：`cloudflared tunnel --url http://localhost:3000`
4. **webhook を設定する**：GitHub リポジトリにトンネル URL を追加する
5. **ワークフローをテストする**：PR を作成し、自動化の動作を見る

### 設定
設定にはファイルベースのシンプルな方式を採用している為、簡単にセットアップ出来ます。
- GitHub トークンは `.env` ファイルに
- Slack の webhook は設定ファイルに
- テンプレートのカスタマイズは `templates/` に
- 全ての設定を1か所に

## トラブルシューティングガイド

### よくある問題

1. **Webhook がイベントを受信しない**
   - Cloudflare Tunnel が動いているか確認する
   - GitHub の webhook 設定を確認する
   - シークレットが一致するか確認する

2. **ツールが Claude に表示されない**
   - ツールスキーマを検証する
   - サーバーの登録を確認する
   - MCP 接続を見直す

3. **リソースにアクセス出来ない**
   - ファイルの権限を確認する
   - URI の形式を確認する
   - リソースの登録を確認する

4. **プロンプトの結果が一貫しない**
   - プロンプトテンプレートを見直す
   - 提供した文脈を確認する
   - 入力の形式を検証する

## まとめ

この PR Agent は、MCP の3つのプリミティブが連携する力を示しています。Tools が機能を提供し、Resources が文脈を提供し、Prompts が一貫性を保証します。これらが組み合わさることで、チームの基準を維持しながら開発者の生産性を高める、インテリジェントな自動化システムが生まれます。

モジュール式のアーキテクチャにより、各コンポーネントを独立して理解・テスト・拡張出来ます。また、コンポーネント同士の連携を通して、実際の本番環境で MCP サーバーを構築する際に役立つパターンを学べます。
