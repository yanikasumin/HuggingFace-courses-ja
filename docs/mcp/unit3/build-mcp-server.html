Module 1：MCP サーバーの構築

CodeCraft Studios の PR の混乱

CodeCraft Studios での最初の週、あなたは開発者なら誰もが顔をしかめる光景を目撃します。チームのプルリクエストはこんな状態です。

  • "stuff"
  • "more changes"
  • "fix"
  • "update things"

その結果、レビュアーは何が何故変更されたのかを理解出来ず、コードレビューの未処理案件が増え続けています。バックエンドチームの Sarah は「various improvements」が具体的に何を意味するのか調べるのに30分を費やし、フロントエンドの Mike は「small fix」の内容を理解する為に47ファイルも調べなければなりませんでした。

チームは、より良い PR の説明が必要だと分かっています。しかし、全員が機能のリリースで忙しく、詳細な説明を書く暇がありません。速度を落とさずに助けてくれるソリューションが必要です。

あなたのミッション：コード変更を分析し、役立つ説明を自動で提案するインテリジェントな PR Agent を構築することです。

スクリーンキャスト：実際の PR の問題

内容：CodeCraft Studios の実際の PR で、タイトルは「various improvements」、説明はただ「Fixed some stuff and made updates」とだけ書かれています。よくある光景ですよね？

混乱ぶり：チームメイトが苦労する様子をご覧ください。 - Sarah（3時間前）：「何が修正されたの？User モデルへの変更は見えるけど、バグ対応なのか機能追加なのか分からない」 - Jamie（3時間前）：「4つのサービスにまたがって8ファイルも有る…これらの変更は関連しているの？レビューではどこに注目すべき？」

問題点：スクリーンキャストには実際の diff が映っています。複数のサービスに散らばった8ファイル、文脈はゼロ。レビュアーは自分で経緯を組み立てなければならず、貴重な時間を浪費し、重大な問題を見逃す可能性もあります。

何故重要か：これはまさに、これから作る MCP サーバーが解決する問題です。このモジュールを終える頃には、内容が分かり難い PR に対して、誰もが理解し易く、次の作業にも役立つ説明を作成出来るようになります。

構築するもの

この最初のモジュールでは、CodeCraft Studios の自動化システムの基盤、つまりチームのプルリクエストの書き方を変える MCP サーバーを作成します。このモジュールでは、Module 2 と Module 3 の土台となる MCP の中核概念に焦点を当てます。

スクリーンキャスト：PR Agent の活躍！

ソリューションの実演：MCP サーバーを使って、分かり難い PR を明確で理解し易いものに改善する様子をご覧ください。 1. analyze_file_changes：全ての変更を取得する（8ファイル、453行！） 2. get_pr_templates：選択肢となる7つのテンプレートを Claude に提示する 3. suggest_template：Claude が「Feature」を選ぶ（賢い選択！）

見どころ：Claude は単にテンプレートを選ぶだけではありません。 - 実際に何が変更されたかの明確な要約を書く - セキュリティ問題に気づく（なんと、ハッシュ化されていないパスワード！） - フォローアップ作業の見易い ToDo リストを作る - 何を先に修正すべきかの優先順位まで付ける

驚きの瞬間：わずか数秒で、MCP サーバーの支援を受けた Claude が、同じブランチの変更内容を明確に説明する PR を作成します。レビュアーが混乱したり、「これは何をする変更？」と質問したりする必要もなくなります。

これが構築するものです：PR の憂鬱を PR の喜びに変えるツールです。さあ、始めましょう！

学ぶこと

この基礎モジュールでは、以下をマスターします。 - FastMCP を使った基本的な MCP サーバーの作り方：Module 2 と Module 3 の土台 - データ取得と分析の為の MCP Tools の実装：Unit 3 全体を通して使う中核プリミティブ
- 生データに基づいて Claude に賢い判断をさせること：全ての MCP 開発における重要な原則 - MCP サーバーのテストと検証：信頼出来るツールを作る為の必須スキル

概要

PR Agent は、MCP 開発の重要な原則を使って CodeCraft Studios の問題を解決します。良い PR とは何かという硬直したルールをハードコードする代わりに、Claude に生の git データを提供し、適切な説明を賢く提案させます。

このアプローチが有効な理由： - 柔軟な分析：単純なルールでは見逃す文脈を Claude が理解出来る - 自然言語：機械的ではなく、人が書いたような自然な提案が出来る - 適応性：あらゆるコードベースやコーディングスタイルで機能する

自動化システム全体のパターンを確立する、3つの必須ツールを実装します。

  1. analyze_file_changes：git の diff 情報と変更ファイルを取得する（データ収集）
  2. get_pr_templates：利用可能な PR テンプレートを一覧表示する（リソース管理）
  3. suggest_template：Claude が最適なテンプレートを推奨出来るようにする（インテリジェントな意思決定）

はじめに

前提条件

  • Python 3.10 以上
  • Git がインストールされていることと、テスト用の Git リポジトリが有ること
  • uv パッケージマネージャ（インストールガイド）

スターターコード

スターターコードのリポジトリをクローンします。

git clone https://github.com/huggingface/mcp-course.git

スターターコードのディレクトリに移動します。

cd mcp-course/projects/unit3/build-mcp-server/starter

依存関係をインストールします。

💡 ヒント

このプロジェクト用に仮想環境を作成するとよいでしょう。

uv venv .venv
source .venv/bin/activate # Windows では .venv\Scripts\activate を使う

uv sync --all-extras

あなたのタスク

初めての MCP 開発のハンズオンです。server.py を開き、TODO コメントに従って3つのツールを実装してください。スターターコードには基本構造が用意されています。行うことは次の通りです。

  1. analyze_file_changes を実装する：git コマンドを実行し、diff データを返す - ⚠️ 重要：おそらくトークン上限エラーに遭遇します（レスポンスあたり最大25,000トークン） - これは実際の開発でも遭遇する制約であり、適切な出力管理を学ぶ機会になります - 解決策は下の「大きな出力の扱い方」のセクションを見てください - ⚠️ 注意：git コマンドはデフォルトでは MCP サーバーのディレクトリで実行されます。詳しくは下の「作業ディレクトリに関する注意点」を見てください
  2. get_pr_templates を実装する：PR テンプレートを管理し、返す
  3. suggest_template を実装する：変更タイプをテンプレートに対応づける

全てを完璧にしようとしなくて大丈夫です。これらのスキルはユニットを進める中で磨かれていきます。

設計哲学

ファイル拡張子や硬直したパターンに基づいて変更を分類する従来のシステムとは異なり、実装では次のようにします。

  • Claude に生の git データ（diff、ファイル一覧、統計）を提供する
  • 実際のコード変更の分析は Claude に任せる
  • Claude に賢いテンプレート提案をさせる
  • ロジックはシンプルに保ち、複雑な処理は Claude に任せる

💡 ヒント

MCP の哲学：ツールに複雑なロジックを組み込む代わりに、Claude に豊富なデータを提供し、その知能に判断を委ねましょう。これにより、コードは従来のルールベースシステムよりもシンプルで柔軟になります。

⚠️ 注意

よくある最初のエラー：「MCP tool response exceeds maximum allowed tokens (25000)」というエラーが出ても、想定内です！大きなリポジトリでは巨大な diff が生成されることがあります。これは貴重な学びの瞬間です。解決策は「大きな出力の扱い方」のセクションを見てください。

エラーハンドリング

発生する可能性の有るエラーには、常に適切に対処しましょう。

try:
    result = subprocess.run(["git", "diff"], capture_output=True, text=True)
    return json.dumps({"output": result.stdout})
except Exception as e:
    return json.dumps({"error": str(e)})

⚠️ 注意

エラーハンドリング：エラー時でも、ツールからは常に有効な JSON を返してください。Claude は、何が問題だったかを理解し、ユーザーに役立つ回答をする為に構造化データを必要とします。

大きな出力の扱い方（重要な学びの瞬間！）

⚠️ 注意

実世界の制約：MCP ツールには、レスポンスあたり25,000トークンの上限があります。大きな git diff は、この上限を簡単に10倍以上超えてしまいます！これは本番の MCP 開発における重要な教訓です。

analyze_file_changes を実装すると、おそらく次のエラーに遭遇します。

Error: MCP tool response (262521 tokens) exceeds maximum allowed tokens (25000)

何故こうなるのか： - 1つのファイルの変更が数千行になることが有る - エンタープライズのリポジトリでは大規模なリファクタリングが頻繁に有る - git diff はデフォルトで完全な文脈を含む - JSON エンコーディングでオーバーヘッドが増える

ここから重要な原則が学べます：ツールは常に出力上限を意識して設計すること。解決策は次の通りです。

@mcp.tool()
async def analyze_file_changes(base_branch: str = "main", 
                              include_diff: bool = True,
                              max_diff_lines: int = 500) -> str:
    """Analyze file changes with smart output limiting.

    Args:
        base_branch: Branch to compare against
        include_diff: Whether to include the actual diff
        max_diff_lines: Maximum diff lines to include (default 500)
    """
    try:
        # diff を取得
        result = subprocess.run(
            ["git", "diff", f"{base_branch}...HEAD"],
            capture_output=True, 
            text=True
        )

        diff_output = result.stdout
        diff_lines = diff_output.split('\n')

        # 必要に応じて賢く切り詰める
        if len(diff_lines) > max_diff_lines:
            truncated_diff = '\n'.join(diff_lines[:max_diff_lines])
            truncated_diff += f"\n\n... Output truncated. Showing {max_diff_lines} of {len(diff_lines)} lines ..."
            diff_output = truncated_diff

        # 要約統計を取得
        stats_result = subprocess.run(
            ["git", "diff", "--stat", f"{base_branch}...HEAD"],
            capture_output=True,
            text=True
        )

        return json.dumps({
            "stats": stats_result.stdout,
            "total_lines": len(diff_lines),
            "diff": diff_output if include_diff else "Use include_diff=true to see diff",
            "files_changed": self._get_changed_files(base_branch)
        })

    except Exception as e:
        return json.dumps({"error": str(e)})

大きな出力のベストプラクティス： 1. ページネーションを実装する：大きな結果をページに分割する 2. フィルタリングオプションを追加する：ユーザーが特定のファイルやディレクトリを要求出来るようにする 3. まず要約を提供する：完全な内容の前に統計を返す 4. 情報を段階的に表示する：まず概要を示し、必要に応じて詳しい情報を確認出来るようにする 5. 妥当なデフォルトを設定する：殆どのケースで機能する合理的な上限をデフォルトにする

作業ディレクトリに関する注意点

デフォルトでは、MCP サーバーは Claude の現在の作業ディレクトリではなく、インストールディレクトリでコマンドを実行します。つまり、git コマンドが間違ったリポジトリを分析してしまう可能性が有るのです。

この問題を解決する為、MCP は roots を提供しています。これは、クライアントがサーバーに関連ディレクトリを知らせる仕組みです。Claude Code は作業ディレクトリを自動的に root として提供します。

ツールからアクセスする方法は次の通りです。

@mcp.tool()
async def analyze_file_changes(...):
    # roots から Claude の作業ディレクトリを取得
    context = mcp.get_context()
    roots_result = await context.session.list_roots()

    # FileUrl オブジェクトからパスを取り出す
    working_dir = roots_result.roots[0].uri.path

    # すべての git コマンドでこれを使う
    result = subprocess.run(
        ["git", "diff", "--name-status"],
        capture_output=True,
        text=True,
        cwd=working_dir  # Claude のディレクトリで実行！
    )

これにより、ツールは MCP サーバーのインストール場所ではなく、Claude が実際に作業しているリポジトリを対象に動作します。

トラブルシューティング

  • インポートエラー：uv sync を実行したか確認する
  • Git エラー：git リポジトリ内にいるか確認する
  • 出力が無い：MCP サーバーは stdio で通信する為、Claude Desktop から接続して動作を確認する
  • JSON エラー：全てのツールは有効な JSON 文字列を返さなければならない
  • トークン上限超過：大きな diff では想定内です！上記のように出力制限を実装する
  • 「Response too large」エラー：max_diff_lines パラメータを追加するか、include_diff=false を設定する
  • Git コマンドが間違ったディレクトリで実行される：MCP サーバーはデフォルトでインストールディレクトリで実行され、Claude の作業ディレクトリでは実行されません。修正するには、MCP の roots を使って Claude の現在のディレクトリにアクセスします。 ```python # roots から Claude の作業ディレクトリを取得 context = mcp.get_context() roots_result = await context.session.list_roots() working_dir = roots_result.roots[0].uri.path # FileUrl オブジェクトには .path プロパティがある

# subprocess の呼び出しで使う subprocess.run(["git", "diff"], cwd=working_dir) ``` Claude Code は作業ディレクトリを自動的に root として提供する為、MCP サーバーは正しい場所で動作出来ます。
