よい Issue の書き方

Hugging Face のライブラリで何かおかしいと感じたら、直せるようぜひ私たちに知らせてください（これは他のオープンソースライブラリでも同じです）。バグが自分のコードにあるのかライブラリにあるのか完全には確信が持てない場合、まず確認すべき場所はフォーラムです。コミュニティが切り分けを手伝ってくれますし、Hugging Face のチームもそこの議論を注意深く見守っています。

バグがあると確信が持てたら、最初のステップは最小再現例を作ることです。

最小再現例を作る

バグを生むコードを切り分けることはとても重要です。Hugging Face のチームのだれも魔法使いではないので（今のところは）、見えないものは直せません。最小再現例は、その名前のとおり再現可能でなければなりません。つまり、手元の外部ファイルやデータに依存しないものにします。使っているデータを、実物に似ていて同じエラーを出すダミーの値に置き換えてみてください。

💡 ヒント

🚨 🤗 Transformers リポジトリの Issue の多くは、再現に使うデータにアクセスできないために未解決のままになっています。

自己完結したものができたら、さらに行数を減らして、いわゆる_最小再現例_に仕上げてみましょう。報告する側には多少の手間がかかりますが、きれいで短い再現コードを用意すれば、助けと修正がほぼ確実に得られます。

余裕があれば、バグが起きている場所のソースコードを自分で調べてみてください。自分の問題の解決策が見つかるかもしれませんし（その場合は修正のプルリクエストを提案することさえできます）、そうでなくても、報告を読むメンテナが原因を理解する助けになります。

Issue テンプレートを埋める

Issue を起票すると、埋めるべきテンプレートがあることに気づくはずです。ここでは 🤗 Transformers の Issue 用のテンプレートに沿って進めますが、他のリポジトリで Issue を報告する場合も、求められる情報の種類は同じです。テンプレートを空欄のままにしないでください。時間をかけて埋めることで、回答が得られて問題が解決する可能性が最大になります。

一般に、Issue を起票するときは常に礼儀正しくしてください。これはオープンソースプロジェクトであり、無料のソフトウェアを使っているのであって、だれにもあなたを助ける義務はありません。正当だと感じる批判を Issue に含めることもできますが、メンテナに悪い印象を与え、対応を後回しにされる可能性があります。プロジェクトの行動規範を必ず読んでください。

環境情報を含める

🤗 Transformers には、あなたの環境について必要な情報をすべて取得するユーティリティが用意されています。ターミナルで次のように入力するだけです。

transformers-cli env

すると、次のような出力が得られるはずです。

- Python version: 3.7.9
- PyTorch version (GPU?): 1.8.1+cu111 (True)

transformers-cli env コマンドの先頭に ! を付ければノートブックのセルから実行することもできます。その結果をコピーして、Issue の冒頭に貼り付けてください。

人をタグ付けする

@ の後に GitHub のハンドルを入力して人をタグ付けすると、その人に通知が届くので、あなたの Issue に気づいて早めに返信してくれるかもしれません。ただし控えめに使ってください。タグ付けされた人が、自分の直接関係しないことで通知されるのを好まないこともあります。バグに関係するソースファイルを見たのであれば、問題の原因だと思う行を最後に変更した人をタグ付けするとよいでしょう（この情報は、その行を GitHub 上で選択して「View git blame」をクリックすると分かります）。

そうでない場合は、テンプレートがタグ付けする人の候補を提示してくれます。一般に、タグ付けは3人までにしてください。

その後に最小再現例を貼り付け、3つのバッククォートだけの新しい行を入力します。これでコードが適切に整形されます。

再現例が作れなかった場合は、エラーが発生するまでに行った操作を、順を追って分かりやすく説明してください。エラーが出た Google Colab ノートブックへのリンクがあれば含めてください。共有する情報が多いほど、メンテナは返信しやすくなります。

いずれの場合も、表示されているエラーメッセージは全部コピーして貼り付けてください。Colab で作業している場合は、スタックトレースの一部のフレームが自動で折りたたまれていることがあるので、コピーする前に展開しておきましょう。コードのサンプルと同じように、エラーメッセージも3つのバッククォートの行同士の間に置いて、適切に整形してください。

期待する動作を説明する

何が得られると期待していたのかを数行で説明し、メンテナが問題を完全に把握できるようにします。この部分はたいてい自明なので1文で済むはずですが、場合によってはたくさん書くこともあるでしょう。

そのあとは？

Issue を起票したら、すべて問題なく表示されているか手早く確認してください。間違えた場合は Issue を編集できますし、問題が当初の想定と違うと気づいたらタイトルを変更することもできます。

回答がないからといって、メンテナに何度も催促の通知を送っても効果はありません。数日たってもだれも助けてくれないなら、おそらくあなたの問題をだれも理解できなかったのでしょう。再現例に戻ることをためらわないでください。もっと短く、要点を絞れませんか？1週間たっても回答がなければ、問題についての情報を追記して Issue を編集したうえで、助けを求めるメッセージを丁寧に残すこともできます。
