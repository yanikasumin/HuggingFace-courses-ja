フォーラムで助けを求める

Hugging Face フォーラムは、オープンソースチームや Hugging Face コミュニティ全体から助けを得るのに最適な場所です。メインページは、日によって多少の違いはありますが、次のような見た目をしています。

左側には、さまざまなトピックが分類されているカテゴリがすべて表示され、右側には最新のトピックが表示されます。トピックとは、タイトル、カテゴリ、説明を含む投稿のことです。Chapter 5 で自分のデータセットを作ったときに見た GitHub の Issue の形式とよく似ています。名前のとおり、Beginners カテゴリは主に、Hugging Face のライブラリやエコシステムを使い始めたばかりの人を対象としています。コードのデバッグであれ、何かのやり方を尋ねるのであれ、どのライブラリについての質問でも歓迎されます（ただし、質問が特定のライブラリに関するものであれば、フォーラムの対応するライブラリカテゴリへ行くのがよいでしょう）。

同様に、Intermediate カテゴリと Research カテゴリは、ライブラリについての高度な質問や、議論したい面白い新しい NLP 研究など、より進んだ質問のためのものです。

そしてもちろん、Hugging Face コースについてなら、どんな質問でも投稿できる Course カテゴリも紹介しておきましょう。

カテゴリを選んだら、最初のトピックを書く準備は完了です。書き方のガイドラインがフォーラムにあります。このセクションでは、よいトピックを構成するいくつかの特徴を見ていきます。

よいフォーラム投稿の書き方

題材として、カスタムの検索エンジンを作るために、Wikipedia の記事から埋め込みを生成しようとしている場面を考えましょう。いつものように、トークナイザとモデルを次のように読み込みます。

from transformers import AutoTokenizer, AutoModel

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)
model = AutoModel.from_pretrained(model_checkpoint)

エラーは 🤗 Transformers だけに関係しているようなので、カテゴリにはこれを選びます。問題を説明する最初の試みは、次のようなものになるかもしれません。

このトピックには助けが必要なエラーメッセージが含まれていますが、書き方にはいくつか問題があります。

  1. タイトルがあまり説明的ではないため、フォーラムを眺めている人は本文も読まなければトピックの内容が分かりません。
  2. 本文には、エラーが_どこから_来ているのか、_どうすれば_再現できるのかの情報が不足しています。
  3. 何人かに直接タグ付けしていて、やや要求の強い口調になっています。

このようなトピックは、速い回答が得られそうにありません（そもそも回答が得られるかどうかも怪しいものです）。では、どうすれば改善できるか見ていきましょう。最初の問題である、よいタイトル選びから始めます。

内容の分かるタイトルを付ける

コードのバグについて助けを求めるときは、タイトルに十分な情報を含めて、他の人が「自分の答えられる質問かどうか」をすばやく判断できるようにするのが、経験則としてよい方法です。今回の例では、発生している例外の名前が分かっており、モデルを呼び出す model(**inputs) のフォワードパスで発生しているらしいという手がかりもあります。これを伝えるタイトルとしては、たとえば次のようなものが考えられます。

AutoModel のフォワードパスで発生する IndexError の原因は？

このタイトルは、バグがどこから来ていると思うかを読み手に伝え、IndexError に遭遇したことがある人なら、デバッグ方法を知っている可能性が高いでしょう。もちろんタイトルは自由に付けられますし、次のようなバリエーションでも問題ありません。

なぜモデルの実行時に IndexError が発生するのか？

説明的なタイトルが決まったので、次は本文の改善を見ていきましょう。

コードスニペットを整形する

ソースコードを読むのは IDE の中でも十分に大変ですが、プレーンテキストとしてコピー＆ペーストされたものを読むのはさらに大変です。幸い、Hugging Face フォーラムは Markdown をサポートしているので、コードを掲載するときは、必ず3つのバッククォートで囲んでコードブロックとして整形してください。エラーメッセージをこの方法できれいに整形してみましょう。ついでに、本文を最初のバージョンよりも少し丁寧な文面にします。

スクリーンショットで分かるように、コードブロックをバッククォートで囲むと、生のテキストが色付けまでされた整形済みコードに変換されます。単一のバッククォートを使えば、distilbert-base-uncased のようにインラインの変数を整形することもできます。このトピックはずいぶんよくなりました。運がよければ、エラーの内容を推測できる人がコミュニティにいるかもしれません。ただ、運に頼るのではなく、トレースバックを省略せず、詳細をすべて掲載して、相手の作業を楽にしましょう。

トレースバックを全部載せる

トレースバックの最後の行だけで自分のコードをデバッグできることが多いため、スペースを「節約」しようとしてトピックにその行だけを載せたくなるものです。善意からではありますが、トレースバックの上部にある情報も非常に役立つため、実際には他の人が問題をデバッグするのを_難しく_してしまいます。ですから、トレースバックは_全文_をコピー＆ペーストし、読みやすく整形して掲載するのがよい方法です。トレースバックはかなり長くなることがあるので、ソースコードを説明した後に載せる人もいます。ここでもそうしてみましょう。これでフォーラムトピックは次のようになります。

再現可能な例を用意する

他人のコードをデバッグしたことがある人なら、たいてい最初に、報告された問題を再現しようとして、トレースバックをたどってエラーの箇所を特定するところから始めたはずです。フォーラムで支援を受ける（あるいは提供する）場合も同じことなので、エラーを再現する小さな例を用意できると本当に助かります。このように再現例を作る過程で、半数ほどのケースでは問題の原因を自分で発見できます。いずれにせよ、この例で欠けているのは、モデルに渡した_入力_を示すことです。それを示すと、次のような完成した例になります。
