# MCP のアーキテクチャコンポーネント

前節では、MCP の主要な概念と用語について説明しました。この節では、MCP エコシステムを構成するアーキテクチャコンポーネントをさらに深く掘り下げます。

## ホスト、クライアント、サーバー

Model Context Protocol（MCP）は、AI モデルと外部システムの間の構造化された通信を可能にするクライアント・サーバーアーキテクチャの上に構築されています。 

![MCP のアーキテクチャ](https://huggingface.co/datasets/mcp-course/images/resolve/main/unit1/4.png)

MCP のアーキテクチャは3つの主要なコンポーネントで構成されており、それぞれに明確に定義された役割と責務があります。ホスト、クライアント、サーバーです。前節でも触れましたが、ここでは各コンポーネントとその責務を詳しく見ていきます。

### ホスト（Host）

**ホスト**は、エンドユーザーが直接操作するユーザー向けの AI アプリケーションです。 

例として次のものがあります。
- OpenAI ChatGPT や Anthropic の Claude Desktop のような AI チャットアプリ
- Cursor のように AI 機能を備えた IDE や、Continue.dev のようなツールとの連携
- LangChain や smolagents のようなライブラリで構築されたカスタム AI エージェントやアプリケーション

ホストの責務は次のとおりです。
- ユーザーとのやり取りと権限の管理
- MCP クライアントを介した MCP サーバーへの接続の開始
- ユーザーのリクエスト、LLM の処理、外部ツールの間の全体的なフローの統括
- 結果をわかりやすい形式でユーザーに表示すること

多くの場合、ユーザーは自分のニーズや好みに合わせてホストアプリケーションを選択します。たとえば開発者は強力なコード編集機能を求めて Cursor を選ぶかもしれませんし、ドメイン専門家は smolagents で構築されたカスタムアプリケーションを使うかもしれません。

### クライアント（Client）

**クライアント**は、ホストアプリケーション内のコンポーネントで、特定の MCP サーバーとの通信を管理します。主な特徴は次のとおりです。

- 各クライアントは単一のサーバーと 1:1 の接続を維持します
- MCP 通信のプロトコルレベルの詳細を処理します
- ホストのロジックと外部サーバーの間の仲介役として動作します

### サーバー（Server）

**サーバー**は、MCP プロトコルを通じて AI モデルに機能を公開する外部のプログラムまたはサービスです。サーバーは次の特徴を持ちます。

- 特定の外部ツール、データソース、サービスへのアクセスを提供します
- 既存の機能を包み込む軽量なプログラムとして動作します
- ローカル（ホストと同じマシン上）でもリモート（ネットワーク越し）でも実行できます
- クライアントが発見して利用できる標準化された形式で機能を公開します

## 通信フロー

典型的な MCP ワークフローでこれらのコンポーネントがどのように連携するかを見てみましょう。

> [!TIP]
> 次節では、これらのコンポーネントが連携する仕組みを支える通信プロトコルについて、具体例を交えながら詳しく説明します。

1. **ユーザーインタラクション**：ユーザーが**ホスト**アプリケーションを操作し、意図やクエリを伝えます。

2. **ホストの処理**：**ホスト**がユーザーの入力を処理します。場合によっては LLM を使ってリクエストを理解し、どの外部機能が必要になりそうかを判断します。

3. **クライアントの接続**：ホストは、内部のクライアントに適切なサーバーへの接続を指示します。

4. **機能の発見**：**クライアント**が**サーバー**に問い合わせ、そのサーバーが提供する機能（ツール、リソース、プロンプト）を発見します。

5. **機能の呼び出し**：ユーザーのニーズや LLM の判断に基づき、ホストが**クライアント**に**サーバー**の特定の機能を呼び出すよう指示します。

6. **サーバーの実行**：**サーバー**がリクエストされた機能を実行し、結果を**クライアント**に返します。

7. **結果の統合**：**クライアント**がこれらの結果を**ホスト**に中継し、ホストはそれを LLM のコンテキストに組み込むか、ユーザーに直接提示します。

このアーキテクチャの重要な利点はモジュール性です。1つの**ホスト**が、異なる**クライアント**を介して複数の**サーバー**に同時に接続できます。既存の**ホスト**を変更することなく、新しい**サーバー**をエコシステムに追加できます。機能は異なる**サーバー**間で簡単に組み合わせられます。

> [!TIP]
> 前節で説明したとおり、このモジュール性により、従来の M×N 統合問題（M 個の AI アプリケーションが N 個のツールやサービスに接続する問題）は、より扱いやすい M+N 問題へと変わります。各ホストとサーバーは MCP 標準を一度だけ実装すればよいからです。

このアーキテクチャは一見シンプルに見えますが、その力は通信プロトコルの標準化と、コンポーネント間の責務の明確な分離にあります。この設計により、AI モデルが絶えず増え続ける外部ツールやデータソースへとシームレスに接続できる、まとまりのあるエコシステムが実現します。

## まとめ

これらのやり取りは、MCP の設計と進化を支える重要な原則に基づいています。MCP は、AI システムを接続するための共通プロトコルを提供することで、**標準化**を重視しています。同時に、基本的なプロトコルをわかりやすく保ちながら、高度な機能にも対応することで**シンプルさ**を維持しています。機密性の高い操作にはユーザーの明示的な承認を必要とし、**安全性**を優先しています。また、発見可能性（discoverability）によって、利用できる機能を動的に見つけられます。さらに、**拡張性**を考慮し、バージョン管理と対応機能のすり合わせによってプロトコルを進化させられるようにしています。これにより、異なる実装や環境間での**相互運用性**も確保しています。
