学習パイプラインをデバッグする

Chapter 7 のアドバイスにきちんと従って、あるタスク向けにモデルを学習・ファインチューニングするスクリプトを、見事に書き上げました。ところが、model.fit() コマンドを実行すると、恐ろしいことが起こります。エラーが出るのです 😱。あるいはもっと悪いことに、すべて問題ないように見え、学習はエラーなく進むのに、できあがったモデルがひどい出来になります。このセクションでは、このような問題をデバッグするために何ができるかを示します。

学習パイプラインをデバッグする

model.fit() でエラーに遭遇したときの問題は、その原因が複数ありうることです。学習処理には、これまでに用意したデータセット、モデル、損失関数、オプティマイザなどが関わるからです。問題は、データセットの何かが間違っていることかもしれませんし、データセットの要素をバッチにまとめようとしたときの問題かもしれません。あるいは、モデルコードの何かが間違っているか、損失関数やオプティマイザの問題かもしれません。さらに、学習がすべて順調に進んでも、指標に問題があれば評価の段階で何かがうまくいかないこともあります。

model.fit() で発生したエラーをデバッグする最良の方法は、このパイプライン全体を手作業でたどり、どこで問題が起きたのかを突き止めることです。そうすれば、エラーはたいてい非常に簡単に解決できます。

これを示すために、MNLI データセットで DistilBERT モデルをファインチューニング（しようと）する次のスクリプトを使います。

from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    TFAutoModelForSequenceClassification,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)

train_dataset = tokenized_datasets["train"].to_tf_dataset(
    columns=["input_ids", "labels"], batch_size=16, shuffle=True
)

validation_dataset = tokenized_datasets["validation_matched"].to_tf_dataset(
    columns=["input_ids", "labels"], batch_size=16, shuffle=True
)

model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)

model.compile(loss="sparse_categorical_crossentropy", optimizer="adam")

model.fit(train_dataset)

これを実行すると、データセットの変換時に VisibleDeprecationWarning がいくつか出るかもしれません。これは私たちが抱えている既知の UX 上の問題なので、無視してください。もし、たとえば2021年11月を過ぎてもまだ起きているようなら、@carrigmat 宛てに怒りのツイートを送って、直してもらってください。

ただし、より深刻な問題として、正真正銘のエラーが出ます。しかも、本当に恐ろしいほど長いエラーです。

```python out ValueError: No gradients provided for any variable: ['tf_distil_bert_for_sequence_classification/distilbert/embeddings/word_embeddings/weight:0', '...']

これはどういう意味でしょう。データで学習しようとしたのに、勾配が得られなかったというのです。かなり当惑します。このようなものをどうやってデバッグし始めればよいのでしょう。得られたエラーから問題の場所がすぐに示唆されない場合、最良の解決策は多くの場合、物事を順番にたどり、各段階ですべてが正しく見えるか確認することです。そしてもちろん、始める場所はいつも……

### データを確認する

言うまでもありませんが、データが壊れていれば、Keras が代わりに直してはくれません。ですから、まず最初に、学習セットの中身を見る必要があります。

`raw_datasets` や `tokenized_datasets` の中を確認したくなるかもしれませんが、モデルに入力される直前のデータを直接確認することを強くおすすめします。つまり、`to_tf_dataset()` 関数で作成した `tf.data.Dataset` からの出力を読むということです。では、どうすればよいでしょう。`tf.data.Dataset` オブジェクトはバッチ全体を一度に渡してくれるもので、インデックス付けはサポートしていないので、`train_dataset[0]` のようにインデックスを指定して取得することはできません。ただし、次のようにループを使えば、最初のバッチを取り出せます。

```py
for batch in train_dataset:
    break

break は1回の反復でループを終了するので、これで train_dataset から出てくる最初のバッチを取得し、batch として保存できます。では、中身を見てみましょう。

```python out {'attention_mask': , 'label': , 'input_ids': }

これは正しく見えますね。モデルに `labels`、`attention_mask`、`input_ids` を渡しているので、出力を計算して損失を算出するために必要なものはすべてそろっているはずです。では、なぜ勾配がないのでしょう。よく見てください。入力として単一の辞書を渡していますが、学習バッチは通常、入力テンソルまたは辞書と、ラベルテンソルです。私たちのラベルは、入力辞書の単なる1つのキーになっています。

これは問題でしょうか。実は、常にそうとは限りません。しかし、TensorFlow で Transformer モデルを学習するときに遭遇する最も一般的な問題の1つです。私たちのモデルはすべて内部で損失を計算できますが、そのためにはラベルを入力辞書の中に渡す必要があります。これは、`compile()` に損失の値を指定しないときに使われる損失です。一方、Keras は通常、ラベルが入力辞書とは別に渡されることを期待していて、そうしないと損失の計算はたいてい失敗します。

問題ははっきりしてきました。私たちは `loss` 引数を渡しました。つまり、Keras に損失を計算するよう求めていますが、ラベルを Keras が期待する独立した教師データとして渡さず、モデルの入力辞書に含めてしまったのです。どちらかを選ぶ必要があります。モデルの内部損失を使い、ラベルを今の場所に置いておくか、Keras の損失を使い続ける代わりに、ラベルを Keras が期待する場所へ移すかです。簡単にするために、最初のアプローチを取りましょう。`compile()` の呼び出しを次のように変更します。

```py
model.compile(optimizer="adam")

これでモデルの内部損失を使うようになり、この問題は解決するはずです。

### モデルを確認する

`model.fit()` は非常に便利ですが、多くのことを代わりにやってくれるため、問題が正確にどこで起きたのかを見つけるのが難しくなります。モデルをデバッグしているとき、本当に役立つ戦略の1つは、モデルにバッチを1つだけ渡し、その1バッチ分の出力を詳しく見ることです。もう1つの本当に役立つコツは、モデルがエラーを出す場合、`run_eagerly=True` でモデルを `compile()` することです。これによりはるかに遅くなりますが、エラーメッセージがずっと分かりやすくなります。モデルのコードの正確にどこで問題が起きたかを示してくれるからです。

ただ、今のところ `run_eagerly` はまだ必要ありません。先ほど取得した `batch` をモデルに通して、出力がどうなるか見てみましょう。

```py
model(batch)

```python out TFSequenceClassifierOutput(loss=, logits=, hidden_states=None, attentions=None)

うーん、これは厄介です。すべてが `nan` です。しかし、奇妙ではありませんか？ロジットがすべて `nan` になるなんて、`nan` は「数ではない（not a number）」を意味します。`nan` の値は、ゼロ除算のような禁止された操作を実行したときによく発生します。しかし、機械学習における `nan` について知っておくべき非常に重要なことの1つは、この値が_伝播_しがちだということです。数に `nan` を掛けると、出力も `nan` になります。そして、出力、損失、勾配のどこかに `nan` が入ると、それはモデル全体に急速に広がります。その `nan` の値がネットワークを逆方向に伝播すると `nan` の勾配が得られ、それらの勾配で重みの更新を計算すると `nan` の重みが得られ、それらの重みはさらに多くの `nan` の出力を計算します。やがてネットワーク全体が `nan` の大きな塊になってしまいます。そうなると、問題がどこから始まったのかを見るのはかなり難しくなります。`nan` が最初に紛れ込んだ場所をどうやって切り分けられるでしょう。

答えは、モデルを_再初期化_してみることです。学習を開始すると、どこかで `nan` が発生し、それがモデル全体にすばやく伝播しました。ですから、チェックポイントからモデルを読み込み、重みの更新を一切行わずに、どこで `nan` の値が得られるか見てみましょう。

```py
model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)

ハイパーパラメータを確認する

上のコードを見返しても、ハイパーパラメータは batch_size を除いてまったく見えないかもしれませんし、それが原因とは考えにくいでしょう。しかし、だまされてはいけません。ハイパーパラメータは常にあるもので、見えない場合は、その値が何に設定されているかを知らないというだけです。特に、Keras についての重要なことを覚えておいてください。損失、オプティマイザ、活性化関数を文字列で設定すると、それらの_すべての引数がデフォルト値に設定_されます。つまり、この方法で文字列を使うのは非常に便利ではありますが、重要なことが隠れてしまうことが容易にあるため、非常に注意が必要です（上の任意のチャレンジに取り組んでいる人は、この事実をよく覚えておいてください）。

この場合、引数を文字列で設定しているのはどこでしょう。当初は損失を文字列で設定していましたが、今はもうしていません。しかし、オプティマイザは文字列で設定しています。これが何かを隠している可能性はあるでしょうか。その引数を見てみましょう。

目立つものがありますか？そのとおり、学習率です。文字列 'adam' を使うだけでは、デフォルトの学習率である 0.001、つまり 1e-3 が得られます。これは Transformer モデルには高すぎます。一般に、モデルには 1e-5 から 1e-4 の間の学習率を試すことをおすすめします。これは、実際に使っている値より10倍から100倍小さい値です。これは大きな問題のように思えるので、減らしてみましょう。そのためには、実際の optimizer オブジェクトをインポートする必要があります。ついでに、高い学習率での学習で重みが損傷している場合に備え、チェックポイントからモデルを再初期化しましょう。

from tensorflow.keras.optimizers import Adam

model = TFAutoModelForSequenceClassification.from_pretrained(model_checkpoint)
model.compile(optimizer=Adam(5e-5))

### メモリ不足エラーに対処する

メモリが不足していることの分かりやすい兆候は、"OOM when allocating tensor" のようなエラーです。OOM は "out of memory" の略です。これは、大規模な言語モデルを扱うときによくある危険です。これに遭遇したら、バッチサイズを半分にして再試行するのがよい戦略です。ただし、一部のモデルは_非常に_大きいことに留意してください。たとえば、フルサイズの GPT-2 は15億パラメータを持ち、これはモデルを格納するだけで6 GB のメモリが必要で、勾配用にさらに6 GB が必要だということです。フルサイズの GPT-2 モデルの学習には、使用するバッチサイズにかかわらず、通常20 GB を超える VRAM が必要になりますが、それを持つ GPU はほとんどありません。`distilbert-base-cased` のような、より軽量なモデルは、実行がはるかに簡単で、学習もはるかに速いです。

### Hungry Hungry TensorFlow 🦛

TensorFlow 特有の挙動として知っておきたいのは、モデルを読み込んだり学習を開始したりすると、GPU メモリの_すべて_を確保し、その後、必要に応じてそのメモリを分割して使用するという点です。これは、PyTorch のような他のフレームワークの動作とは異なります。一方、PyTorch は TensorFlow のように GPU メモリをあらかじめ一括確保せず、CUDA を通じて必要な分だけ確保します。TensorFlow のアプローチの利点の1つは、メモリが不足したときに有益なエラーを出すことが多く、CUDA カーネル全体をクラッシュさせることなくその状態から回復できることです。しかし、重要な欠点もあります。2つの TensorFlow プロセスを同時に実行すると、**大変なことになります**。

Colab で実行している場合は、このことを心配する必要はありませんが、ローカルで実行している場合は間違いなく注意すべきことです。特に、ノートブックのタブを閉じても、そのノートブックがシャットダウンするとは限らないことに注意してください。ディレクトリ一覧で、実行中のノートブック（緑色のアイコンが付いたもの）を選択して、手動でシャットダウンする必要があるかもしれません。TensorFlow を使っていた実行中のノートブックは、GPU メモリの大部分を握ったままになっている可能性があり、それは、新しく始めるノートブックが非常に奇妙な問題に遭遇しうることを意味します。

CUDA、BLAS、cuBLAS についてのエラーが、以前は動いていたコードで出始めたら、これは非常によくある原因です。`nvidia-smi` のようなコマンドで確認できます。現在のノートブックをシャットダウンまたは再起動したときに、メモリのほとんどは空いていますか、それともまだ使われていますか？まだ使われているなら、何か他のものがメモリを握っています。


### データを（もう一度！）確認する

データから何かを学ぶことが実際に可能でなければ、モデルは何も学習しません。データを壊すバグがあるか、ラベルがランダムに付けられている場合、そのデータセットで学習するモデルはおそらく何も得られません。ここで役立つツールの1つが `tokenizer.decode()` です。これにより `input_ids` が文字列に戻るので、データを見て、学習データが教えたいことを教えているかどうかを確認できます。たとえば、上のように `tf.data.Dataset` から `batch` を取得したら、最初の要素を次のようにデコードできます。

```py
input_ids = batch["input_ids"].numpy()
tokenizer.decode(input_ids[0])

次に、それを最初のラベルと比較できます。

labels = batch["labels"].numpy()
label = labels[0]

このようにデータを表示できるようになったら、次の質問を自分に投げかけてみてください。

  • デコードされたデータは理解できますか？
  • ラベルに同意できますか？
  • 他より一般的なラベルはありますか？
  • モデルがランダムな答えや常に同じ答えを予測した場合、損失や指標はどうなりますか？

データを見た後は、モデルの予測をいくつかたどってみてください。モデルがトークンを出力する場合は、それらもデコードしてみましょう。モデルが常に同じものを予測している場合、それはデータセットがあるカテゴリに偏っているためかもしれません（分類問題の場合）。そのため、まれなクラスのオーバーサンプリングのようなテクニックが役立つことがあります。あるいは、悪いハイパーパラメータ設定のような学習の問題が原因である場合もあります。

学習前の初期モデルの損失や指標が、ランダムな予測に期待する値と大きく異なる場合は、損失や指標の計算方法を再確認してください。おそらくそこにバグがあります。最後に加算する複数の損失を使っている場合は、それらが同じスケールであるか確認してください。

データが完璧だと確信したら、モデルがそのデータで学習できるかどうかを、1つのシンプルなテストで確認できます。

モデルを1つのバッチに過学習させる

過学習は、通常は学習時に避けようとするものです。モデルが、学習してほしい一般的な特徴を認識することを学ぶのではなく、学習サンプルをただ記憶してしまうことを意味するからです。しかし、モデルを同じ1つのバッチで何度も学習させてみるのは、自分が組み立てた問題を、学習させようとしているモデルで解けるかどうかを確認するよいテストです。初期の学習率が高すぎないかを見る助けにもなります。

model を定義したら、これは本当に簡単です。学習データのバッチを1つ取得し、その batch をデータセット全体として扱い、多数のエポックで学習させるだけです。

for batch in train_dataset:
    break

# model.compile() を実行し、オプティマイザを設定済みであることを確認してください。
# 損失や指標を使う場合は、それらも設定してください

model.fit(batch, epochs=20)

💡 ヒント

💡 学習データが不均衡な場合は、すべてのラベルを含む学習データのバッチを必ず作ってください。

結果のモデルは、batch に対してほぼ完璧な結果を示し、損失は0（または使用している損失の最小値）に向かってすばやく下降するはずです。

このテストでモデルがほぼ完璧な結果を出せない場合、それは問題の組み立て方かデータに何か問題があることを意味するので、それを修正すべきです。過学習テストに合格して初めて、モデルが実際に何かを学習できると確信できます。

⚠️ 注意

⚠️ この過学習テストの後は、モデルを再作成し、再コンパイルする必要があります。得られたモデルは、おそらく回復して、完全なデータセットで有益なものを学習することはできないでしょう。

最初のベースラインが出るまで何もチューニングしない

集中的なハイパーパラメータチューニングは、機械学習で最も難しい部分だとしばしば強調されますが、実際には評価指標をさらに改善するため、最後に取り組む調整作業にすぎません。もちろん、デフォルトの Adam の学習率 1e-3 を Transformer モデルに使うような、ハイパーパラメータの_非常に_悪い値は、学習を非常に遅くしたり完全に停滞させたりします。しかし、ほとんどの場合、学習率が 1e-5 から 5e-5 のような「妥当な」ハイパーパラメータで、データセットについて持っているベースラインを上回るよい結果が十分に得られます。ですから、データセットについて持っているベースラインを上回るものが得られるまで、時間とコストのかかるハイパーパラメータ探索に乗り出さないでください。

十分に良いモデルが得られたら、少しずつ調整を始めることができます。異なるハイパーパラメータで千回も実行しようとはせず、1つのハイパーパラメータについて異なる値の実行をいくつか比較して、どれが最も影響が大きいか感触をつかんでください。

モデル自体を調整する場合は、シンプルに保ち、合理的に正当化できないことは試さないでください。変更が意図しない結果を招いていないか確認するために、過学習テストに常に戻ってください。
