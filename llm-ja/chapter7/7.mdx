## データを準備する[[preparing-the-data]]

### 学習データを処理する[[processing-the-training-data]]

この例のコンテキストは長くありません。しかし、データセットには、設定した最大長（この場合は384）を超える長いコンテキストを持つサンプルもあります。長いコンテキストへの対処法は、[Chapter 6](/course/chapter6/4) で `question-answering` pipeline の内部を調べた際に扱いました。1つのサンプルからスライディングウィンドウで複数の学習用特徴量を作成する方法です。

現在の例でこの方法の動きを確認する為に、長さを100に制限し、50トークンのスライディングウィンドウを使います。使用する引数は次の通りです。

- 最大長を設定する `max_length`（ここでは100）
- 質問とコンテキストが長過ぎる場合に（2番目の位置にある）コンテキストを切り捨てる `truncation="only_second"`
- 連続する2つのチャンク間で重なるトークン数を設定する `stride`（ここでは50）
- あふれたトークンを返すことをトークナイザに指定する `return_overflowing_tokens=True`

```py
inputs = tokenizer(
    question,
    context,
    max_length=100,
    truncation="only_second",
    stride=50,
    return_overflowing_tokens=True,
)

for ids in inputs["input_ids"]:
    print(tokenizer.decode(ids))
```

長いコンテキストをこの方法で扱うと、答えがコンテキストに含まれない学習サンプルも生じます。その場合のラベルは `start_position = end_position = 0` です。これは `[CLS]` トークンを予測することに当たります。答えが切り捨てられ、開始部分（又は終了部分）しか残らない場合も、同じラベルを設定します。答えが完全にコンテキスト内に含まれる場合は、答えが始まるトークンのインデックスと、答えが終わるトークンのインデックスがラベルになります。

データセットには、コンテキスト内での答えの開始文字が記録されています。開始文字に答えの長さを加えると、終了文字が得られます。開始文字と終了文字をトークンのインデックスに対応付けるには、[Chapter 6](/course/chapter6/4) で学んだオフセットマッピングを使います。トークナイザに `return_offsets_mapping=True` を渡すと、オフセットマッピングが返ります。

```py
inputs = tokenizer(

    stride=50,
    return_overflowing_tokens=True,
    return_offsets_mapping=True,
```


返されるのは、通常の入力 ID、トークンタイプ ID、アテンションマスクに加えて、要求したオフセットマッピングと、追加のキー `overflow_to_sample_mapping` です。このキーの値は、複数のテキストを同時にトークン化する際に使います。トークナイザが Rust に基づく利点を活かす為にも、トークン化はまとめて行うのが適切です。1つのサンプルから複数の特徴量が生まれる場合がある為、この値は各特徴量がどのサンプルに由来するかを表します。ここではサンプルを1つだけトークン化したので、得られるのは `0` のリストです。

```py

```


複数のサンプルをトークン化すると、この値が役立ちます。

```py

    raw_datasets["train"][2:6]["context"],

print(f"4つのサンプルから {len(inputs['input_ids'])} 個の特徴量が得られました。")
print(f"それぞれの由来は次のとおりです: {inputs['overflow_to_sample_mapping']}.")
```

最初の3つのサンプル（学習セットのインデックス2、3、4）は、それぞれ4つの特徴量を生みました。最後のサンプル（学習セットのインデックス5）は、7つの特徴量を生みました。

この対応付けを使って、各特徴量にラベルを割り当てます。ラベルの決め方は次の通りです。

- 答えがコンテキストの対応する範囲にない場合は `(0, 0)`
- 答えがコンテキストの対応する範囲に在る場合は `(start_position, end_position)`。ここで `start_position` は答えの開始位置に在るトークンの（入力 ID における）インデックス、`end_position` は答えが終わるトークンのインデックスです

どちらの場合に当たるかと、当たる場合のトークン位置を決めるには、まず入力 ID の中でコンテキストが始まる位置と終わる位置を求めます。求め方にはトークンタイプ ID を使う方法もあります。しかし、トークンタイプ ID は全てのモデルに存在するとは限りません。例えば DistilBERT はトークンタイプ ID を必要としません。そこで、トークナイザが返す `BatchEncoding` の `sequence_ids()` メソッドを使います。

次に、各トークンに対応するオフセットを見ます。オフセットは、元のコンテキスト内での文字範囲を表す2つの整数のタプルです。オフセットからは、この特徴量に含まれるコンテキストが答えより後から始まっているか、答えが始まる前に終わっているかを判定出来ます。どちらかに当たる場合、答えはこの範囲に無く、ラベルは `(0, 0)` です。どちらにも当たらない場合は、範囲内を走査して答えの最初と最後のトークンを求めます。

```py
answers = raw_datasets["train"][2:6]["answers"]
start_positions = []
end_positions = []

for i, offset in enumerate(inputs["offset_mapping"]):
    sample_idx = inputs["overflow_to_sample_mapping"][i]
    answer = answers[sample_idx]
    start_char = answer["answer_start"][0]
    end_char = answer["answer_start"][0] + len(answer["text"][0])
    sequence_ids = inputs.sequence_ids(i)

    # コンテキストの開始と終了を見つける
    idx = 0
    while sequence_ids[idx] != 1:
        idx += 1
    context_start = idx
    while sequence_ids[idx] == 1:
        idx += 1
    context_end = idx - 1

    # 答えがコンテキスト内に完全には含まれない場合、ラベルは (0, 0)
    if offset[context_start][0] > start_char or offset[context_end][1] < end_char:
        start_positions.append(0)
        end_positions.append(0)
    else:
        # そうでない場合は、開始と終了のトークン位置
        idx = context_start
        while idx <= context_end and offset[idx][0] <= start_char:
            idx += 1
        start_positions.append(idx - 1)

        idx = context_end
        while idx >= context_start and offset[idx][1] >= end_char:
            idx -= 1
        end_positions.append(idx + 1)

start_positions, end_positions
```

```python out
 [85, 53, 21, 0, 0, 70, 33, 0, 40, 0, 0, 0, 68, 35, 0, 0, 0, 0, 0])
```

この方法が正しいかどうかを、いくつかの結果で確認します。最初の特徴量のラベルは `(83, 85)` です。データセットに記録された正解と、83から85（両端を含む）までのトークンをデコードした文字列を比較します。

```py

answer = answers[sample_idx]["text"][0]

start = start_positions[idx]
end = end_positions[idx]
labeled_answer = tokenizer.decode(inputs["input_ids"][idx][start : end + 1])

print(f"正解: {answer}, ラベルによる答え: {labeled_answer}")
```

ここまでの前処理を関数にまとめ、学習データセット全体に適用します。コンテキストの多くは長く、対応するサンプルは複数の特徴量に分割されます。その為、動的パディングに実質的な利点はありません。全ての特徴量は、設定した最大長までパディングします。

```py
max_length = 384
stride = 128


def preprocess_training_examples(examples):
    questions = [q.strip() for q in examples["question"]]
    inputs = tokenizer(
        questions,
        examples["context"],
        max_length=max_length,
        truncation="only_second",
        stride=stride,
        return_overflowing_tokens=True,
        return_offsets_mapping=True,
        padding="max_length",
    )

    offset_mapping = inputs.pop("offset_mapping")
    sample_map = inputs.pop("overflow_to_sample_mapping")
    answers = examples["answers"]
    start_positions = []
    end_positions = []

    for i, offset in enumerate(offset_mapping):
        sample_idx = sample_map[i]
        answer = answers[sample_idx]
        start_char = answer["answer_start"][0]
        end_char = answer["answer_start"][0] + len(answer["text"][0])
        sequence_ids = inputs.sequence_ids(i)

        # コンテキストの開始と終了を見つける
        idx = 0
        while sequence_ids[idx] != 1:
            idx += 1
        context_start = idx
        while sequence_ids[idx] == 1:
            idx += 1
        context_end = idx - 1

        # 答えがコンテキスト内に完全には含まれない場合、ラベルは (0, 0)
        if offset[context_start][0] > start_char or offset[context_end][1] < end_char:
            start_positions.append(0)
            end_positions.append(0)
        else:
            # そうでない場合は、開始と終了のトークン位置
            idx = context_start
            while idx <= context_end and offset[idx][0] <= start_char:
                idx += 1
            start_positions.append(idx - 1)

            idx = context_end
            while idx >= context_start and offset[idx][1] >= end_char:
                idx -= 1
            end_positions.append(idx + 1)

    inputs["start_positions"] = start_positions
    inputs["end_positions"] = end_positions
    return inputs
```

この関数では、使用する最大長とスライディングウィンドウの長さを決める2つの定数を定義しています。トークン化の前には、小さな前処理も加えています。SQuAD データセットの一部の質問には、冒頭と末尾に余分な空白が含まれます。余分な空白に意味はありません。RoBERTa のようなモデルでトークン化すると、空白が場所を取るだけです。その為、余分な空白は取り除いています。

### 検証データを処理する[[processing-the-validation-data]]

検証データの前処理は、学習データより少し簡単です。ラベルを生成する必要がない為です。検証の損失を計算する使い方もありますが、その数値はモデルの良し悪しを判断する材料にはあまりなりません。検証データで中心になるのは、モデルの予測を元のコンテキストの範囲として解釈する処理です。この処理には、オフセットマッピングと、作成した各特徴量を元のサンプルに対応付ける方法の両方が必要です。元のデータセットには ID 列がある為、対応付けにはその ID を使います。

ここで加える処理は、オフセットマッピングの小さな整理だけです。オフセットマッピングには、質問とコンテキストの両方のオフセットが含まれます。しかし、後処理の段階では、入力 ID のどの部分がコンテキストで、どの部分が質問だったかを知る方法がありません。`sequence_ids()` メソッドはトークナイザの出力に対してのみ使える為です。そこで、質問に対応するオフセットは `None` に設定します。

```py
def preprocess_validation_examples(examples):
    questions = [q.strip() for q in examples["question"]]
    inputs = tokenizer(
        questions,
        examples["context"],
        max_length=max_length,
        truncation="only_second",
        stride=stride,
        return_overflowing_tokens=True,
        return_offsets_mapping=True,
        padding="max_length",
    )

    sample_map = inputs.pop("overflow_to_sample_mapping")
    example_ids = []

    for i in range(len(inputs["input_ids"])):
        sample_idx = sample_map[i]
        example_ids.append(examples["id"][sample_idx])

        sequence_ids = inputs.sequence_ids(i)
        offset = inputs["offset_mapping"][i]
        inputs["offset_mapping"][i] = [
            o if sequence_ids[k] == 1 else None for k, o in enumerate(offset)
        ]

    inputs["example_id"] = example_ids
    return inputs
```

モデルは、入力 ID における答えの開始位置と終了位置のロジットを出力します。これは [`question-answering` pipeline](/course/chapter6/3b) の内部を調べた際に見た通りです。後処理の手順はその際の処理と似ています。まず、行った操作を簡単に振り返ります。

- コンテキスト外のトークンに対応する開始と終了のロジットをマスクしました。
- 次に、ソフトマックスを使って開始と終了のロジットを確率に変換しました。
- 対応する2つの確率の積を取ることで、各 `(start_token, end_token)` ペアにスコアを与えました。
- 有効な答えが得られる（例: `start_token` が `end_token` より小さい）ペアの中で、スコアが最大のものを探しました。

ここでは、この処理を少し変更します。実際のスコアは必要ありません。必要なのは予測された答えだけです。その為、ソフトマックスのステップは省略出来ます。高速化の為、スコアを付ける対象も絞ります。可能な全ての `(start_token, end_token)` ペアではなく、上位の `n_best` 個のロジット（`n_best=20`）に対応するペアだけにスコアを付けます。ソフトマックスを省略する為、スコアはロジットのままです。スコアは、開始のロジットと終了のロジットの合計で得られます（規則 \\(\log(ab) = \log(a) + \log(b)\\)).

この後処理を示すには、予測の実例が必要です。モデルはまだ学習していません。そこで、QA pipeline のデフォルトモデルを使い、検証セットの一部について予測を生成します。処理には前と同じ関数が使えます。この関数はグローバル定数 `tokenizer` に依存します。その為、そのオブジェクトを、一時的に使いたいモデルのトークナイザに差し替えます。

対応付けが出来たら、予測された答えを求める処理に入ります。全てのサンプルを走査し、各サンプルについて、関連する全ての特徴量を走査します。開始と終了の上位 `n_best` 個のロジットについてロジットスコアを調べます。但し、次の位置は除外します。

- 答えがコンテキストの中に入らないもの
- 答えの長さが負になるもの
- 答えが長過ぎるもの（可能性を `max_answer_length=30` に制限します）

```python
import numpy as np

n_best = 20
max_answer_length = 30
predicted_answers = []

for example in small_eval_set:
    example_id = example["id"]
    context = example["context"]
    answers = []

    for feature_index in example_to_features[example_id]:
        start_logit = start_logits[feature_index]
        end_logit = end_logits[feature_index]
        offsets = eval_set["offset_mapping"][feature_index]

        start_indexes = np.argsort(start_logit)[-1 : -n_best - 1 : -1].tolist()
        end_indexes = np.argsort(end_logit)[-1 : -n_best - 1 : -1].tolist()
        for start_index in start_indexes:
            for end_index in end_indexes:
                # 答えがコンテキスト内に完全には含まれないものはスキップする
                if offsets[start_index] is None or offsets[end_index] is None:
                    continue
                # 長さが 0 未満、または max_answer_length を超える答えはスキップする
                if (
                    end_index < start_index
                    or end_index - start_index + 1 > max_answer_length
                ):
                    continue

                answers.append(
                    {
                        "text": context[offsets[start_index][0] : offsets[end_index][1]],
                        "logit_score": start_logit[start_index] + end_logit[end_index],
                    }
                )

    best_answer = max(answers, key=lambda x: x["logit_score"])
    predicted_answers.append({"id": example_id, "prediction_text": best_answer["text"]})
```

```python
from tqdm.auto import tqdm


def compute_metrics(start_logits, end_logits, features, examples):
    example_to_features = collections.defaultdict(list)
    for idx, feature in enumerate(features):
        example_to_features[feature["example_id"]].append(idx)

    predicted_answers = []
    for example in tqdm(examples):
        example_id = example["id"]
        context = example["context"]
        answers = []

        # そのサンプルに関連付けられたすべての特徴量をループする
        for feature_index in example_to_features[example_id]:
            start_logit = start_logits[feature_index]
            end_logit = end_logits[feature_index]
            offsets = features[feature_index]["offset_mapping"]

            start_indexes = np.argsort(start_logit)[-1 : -n_best - 1 : -1].tolist()
            end_indexes = np.argsort(end_logit)[-1 : -n_best - 1 : -1].tolist()
            for start_index in start_indexes:
                for end_index in end_indexes:
                    # 答えがコンテキスト内に完全には含まれないものはスキップする
                    if offsets[start_index] is None or offsets[end_index] is None:
                        continue
                    # 長さが 0 未満、または max_answer_length を超える答えはスキップする
                    if (
                        end_index < start_index
                        or end_index - start_index + 1 > max_answer_length
                    ):
                        continue

                    answer = {
                        "text": context[offsets[start_index][0] : offsets[end_index][1]],
                        "logit_score": start_logit[start_index] + end_logit[end_index],
                    }
                    answers.append(answer)

        # 最もスコアの良い答えを選択する
        if len(answers) > 0:
            best_answer = max(answers, key=lambda x: x["logit_score"])
            predicted_answers.append(
                {"id": example_id, "prediction_text": best_answer["text"]}
            )
        else:
            predicted_answers.append({"id": example_id, "prediction_text": ""})

    theoretical_answers = [{"id": ex["id"], "answers": ex["answers"]} for ex in examples]
    return metric.compute(predictions=predicted_answers, references=theoretical_answers)
```

ログインが終わったら、`TrainingArguments` を定義出来ます。メトリクスを計算する関数を定義した際に述べたように、`compute_metrics()` 関数のシグネチャの為、通常の評価ループは持てません。独自の `Trainer` サブクラスを書けば評価ループを持てます。その方法は[質問応答のサンプルスクリプト](https://github.com/huggingface/transformers/blob/master/examples/pytorch/question-answering/trainer_qa.py)にあります。但し、このセクションで扱うには少し長過ぎます。ここでは学習の最後にのみモデルを評価します。通常の評価の方法は、下の「カスタム学習ループ」で示します。

この制約は、`Trainer` API の限界です。クラスを特定の用途に合わせてカスタマイズするのは骨が折れます。一方、Accelerate ライブラリのように学習ループが全て公開されている場合は、調整は容易です。

`TrainingArguments` の内容は次の通りです。

```python
from transformers import TrainingArguments

args = TrainingArguments(
    "bert-finetuned-squad",
    evaluation_strategy="no",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
    fp16=True,
    push_to_hub=True,
)
```

これらの項目の殆どは以前にも出てきたものです。ハイパーパラメータとして、学習率、学習するエポック数、重み減衰などを設定しています。併せて、各エポックの終了時にモデルを保存すること、評価をスキップすること、結果を Model Hub にアップロードすることを指定しています。`fp16=True` は混合精度の学習を有効にする指定です。最近の GPU では、混合精度により学習をかなり高速化出来ます。

{:else}

```python
from transformers import create_optimizer
from transformers.keras_callbacks import PushToHubCallback
import tensorflow as tf

# 学習ステップ数は、データセットのサンプル数をバッチサイズで割ってから
# 総エポック数を掛けたものです。ここでの tf_train_dataset はバッチ化された tf.data.Dataset であり、
# 元の Hugging Face Dataset ではないため、その len() はすでに num_samples // batch_size です。

num_train_steps = len(tf_train_dataset) * num_train_epochs

    init_lr=2e-5,

# 混合精度 float16 で学習する
tf.keras.mixed_precision.set_global_policy("mixed_float16")
```

## カスタム学習ループ[[a-custom-training-loop]]

完全な学習ループを示します。学習ループを直接書けば、必要な部分を簡単にカスタマイズ出来ます。この学習ループは、評価ループを除いて、[Chapter 3](/course/chapter3/4) の学習ループとよく似ています。`Trainer` クラスの制約を受けない為、モデルを定期的に評価出来ます。

### 学習のための準備をする[[preparing-everything-for-training]]

まず、データセットから `DataLoader` を構築します。データセットの形式は `"torch"` に設定します。検証セットからは、モデルが使わない列を取り除きます。次に、Transformers が提供する `default_data_collator` を `collate_fn` として使います。学習セットはシャッフルしますが、検証セットはシャッフルしません。

```py
from torch.utils.data import DataLoader
from transformers import default_data_collator

train_dataset.set_format("torch")
validation_set = validation_dataset.remove_columns(["example_id", "offset_mapping"])
validation_set.set_format("torch")

train_dataloader = DataLoader(
    train_dataset,
    shuffle=True,
    collate_fn=default_data_collator,
    batch_size=8,
)
eval_dataloader = DataLoader(
    validation_set, collate_fn=default_data_collator, batch_size=8
)
```

次に、モデルを再びインスタンス化します。BERT の事前学習済みモデルから始める為です。前のファインチューニングの続きから始めることはしません。

```py
model = AutoModelForQuestionAnswering.from_pretrained(model_checkpoint)
```

次に、オプティマイザを用意します。オプティマイザには古典的な `AdamW` を使います。これは Adam に似ていますが、重み減衰の適用方法に修正が加えられています。

```py
from torch.optim import AdamW

optimizer = AdamW(model.parameters(), lr=2e-5)
```

これらのオブジェクトが全て揃ったら、`accelerator.prepare()` メソッドに送ることが出来ます。Colab ノートブックで TPU を使って学習する場合は、このコードを全て学習関数の中に移動する必要があります。その場合、`Accelerator` をインスタンス化するセルは一切実行してはいけません。混合精度の学習は、`Accelerator` に `fp16=True` を渡すことで強制出来ます。スクリプトとしてコードを実行している場合は、Accelerate の `config` を適切に設定してください。

```py
from accelerate import Accelerator

accelerator = Accelerator(fp16=True)
model, optimizer, train_dataloader, eval_dataloader = accelerator.prepare(
    model, optimizer, train_dataloader, eval_dataloader
)
```

学習ステップ数を `train_dataloader` の長さから計算出来るのは、それが `accelerator.prepare()` メソッドを経た後だけです。これは前のセクションで確認した通りです。スケジュールには、前のセクションと同じ線形スケジュールを使います。

```py
from transformers import get_scheduler

num_train_epochs = 3
num_update_steps_per_epoch = len(train_dataloader)
num_training_steps = num_train_epochs * num_update_steps_per_epoch

lr_scheduler = get_scheduler(
    "linear",
    optimizer=optimizer,
    num_warmup_steps=0,
    num_training_steps=num_training_steps,
)
```

モデルを Hub にプッシュするには、作業フォルダ内に `Repository` オブジェクトを作成する必要があります。まだログインしていない場合は、まず Hugging Face Hub にログインしてください。リポジトリ名は、モデルに付けたいモデル ID から決まります。`repo_name` は自由に置き換えてかまいません。但し、ユーザー名を含む必要があります。ユーザー名を含める処理を行うのが `get_full_repo_name()` 関数です。

```py
from huggingface_hub import Repository, get_full_repo_name

model_name = "bert-finetuned-squad-accelerate"
repo_name = get_full_repo_name(model_name)
repo_name
```

```python out
'sgugger/bert-finetuned-squad-accelerate'
```

次に、そのリポジトリをローカルフォルダにクローン出来ます。既に存在する場合は、そのローカルフォルダは作業対象リポジトリのクローンである必要があります。

```py
output_dir = "bert-finetuned-squad-accelerate"
repo = Repository(output_dir, clone_from=repo_name)
```

`repo.push_to_hub()` メソッドを呼ぶと、`output_dir` に保存したものをアップロード出来ます。これにより、各エポックの終了時に中間モデルをアップロード出来ます。

## 学習ループ[[training-loop]]

完全な学習ループを書く準備が整いました。ループは3つの部分から構成されます。最初に、学習の進み具合を追うプログレスバーを定義します。

- 学習そのもの。`train_dataloader` に対する古典的な反復、モデルを通じた順伝播、それに続く逆伝播とオプティマイザのステップです。
- 評価。`start_logits` と `end_logits` の値を全て集め、NumPy 配列に変換します。評価ループが終わったら、全ての結果を連結します。`Accelerator` が末尾にサンプルを追加している場合がある為、結果は切り捨てます。末尾へのサンプルの追加は、各プロセスでサンプル数を同じにする為に行われます。
- 保存とアップロード。まずモデルとトークナイザを保存し、次に `repo.push_to_hub()` を呼びます。前と同様に、引数 `blocking=False` を使って、Hub ライブラリに非同期プロセスでプッシュするよう伝えます。こうすると、学習は通常通り続き、この（長い）命令はバックグラウンドで実行されます。

学習ループの完全なコードは次の通りです。

```py
from tqdm.auto import tqdm
import torch

progress_bar = tqdm(range(num_training_steps))

for epoch in range(num_train_epochs):
    # 学習
    model.train()
    for step, batch in enumerate(train_dataloader):
        outputs = model(**batch)
        loss = outputs.loss
        accelerator.backward(loss)

        optimizer.step()
        lr_scheduler.step()
        optimizer.zero_grad()
        progress_bar.update(1)

    # 評価
    model.eval()
    start_logits = []
    end_logits = []
    accelerator.print("評価！")
    for batch in tqdm(eval_dataloader):
        with torch.no_grad():
            outputs = model(**batch)

        start_logits.append(accelerator.gather(outputs.start_logits).cpu().numpy())
        end_logits.append(accelerator.gather(outputs.end_logits).cpu().numpy())

    start_logits = np.concatenate(start_logits)
    end_logits = np.concatenate(end_logits)
    start_logits = start_logits[: len(validation_dataset)]
    end_logits = end_logits[: len(validation_dataset)]

    metrics = compute_metrics(
        start_logits, end_logits, validation_dataset, raw_datasets["validation"]
    )
    print(f"エポック {epoch}:", metrics)

    # 保存とアップロード
    accelerator.wait_for_everyone()
    unwrapped_model = accelerator.unwrap_model(model)
    unwrapped_model.save_pretrained(output_dir, save_function=accelerator.save)
    if accelerator.is_main_process:
        tokenizer.save_pretrained(output_dir)
        repo.push_to_hub(
            commit_message=f"Training in progress epoch {epoch}", blocking=False
        )
```

Accelerate で保存されたモデルを初めて扱う場合の為に、保存に伴う3行のコードを説明します。

```py
accelerator.wait_for_everyone()
unwrapped_model = accelerator.unwrap_model(model)
unwrapped_model.save_pretrained(output_dir, save_function=accelerator.save)
```

最初の行は自明です。全てのプロセスに、全員がその段階に到達するまで待ってから続行するよう伝えます。これは、保存前に全てのプロセスで同じモデルを持つことを確実にする為です。

次に、`unwrapped_model` を取得します。これは、定義したベースモデルそのものです。`accelerator.prepare()` メソッドはモデルを分散学習用に変更する為、変更後のモデルには `save_pretrained()` メソッドがありません。`accelerator.unwrap_model()` メソッドは、この変更を元に戻します。最後に `save_pretrained()` を呼びます。その際、保存には `torch.save()` ではなく `accelerator.save()` を使うよう指定します。

以上で学習は完了です。得られるモデルは、`Trainer` で学習したモデルとかなり似た結果を出すはずです。このコードで学習したモデルは [*huggingface-course/bert-finetuned-squad-accelerate*](https://huggingface.co/huggingface-course/bert-finetuned-squad-accelerate) で確認出来ます。学習ループへの調整を試す場合は、上のコードを編集して直接実装出来ます。

## ファインチューニングしたモデルを使う[[using-the-fine-tuned-model]]

Model Hub 上でファインチューニングしたモデルを推論ウィジェットで使う方法は、既に示しました。ローカルで `pipeline` を使って推論する場合は、モデル識別子を指定します。

```py

context = """
🤗 Transformers is backed by the three most popular deep learning libraries — Jax, PyTorch and TensorFlow — with a seamless integration
between them. It's straightforward to train your models with one before loading them for inference with the other.
"""
question = "Which deep learning libraries back 🤗 Transformers?"
question_answerer(question=question, context=context)
```
