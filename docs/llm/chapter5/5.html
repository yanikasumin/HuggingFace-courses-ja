独自のデータセットを作成する

NLP アプリケーションに必要なデータセットが存在しない時は、自分で作る必要があります。このセクションでは、GitHub リポジトリのバグや機能追加の対応状況を追跡する為によく使われる GitHub issues を集めて、コーパスを作る方法を紹介します。このコーパスには、次のような使い道があります。

  • オープンな issue やプルリクエストをクローズするのにかかる時間を調べる
  • issue の説明文に基づいて、"bug"、"enhancement"、"question" などのメタデータ（ラベル）を付けるマルチラベル分類器を訓練する
  • ユーザーのクエリに一致する issue を探すセマンティック検索エンジンを作る

ここではコーパスの作成に焦点を当て、次のセクションでセマンティック検索アプリケーションに取り組みます。今回は少し趣向を凝らして、人気のオープンソースプロジェクトである 🤗 Datasets 自身の GitHub issues を題材にします。データの取得方法と、これらの issue にどのような情報が含まれているかを見ていきましょう。

データの取得

Datasets の全ての issue は、リポジトリの Issues タブに移動すれば確認出来ます。次のスクリーンショットに示すように、執筆時点では331件のオープンな issue と668件のクローズされた issue がありました。

いずれかの issue をクリックすると、そのタイトルや説明、issue の内容を表すラベルが表示されます。下のスクリーンショットはその一例です。

リポジトリの全ての issue をダウンロードするには、GitHub REST API を使って Issues エンドポイントをポーリングします。このエンドポイントは JSON オブジェクトのリストを返し、各オブジェクトにはタイトルと説明のほか、issue のステータスに関するメタデータなど、多数のフィールドが含まれています。

issue をダウンロードするには、Python で HTTP リクエストを送る際によく使われる requests ライブラリが便利です。次のコマンドでインストール出来ます。

GitHub の[ドキュメント](https://docs.github.com/en/rest/overview/resources-in-the-rest-api#rate-limiting)に記載されているように、認証されていないリクエストは1時間あたり60リクエストに制限されます。`per_page` クエリパラメータを増やしてリクエスト回数を減らすことは出来ますが、数千件を超える issue を持つリポジトリでは、それでもレート制限に引っかかります。そこで、GitHub の[手順](https://docs.github.com/en/github/authenticating-to-github/creating-a-personal-access-token)に従って個人アクセストークンを作成し、レート制限を1時間あたり5,000リクエストまで引き上げるべきです。トークンが用意出来たら、リクエストヘッダの一部として含めることが出来ます。

```py
GITHUB_TOKEN = xxx  # ここに自分の GitHub トークンを貼り付けます
headers = {"Authorization": f"token {GITHUB_TOKEN}"}

⚠️ 注意

⚠️ GITHUB_TOKEN を貼り付けたノートブックを共有しないでください。誤ってこの情報を漏らさないよう、実行後は最後のセルを削除することをお勧めします。更に良いのは、トークンを .env ファイルに保存し、python-dotenv ライブラリを使って環境変数として自動的に読み込む方法です。

アクセストークンが用意出来たので、GitHub リポジトリから全ての issue をダウンロード出来る関数を作りましょう。

import time
import math
from pathlib import Path
import pandas as pd
from tqdm.notebook import tqdm


def fetch_issues(
    owner="huggingface",
    repo="datasets",
    num_issues=10_000,
    rate_limit=5_000,
    issues_path=Path("."),
):
    if not issues_path.is_dir():
        issues_path.mkdir(exist_ok=True)

    batch = []
    all_issues = []
    per_page = 100  # 1ページあたりに返す issue の数
    num_pages = math.ceil(num_issues / per_page)
    base_url = "https://api.github.com/repos"

    for page in tqdm(range(num_pages)):
        # state=all でクエリし、オープンとクローズの両方の issue を取得します
        query = f"issues?page={page}&per_page={per_page}&state=all"
        issues = requests.get(f"{base_url}/{owner}/{repo}/{query}", headers=headers)
        batch.extend(issues.json())

        if len(batch) > rate_limit and len(all_issues) < num_issues:
            all_issues.extend(batch)
            batch = []  # 次の期間のためにバッチを空にします
            print(f"GitHub API のレート制限に達しました。1時間待機します...")
            time.sleep(60 * 60 + 1)

    all_issues.extend(batch)
    df = pd.DataFrame.from_records(all_issues)
    df.to_json(f"{issues_path}/{repo}-issues.jsonl", orient="records", lines=True)
    print(
        f"{repo} のすべての issue をダウンロードしました。データセットの保存先: {issues_path}/{repo}-issues.jsonl"
    )

fetch_issues() を呼び出すと、GitHub の1時間あたりのリクエスト数の上限を超えないよう、全ての issue がバッチ単位でダウンロードされます。結果は リポジトリ名-issues.jsonl ファイルに保存され、各行が issue を表す JSON オブジェクトになります。この関数を使って、Datasets の全ての issue を取得しましょう。

素晴らしい。これで初めてのデータセットをゼロから作れました！しかし、Datasets リポジトリの [Issues タブ](https://github.com/huggingface/datasets/issues)には合計で約1,000件の issue しか表示されないのに、何故数千件もの issue が有るのでしょうか？  GitHub の[ドキュメント](https://docs.github.com/en/rest/reference/issues#list-issues-assigned-to-the-authenticated-user)に記載されているように、これはプルリクエストも全てダウンロードしている為です。

> GitHub の REST API v3 では、全てのプルリクエストを issue とみなしますが、全ての issue がプルリクエストであるとは限りません。その為、「Issues」エンドポイントは issue とプルリクエストの両方を返すことがあります。プルリクエストは `pull_request` キーで識別出来ます。なお、「Issues」エンドポイントから取得したプルリクエストの `id` は、プルリクエスト自身の ID ではなく、issue としての ID であることに注意してください。

issue とプルリクエストの内容はかなり異なる為、両者を区別出来るよう、軽い前処理を行いましょう。

## データのクリーニング

def get_comments(issue_number):

    response = requests.get(url, headers=headers)
    return [r["body"] for r in response.json()]

データセットを Hugging Face Hub にアップロードする

拡張したデータセットが用意出来たので、コミュニティと共有する為に Hub にプッシュしましょう！データセットのアップロードは非常に簡単です。Transformers のモデルやトークナイザと同様に、push_to_hub() メソッドを使ってデータセットをプッシュ出来ます。

その為には認証トークンが必要です。まず notebook_login() 関数で Hugging Face Hub にログインすれば取得出来ます。

from huggingface_hub import notebook_login

notebook_login()

これにより、ユーザー名とパスワードを入力出来るウィジェットが作られ、API トークンが ~/.huggingface/token に保存されます。ターミナルでコードを実行している場合は、代わりに CLI でログイン出来ます。

huggingface-cli login

ログイン出来たら、次のように実行してデータセットをアップロード出来ます。

issues_with_comments_dataset.push_to_hub("github-issues")

これ以降は、誰でもリポジトリ ID を load_dataset() の path 引数として渡すだけで、データセットをダウンロード出来ます。

remote_dataset = load_dataset("lewtun/github-issues", split="train")

データセットカードの作成

ドキュメントが十分に整備されたデータセット程、他の人（そして未来の自分！）にとって役立つ可能性が高くなります。ドキュメントがあれば、利用者はそのデータセットが自分のタスクに適しているかを判断したり、使用する際に考えられるバイアスやリスクを評価したり出来ます。

Hugging Face Hub では、この情報は各データセットリポジトリの README.md ファイルに保存されます。このファイルを作成する前に、主に次の2つのステップを行うべきです。

  1. datasets-tagging アプリケーションを使って、YAML 形式のメタデータタグを作成します。これらのタグは Hugging Face Hub の様々な検索機能に使われ、データセットがコミュニティのメンバーに簡単に見つけてもらえるようにします。ここではカスタムデータセットを作成した為、datasets-tagging リポジトリをクローンして、アプリケーションをローカルで実行する必要があります。インターフェースは次のようになっています。
  1. データセットカードの作成に関する Datasets ガイドを読み、テンプレートとして使います。

README.md ファイルは Hub 上で直接作成出来ます。lewtun/github-issues データセットリポジトリには、テンプレートとして参考に出来るデータセットカードがあります。下のスクリーンショットは、記入済みのデータセットカードを示しています。
