評価

SFT 又は LoRA を使った SFT でファインチューニングしたモデルは、標準的なベンチマークで評価すべきです。機械学習エンジニアとしては、対象分野に適した評価項目やベンチマークを体系的に整備し、継続的に管理することが重要です。このページでは、代表的なベンチマークと、それらを使ってモデルを評価する方法を見ていきます。特定のユースケースに合わせたカスタムベンチマークの作り方も扱います。

自動ベンチマーク

自動ベンチマークは、言語モデルが様々なタスクをどの程度こなせるかを、標準化された方法で評価する仕組みです。モデルの性能を理解する出発点として有用ですが、包括的な評価戦略の一部に過ぎないことを認識しておくことが大切です。

自動ベンチマークの理解

自動ベンチマークは通常、予め定義されたタスクと評価メトリクスを持つ、厳選されたデータセットで構成されます。これらのベンチマークは、基本的な言語理解から複雑な推論まで、モデル能力の様々な側面を評価することを目的としています。

自動ベンチマークを使う主な利点は標準化です。異なるモデル間での一貫した比較が出来、再現可能な結果が得られます。

但し、ベンチマークの性能が実世界での有効性にそのまま結びつくとは限らないことを理解しておく必要があります。学術的なベンチマークで優れたモデルでも、特定のドメインの用途や実践的なユースケースでは苦戦することがあります。

汎用知識のベンチマーク

MMLU（Massive Multitask Language Understanding）は、科学から人文科学まで57の科目にわたる知識をテストします。包括的ではありますが、特定のドメインで必要となる専門性の深さを反映しているとは限りません。

TruthfulQA は、モデルが一般的な誤解を再生産する傾向を評価しますが、あらゆる形の誤情報を捉えられる訳ではありません。

推論のベンチマーク

BBH（Big Bench Hard）と GSM8K は、複雑な推論タスクに焦点を当てています。BBH は論理的思考と計画をテストし、GSM8K は特に数学の問題解決を対象とします。これらのベンチマークは分析能力の評価に役立ちますが、実際の場面で必要となる、微妙な条件や文脈を踏まえた推論能力までは十分に評価出来ないことがあります。

言語理解

HELM は、言語モデルを多面的に評価する為のフレームワークです。HELM のようなベンチマークは、常識、世界知識、推論といった側面から、モデルの言語処理能力を把握出来ます。但し、自然な会話の複雑さやドメイン固有の専門用語を完全には表せないことがあります。

ドメイン固有のベンチマーク

数学、コーディング、チャットといった特定のドメインに焦点を当てたベンチマークをいくつか見てみましょう。

MATH ベンチマーク は、数学的推論のもう1つの重要な評価ツールです。代数、幾何、数論、数え上げ、確率などを含む数学コンペティションからの 12,500 問で構成されます。MATH が特に難しいのは、多段階の推論、形式的な数学表記の理解、段階的な解法の生成能力が必要な点です。単純な算術タスクとは異なり、MATH の問題は高度な問題解決戦略と数学概念の応用を求めることが多くあります。

HumanEval ベンチマーク は、164 のプログラミング問題で構成される、コーディングに焦点を当てた評価データセットです。このベンチマークは、与えられたプログラミング課題を解決する、正しく動作する Python コードをモデルが生成出来るかを評価します。HumanEval の特徴は、参照解との表面的な類似度だけでなく、生成されたコードに対して実際にテストケースを実行し、コードが正しく動作するかを評価する点です。問題は、基本的な文字列操作から、より複雑なアルゴリズムやデータ構造まで多岐にわたります。

Alpaca Eval は、指示に従う言語モデルの品質を評価する為に設計された自動評価フレームワークです。GPT-4 を判定者として使い、有用性、正直さ、無害性といった様々な観点でモデルの出力を評価します。このフレームワークは 805 件の厳選されたプロンプトのデータセットを含み、Claude、GPT-4 など複数の参照モデルに対して応答を評価出来ます。Alpaca Eval が特に便利なのは、人間のアノテータを必要とせずに一貫性の有るスケーラブルな評価を提供しながら、従来の評価指標では捉え難い、モデル性能の細かな違いも評価出来る点です。

代替の評価アプローチ

標準ベンチマークの限界に対処する為、多くの組織が代替の評価方法を開発してきました。

LLM-as-Judge

或る言語モデルを使って別のモデルの出力を評価する方法が、ますます普及しています。このアプローチは、従来の指標では捉え難い応答品質の違いを評価出来ますが、評価に用いるモデル自体にも偏りや限界があります。

評価アリーナ

Chatbot Arena のような評価アリーナでは、多数のユーザーから集めた評価を基に LLM の性能を比較します。ユーザーはモデル名を伏せた2つのモデルに質問し、それぞれの回答を比較して、どちらが優れているかに投票します。この方法では、多様で難しい質問を通じて、実際の利用傾向やユーザーの好みを反映した評価が得られます。一般ユーザーの投票結果と専門家による評価がよく一致することも、研究で示されています。

但し、参加者の偏りや質問内容の偏り、安全性よりも有用性を重視し易いことなどが限界として挙げられます。

カスタムベンチマークスイート

組織は、自社の具体的なニーズとユースケースに合わせた内製のベンチマークスイートを開発することがよくあります。ドメイン固有の知識テストや、実際のデプロイ条件を反映した評価シナリオが含まれることもあります。

カスタム評価

標準ベンチマークは有用なベースラインを提供しますが、それだけを評価方法にすべきではありません。より包括的なアプローチの作り方は次の通りです。

  1. 関連する標準ベンチマークから始めてベースラインを確立し、他のモデルと比較出来るようにする

  2. そのユースケース特有の要件と課題を特定する。モデルは実際にどんなタスクを行うのか。どんな種類のエラーが最も問題になるのか

  3. 実際のユースケースを反映したカスタム評価データセットを開発する。例えば次のようなものを含められます： - ドメインにおける実際のユーザーのクエリ - 遭遇したことのある一般的なエッジケース - 特に難しいシナリオの例

  4. 多層的な評価戦略の実装を検討する： - 素早いフィードバックの為の自動メトリクス - 微妙な違いを捉える為の人間による評価 - 専門的な用途の為のドメイン専門家によるレビュー - 管理された環境での A/B テスト

カスタム評価の実装

このセクションでは、ファインチューニングしたモデルの評価を実装します。lighteval を使って、標準ベンチマークでファインチューニングしたモデルを評価出来ます。このライブラリには幅広いタスクが組み込まれています。評価したいタスクと評価のパラメータを定義するだけです。

LightEval のタスクは、特定の形式で定義されます。

{suite}|{task}|{num_few_shot}|{auto_reduce}
パラメータ 説明
suite ベンチマークスイート（例: 'mmlu'、'truthfulqa'）
task スイート内の特定のタスク（例: 'abstract_algebra'）
num_few_shot プロンプトに含める例の数（ゼロショットの場合は 0）
auto_reduce プロンプトが長過ぎる場合に Few-shot の例を自動で減らすかどうか（0 又は 1）

例："mmlu|abstract_algebra|0|0" は、MMLU の abstract algebra タスクをゼロショット推論で評価します。

評価パイプラインの例

ファインチューニングしたモデルの評価パイプラインを構築してみましょう。医療ドメインに関連するサブタスクのセットでモデルを評価します。

Lighteval と VLLM バックエンドを使って、特定の1ドメインに関連する自動ベンチマークで評価する完全な例がこちらです。

lighteval accelerate \
    "pretrained=your-model-name" \
    "mmlu|anatomy|0|0" \
    "mmlu|high_school_biology|0|0" \
    "mmlu|high_school_chemistry|0|0" \
    "mmlu|professional_medicine|0|0" \
    --max_samples 40 \
    --batch_size 1 \
    --output_path "./results" \
    --save_generations true

結果は表形式で表示されます。

|                  Task                  |Version|Metric|Value |   |Stderr|
|----------------------------------------|------:|------|-----:|---|-----:|
|all                                     |       |acc   |0.3333|±  |0.1169|
|leaderboard:mmlu:_average:5             |       |acc   |0.3400|±  |0.1121|
|leaderboard:mmlu:anatomy:5              |      0|acc   |0.4500|±  |0.1141|
|leaderboard:mmlu:high_school_biology:5  |      0|acc   |0.1500|±  |0.0819|

Lighteval には、より詳細な評価タスクの為の Python API も含まれており、結果をより柔軟に扱うのに便利です。詳細は Lighteval のドキュメントを確認して下さい。

章末クイズ

1. モデル評価に自動ベンチマークを使う主な利点は何ですか？

不正解です！自動ベンチマークは有用ですが、実世界のパフォーマンスにそのまま結びつくとは限りません。
正解です！これは自動ベンチマークの重要な利点の1つです。
不正解です！自動ベンチマークは包括的な評価戦略の一部であるべきで、唯一の方法ではありません。

2. 57科目にわたる知識を評価するベンチマークはどれですか？

不正解です！BBH は複雑な推論タスクに焦点を当てており、幅広い科目知識ではありません。
不正解です！GSM8K は特に数学の問題解決を対象としています。
正解です！MMLU（Massive Multitask Language Understanding）は、科学から人文科学まで57科目にわたる知識をテストします。

3. LLM-as-Judge とは何ですか？

正解です！これは、より細かなフィードバックを提供出来る代替の評価アプローチです。
不正解です！LLM-as-Judge とは、或るモデルを使って別のモデルを評価することであり、司法的な推論をテストすることではありません。
不正解です！これは法律データでの学習とは関係がなく、或るモデルを使って別のモデルの出力を評価することです。

4. 包括的な評価戦略に含めるべきなのは何ですか？

不正解です！包括的な戦略には、複数の評価方法を含めるべきです。
正解です！包括的な戦略には、複数層の評価を含めるべきです。
不正解です！カスタムデータセットは重要ですが、それだけを評価方法にすべきではありません。

5. 自動ベンチマークの限界は何ですか？

不正解です！コストは通常、自動ベンチマークの主な限界ではありません。
正解です！これは、自動ベンチマークを使う際に念頭に置くべき重要な限界です。
不正解です！自動ベンチマークは、様々なサイズのモデルの評価に使えます。

6. カスタム評価データセットを作成する目的は何ですか？

正解です！カスタムデータセットを使うことで、評価を実際のニーズに即したものに出来ます。
不正解です！カスタムデータセットは標準ベンチマークを補完するものであり、置き換えるものではありません。
不正解です！カスタムデータセットの作成には追加の労力がかかりますが、より関連性の高い評価が得られます。
