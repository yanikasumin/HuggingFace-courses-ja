MCP のアーキテクチャコンポーネント

前節では、MCP の主要な概念と用語について説明しました。この節では、MCP エコシステムを構成するアーキテクチャコンポーネントをさらに深く掘り下げます。

ホスト、クライアント、サーバー

Model Context Protocol（MCP）は、AI モデルと外部システムの間の構造化された通信を可能にするクライアント・サーバーアーキテクチャの上に構築されています。

MCP のアーキテクチャは3つの主要なコンポーネントで構成されており、それぞれに明確に定義された役割と責務があります。ホスト、クライアント、サーバーです。前節でも触れましたが、ここでは各コンポーネントとその責務を詳しく見ていきます。

ホスト（Host）

ホストは、エンドユーザーが直接操作するユーザー向けの AI アプリケーションです。

例として次のものがあります。 - OpenAI ChatGPT や Anthropic の Claude Desktop のような AI チャットアプリ - Cursor のような AI 強化 IDE や、Continue.dev のようなツールへの統合 - LangChain や smolagents のようなライブラリで構築されたカスタム AI エージェントやアプリケーション

ホストの責務は次のとおりです。 - ユーザーとのやり取りと権限の管理 - MCP クライアントを介した MCP サーバーへの接続の開始 - ユーザーのリクエスト、LLM の処理、外部ツールの間の全体的なフローの統括 - 結果をわかりやすい形式でユーザーに表示すること

多くの場合、ユーザーは自分のニーズや好みに合わせてホストアプリケーションを選択します。たとえば開発者は強力なコード編集機能を求めて Cursor を選ぶかもしれませんし、ドメイン専門家は smolagents で構築されたカスタムアプリケーションを使うかもしれません。

クライアント（Client）

クライアントは、ホストアプリケーション内のコンポーネントで、特定の MCP サーバーとの通信を管理します。主な特徴は次のとおりです。

  • 各クライアントは単一のサーバーと 1:1 の接続を維持します
  • MCP 通信のプロトコルレベルの詳細を処理します
  • ホストのロジックと外部サーバーの間の仲介役として動作します

サーバー（Server）

サーバーは、MCP プロトコルを通じて AI モデルに機能を公開する外部のプログラムまたはサービスです。サーバーは次の特徴を持ちます。

  • 特定の外部ツール、データソース、サービスへのアクセスを提供します
  • 既存の機能を軽量にラップするラッパーとして動作します
  • ローカル（ホストと同じマシン上）でもリモート（ネットワーク越し）でも実行できます
  • クライアントが発見して利用できる標準化された形式で機能を公開します

通信フロー

典型的な MCP ワークフローでこれらのコンポーネントがどのように連携するかを見てみましょう。

💡 ヒント

次節では、実用的な例とともに、これらのコンポーネントを可能にする通信プロトコルを詳しく見ていきます。

  1. ユーザーインタラクション: ユーザーがホストアプリケーションを操作し、意図やクエリを伝えます。

  2. ホストの処理: ホストがユーザーの入力を処理します。場合によっては LLM を使ってリクエストを理解し、どの外部機能が必要になりそうかを判断します。

  3. クライアントの接続: ホストが、そのクライアントコンポーネントに適切なサーバーへの接続を指示します。

  4. 機能の発見: クライアントがサーバーに問い合わせ、そのサーバーが提供する機能（ツール、リソース、プロンプト）を発見します。

  5. 機能の呼び出し: ユーザーのニーズや LLM の判断に基づき、ホストがクライアントにサーバーの特定の機能を呼び出すよう指示します。

  6. サーバーの実行: サーバーがリクエストされた機能を実行し、結果をクライアントに返します。

  7. 結果の統合: クライアントがこれらの結果をホストに中継し、ホストはそれを LLM のコンテキストに組み込むか、ユーザーに直接提示します。

このアーキテクチャの重要な利点はモジュール性です。1つのホストが、異なるクライアントを介して複数のサーバーに同時に接続できます。既存のホストを変更することなく、新しいサーバーをエコシステムに追加できます。機能は異なるサーバー間で簡単に組み合わせられます。

💡 ヒント

前節で説明したとおり、このモジュール性により、従来の M×N 統合問題（M 個の AI アプリケーションが N 個のツール/サービスに接続する問題）は、より扱いやすい M+N 問題へと変わります。各ホストとサーバーは MCP 標準を一度だけ実装すればよいからです。

このアーキテクチャは一見シンプルに見えますが、その力は通信プロトコルの標準化と、コンポーネント間の責務の明確な分離にあります。この設計により、AI モデルが絶えず増え続ける外部ツールやデータソースへとシームレスに接続できる、まとまりのあるエコシステムが実現します。

まとめ

これらの相互作用のパターンは、MCP の設計と進化を形作るいくつかの重要な原則に基づいています。このプロトコルは、AI 接続のための汎用プロトコルを提供することで標準化を重視しつつ、コアプロトコルをわかりやすく保ちながら高度な機能を可能にすることでシンプルさを維持します。安全性は、機密性の高い操作に明示的なユーザーの承認を必須とすることで優先されます。また、発見可能性（discoverability）により、機能の動的な発見が可能になります。このプロトコルは拡張性を念頭に置いて構築されており、バージョニングと機能ネゴシエーションによる進化をサポートし、異なる実装や環境間での相互運用性を保証します。
