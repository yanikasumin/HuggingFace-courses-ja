学習パイプラインをデバッグする

Chapter 7 の説明に従い、或るタスク向けにモデルを学習させるスクリプト、又はファインチューニングするスクリプトを書き上げたとします。trainer.train() を実行すると、エラーが発生することがあります 😱。エラーが発生せず、学習が最後まで進む場合もあります。但し、その場合でも、出来上ったモデルの性能が著しく低いことがあります。このセクションでは、このような問題をデバッグする方法を示します。

学習パイプラインをデバッグする

trainer.train() でエラーが発生した場合、原因の特定は容易ではありません。Trainer は多くの処理をまとめて実行する為、エラーの発生源が複数考えられるからです。

まず、データセットはデータローダに変換されます。この段階の原因としては、データセット自体の誤りや、データセットの要素をバッチにまとめる際の誤りが考えられます。次に、データのバッチがモデルに入力されます。この段階では、モデルコードの誤りが原因になります。その後、勾配が計算され、最適化ステップが実行されます。この段階では、オプティマイザの誤りが原因になります。学習が順調に進んだ場合でも、指標に問題があれば、評価の段階で失敗することがあります。

trainer.train() で発生したエラーをデバッグするには、パイプライン全体を手作業で順に確認し、問題の発生箇所を特定します。発生箇所が分かれば、エラーの解決は容易になることが殆どです。

以下では、次のスクリプトを例に手順を示します。このスクリプトは、MNLI データセットで DistilBERT モデルをファインチューニングしようとするものです。

from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)


trainer = Trainer(
    model,
    args,
    train_dataset=raw_datasets["train"],
    eval_dataset=raw_datasets["validation_matched"],
    compute_metrics=compute_metrics,
)
trainer.train()

### データを確認する

データが壊れている場合、`Trainer` はバッチを作成出来ません。モデルの学習も出来ません。その為、まず学習セットの中身を確認します。

確認には `trainer.train_dataset` だけを使います。他の対象を確認すると、バグの発生源ではない箇所の修正に時間を費やす恐れがあります。

```py
trainer.train_dataset[0]

```python out {'hypothesis': 'Product and geography are what make cream skimming work. ', 'idx': 0, 'label': 1, 'premise': 'Conceptually cream skimming has two basic dimensions - product and geography.'}

（データセットの文の訳：前提文は「概念的には、クリームスキミングには製品と地理という2つの基本的な次元が有ります」、仮説文は「製品と地理こそがクリームスキミングを成り立たせるものです」）

内容に問題があります。エラーメッセージは `input_ids` が無いことを示しています。データセットの中身と合わせると、中身は数値ではなくテキストであることが分かります。モデルはテキストをそのままでは処理出来ません。元のエラーメッセージは、この点で誤解を招きやすいものです。`Trainer` は、モデルのシグネチャに一致しない列を自動で削除します。モデルのシグネチャとは、モデルが期待する引数のことです。その為、この例ではラベル以外の列が全て削除されていました。バッチの作成とモデルへの送信自体には問題がありませんでした。モデルが適切な入力を受け取れなかった為、エラーが発生したのです。

データが処理されなかった理由は、データセットの渡し方の誤りです。各サンプルには、`Dataset.map()` メソッドでトークナイザを適用していました。但し、コードをよく見ると、`Trainer` へ渡していたのは処理済みのデータセットではありませんでした。`raw_datasets` を渡しており、本来は `tokenized_datasets` を渡す必要がありました 🤦。次に、この点を修正します。

### データセットからデータローダへ

次に問題が発生しやすいのは、`Trainer` が学習セットや検証セットからバッチを作成する段階です。`Trainer` のデータセットが正しいことを確認したら、次のコードでバッチを手作業で作成します。検証データローダの場合は、`train` を `eval` に置き換えます。

```py
for batch in trainer.get_train_dataloader():
    break

このコードは、学習データローダを作成し、最初のバッチで反復を停止します。エラーなく実行出来れば、最初の学習バッチを確認出来ます。エラーが発生すれば、問題はデータローダにあります。この例では、エラーが発生します。

```python out ~/git/transformers/src/transformers/data/data_collator.py in torch_default_data_collator(features) 105 batch[k] = torch.stack([f[k] for f in features]) 106 else: --> 107 batch[k] = torch.tensor([f[k] for f in features]) 108 109 return batch

ValueError: expected sequence of length 45 at dim 1 (got 76)

トレースバックの最後のフレームを確認すれば、手がかりは得られます。但し、ここではもう少し詳しく調べます。バッチ作成時の問題は、複数のサンプルを1つのバッチにまとめる処理で発生することが殆どです。その為、最初に確認するのは、使用している `DataLoader` の `collate_fn` です。

```py
data_collator = trainer.get_train_dataloader().collate_fn
data_collator

```python out <function transformers.data.data_collator.default_data_collator(features: List[InputDataClass], return_tensors='pt') -> Dict[str, Any]>

使用されているのは `default_data_collator` です。但し、この例で必要な処理は異なります。必要なのは、サンプルをバッチ内の最も長い文に合わせてパディングすることです。この処理を行うのは `DataCollatorWithPadding` です。このコレータは、`Trainer` が既定で使うはずのものです。それにもかかわらず、ここでは使われていません。

原因は、`Trainer` に `tokenizer` を渡していないことです。その為、必要な `DataCollatorWithPadding` を作成出来ませんでした。この種のエラーを避ける為、使用するデータコレータは明示的に渡します。次に、コードを修正して、データコレータを明示的に渡します。

```py
from datasets import load_dataset
import evaluate
from transformers import (
    AutoTokenizer,
    AutoModelForSequenceClassification,
    DataCollatorWithPadding,
    TrainingArguments,
    Trainer,
)

raw_datasets = load_dataset("glue", "mnli")

model_checkpoint = "distilbert-base-uncased"
tokenizer = AutoTokenizer.from_pretrained(model_checkpoint)


def preprocess_function(examples):
    return tokenizer(examples["premise"], examples["hypothesis"], truncation=True)


tokenized_datasets = raw_datasets.map(preprocess_function, batched=True)
model = AutoModelForSequenceClassification.from_pretrained(model_checkpoint)

args = TrainingArguments(
    f"distilbert-finetuned-mnli",
    evaluation_strategy="epoch",
    save_strategy="epoch",
    learning_rate=2e-5,
    num_train_epochs=3,
    weight_decay=0.01,
)

metric = evaluate.load("glue", "mnli")


def compute_metrics(eval_pred):
    predictions, labels = eval_pred
    return metric.compute(predictions=predictions, references=labels)


data_collator = DataCollatorWithPadding(tokenizer=tokenizer)

trainer = Trainer(
    model,
    args,
    train_dataset=tokenized_datasets["train"],
    eval_dataset=tokenized_datasets["validation_matched"],
    compute_metrics=compute_metrics,
    data_collator=data_collator,
    tokenizer=tokenizer,
)
trainer.train()

修正により、前のエラーは発生しなくなりました。これは前進です。但し、代わりに CUDA エラーが発生します。CUDA エラーは、デバッグが難しいことで知られています。

``python out RuntimeError: CUDA error: CUBLAS_STATUS_ALLOC_FAILED when callingcublasCreate(handle)`

CUDA エラーは、一般にデバッグが非常に困難です。解決方法は後で説明します。まず、バッチ作成の確認を終わらせます。

データコレータが正しいことを確認したら、データセットのサンプルにデータコレータを適用して確認します。

```py
data_collator = trainer.get_train_dataloader().collate_fn
batch = data_collator([trainer.train_dataset[i] for i in range(4)])

このコードは失敗します。train_dataset には文字列の列が含まれており、通常は Trainer が文字列の列を削除する為です。文字列の列は手作業で削除出来ます。Trainer が内部で行う処理をそのまま再現する場合は、その処理を行う非公開メソッド Trainer._remove_unused_columns() を呼びます。

data_collator = trainer.get_train_dataloader().collate_fn
actual_train_set = trainer._remove_unused_columns(trainer.train_dataset)
batch = data_collator([actual_train_set[i] for i in range(4)])

この方法であれば、エラーが続く場合でも、データコレータの内部で起きていることを手作業で確認出来ます。

バッチ作成の確認は終わりました。次に、バッチをモデルに入力します。

モデルに通してみる

バッチは、次のコマンドで取得出来ます。

for batch in trainer.get_train_dataloader():
    break

このコードをノートブックで実行すると、先程と似た CUDA エラーが発生することがあります。その場合は、ノートブックを再起動し、trainer.train() の行を除いて、最後のスニペットを再実行します。これが CUDA エラーの2番目に厄介な点です。カーネルが正常に動作しなくなる為です。最も厄介な点は、デバッグが難しいことです。

理由は、GPU の動作方法にあります。GPU は大量の処理を並列に実行する為、処理は高速です。但し、命令の1つでエラーが発生しても、その時点では検出されません。

エラーが検出されるのは、プログラムが GPU 上の複数のプロセスの同期を行う時点です。その為、エラーの原因となった処理とは無関係に見える場所で、エラーが報告されることがあります。例えば、先程のトレースバックでは、エラーは逆伝播の最中に報告されています。但し、実際の原因はフォワードパスにあります。フォワードパスに原因があることは、後で分かります。

この種の CUDA エラーは、GPU 上ではデバッグしません。メモリ不足エラーを除き、デバッグは CPU 上で行います。メモリ不足エラーとは、GPU のメモリが不足するエラーです。

この例では、モデルを CPU に戻し、バッチを入力として呼び出します。DataLoader が返すバッチは、まだ GPU に移されていません。

最適化ステップを1回実行する

バッチを作成し、モデルに入力出来ることを確認しました。次に、学習パイプラインの次の段階に進みます。勾配を計算し、最適化ステップを実行する段階です。

勾配の計算は、損失に対して backward() メソッドを呼ぶことで行います。

loss = outputs.loss
loss.backward()

この段階でエラーが発生することはまれです。エラーが発生した場合は、CPU 上で実行し直します。CPU 上では、原因の特定に役立つエラーメッセージが得られます。

最適化ステップは、optimizer を作成し、step() メソッドを呼ぶことで実行します。

trainer.create_optimizer()
trainer.optimizer.step()

Trainer の既定のオプティマイザを使用している場合、この段階でエラーが発生することは通常ありません。カスタムのオプティマイザを使用している場合は、この段階に問題がある可能性があります。この段階で奇妙な CUDA エラーが発生した場合は、CPU 上で確認します。CUDA エラーについては、先程、特殊な場合に触れました。次に、その場合を説明します。

CUDA のメモリ不足エラーに対処する

エラーメッセージが RuntimeError: CUDA out of memory で始まる場合、GPU メモリが不足しています。このエラーは、コード自体に直接関係するものではありません。正常に動作するスクリプトでも発生します。原因は、GPU の内部メモリに収まる量を超えてデータを置こうとしたことです。他の CUDA エラーと同様に、学習を再開するにはカーネルを再起動する必要があります。

この問題を解決するには、GPU の使用量を減らします。使用量を減らす方法は、場合によっては容易ではありません。

まず、GPU 上にモデルが2つ同時に置かれていないかを確認します。問題の性質上、複数のモデルが必要な場合を除きます。次に、バッチサイズを減らします。バッチサイズは、モデルの全ての中間出力と、その勾配の大きさに直接影響する為です。問題が続く場合は、より小さいモデルの使用を検討します。

💡 ヒント

💡 手作業の学習ループを使用している場合も、同じ手順で学習パイプラインをデバッグ出来ます。手作業の場合は、手順を分離しやすいという違いがあります。適切な場所で model.eval() と model.train() を呼び忘れていないか、各ステップで zero_grad() を呼び忘れていないかを確認してください。

学習中のサイレントエラーをデバッグする

学習がエラーなく完了しても、良い結果が得られない場合があります。ここでは、その場合の手がかりをいくつか示します。但し、この種のデバッグは機械学習で最も難しい部分であり、決まった解法はありません。

データを（もう一度）確認する

モデルが学習出来るのは、データから実際に学ぶべき内容がある場合に限ります。データを壊すバグがある場合や、ラベルがランダムに付けられている場合は、モデルは何も学習出来ません。その為、まずデコードした入力とラベルを再確認し、次の質問に答えられるかを確認します。

  • デコードされたデータは理解出来ますか？
  • ラベルに同意出来ますか？
  • 他のラベルより多く現れるラベルはありますか？
  • モデルがランダムな答えや常に同じ答えを予測した場合、損失や指標はどうなりますか？

⚠️ 注意

⚠️ 分散学習をしている場合は、各プロセスでデータセットのサンプルを出力し、同じ内容が得られることを確認してください。よくあるバグの1つは、データ作成にランダム性の要素があり、各プロセスでデータセットの内容が異なることです。

データを確認したら、モデルの予測もいくつか確認し、デコードします。モデルが常に同じ予測を返す場合、データセットが或るカテゴリに偏っている可能性があります。分類問題では、この偏りが原因になることがあります。まれなクラスをオーバーサンプリングする手法が役立つことがあります。

初期モデルの損失や指標が、ランダムな予測で期待される値と大きく異なる場合は、損失や指標の計算方法を再確認します。計算方法にバグがある可能性が高い為です。複数の損失を最後に加算している場合は、各損失のスケールが揃っているかを確認します。

データに問題が無いことを確認したら、モデルがそのデータで学習出来るかを、1つの簡単なテストで確認します。

モデルを1つのバッチに過学習させる

過学習とは、モデルが学習サンプルを記憶してしまうことです。学習してほしい一般的な特徴を認識出来るようにはなりません。その為、通常は避けるべきものです。但し、同じ1つのバッチでモデルを繰り返し学習させる方法は、テストとして有用です。組み立てた問題を、使用するモデルで解けるかを確認出来ます。初期の学習率が高過ぎないかを確認する助けにもなります。

Trainer を定義した後は、手順は簡単です。学習データのバッチを1つ取得し、そのバッチだけを使い、20ステップ程度の小さな学習ループを手作業で実行します。

for batch in trainer.get_train_dataloader():
    break

batch = {k: v.to(device) for k, v in batch.items()}
trainer.create_optimizer()

for _ in range(20):
    outputs = trainer.model(**batch)
    loss = outputs.loss
    loss.backward()
    trainer.optimizer.step()
    trainer.optimizer.zero_grad()

💡 ヒント

💡 学習データが不均衡な場合は、全てのラベルを含む学習データのバッチを必ず作ってください。

学習後のモデルは、同じ batch に対してほぼ完璧な結果を示すはずです。予測に対して指標を計算します。

    outputs = trainer.model(**batch)
preds = outputs.logits

compute_metrics((preds.cpu().numpy(), labels.cpu().numpy()))

正解率は100%です。これは過学習の例です。他の文でモデルを試すと、おそらく誤った答えが返ってきます。

このテストでモデルがほぼ完璧な結果を出せない場合は、問題の組み立て方かデータに問題があります。その問題を修正します。過学習テストに合格した場合に限り、モデルが実際に学習出来ると判断出来ます。

⚠️ 注意

⚠️ このテストの後は、モデルと Trainer を再作成してください。テスト後のモデルは回復が難しく、完全なデータセットで有益な学習が出来ない可能性が高い為です。

最初のベースラインが出るまで何もチューニングしない

ハイパーパラメータチューニングは、機械学習で最も難しい部分だと強調されることがよくあります。但し、実際には、指標を少し改善する為の最後の調整に過ぎません。殆どの場合、Trainer の既定のハイパーパラメータで十分に良い結果が得られます。その為、データセットに対するベースラインを上回る結果が得られるまでは、時間とコストのかかるハイパーパラメータ探索は行いません。

十分に良いモデルが得られたら、少しずつ調整を始めます。異なるハイパーパラメータの組み合わせで千回も実行するのではなく、1つのハイパーパラメータについて、値を変えた実行をいくつか比較します。どの値が最も影響が大きいかを確認する為です。

モデル自体を調整する場合は、変更を単純なものに留め、合理的に説明出来ない変更は試しません。変更のたびに過学習テストに戻り、意図しない影響が出ていないかを確認します。
