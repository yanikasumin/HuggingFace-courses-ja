アクション（Actions）：エージェントが環境と関わるための手段

💡 ヒント

このセクションでは、AI エージェントが環境とやり取りするために取る具体的なステップを探ります。

アクションの表現方法（JSON やコードの使用）、stop and parse アプローチの重要性を扱い、さまざまなタイプのエージェントを紹介します。

アクションは、AI エージェントが環境とやり取りするために取る具体的なステップ です。

情報を得るために Web を閲覧するにせよ、物理デバイスを制御するにせよ、各アクションはエージェントが実行する意図的な操作です。

たとえば、カスタマーサービスを支援するエージェントは、顧客データを取得したり、サポート記事を提示したり、課題を人間の担当者に転送したりすることがあります。

エージェントのアクションのタイプ

アクションの取り方が異なる、複数のタイプのエージェントがあります。

エージェントのタイプ 説明
JSON Agent 取るべきアクションが JSON 形式で指定される。
Code Agent エージェントがコードブロックを書き、それが外部で解釈される。
Function-calling Agent JSON Agent のサブカテゴリであり、各アクションごとに新しいメッセージを生成するようファインチューニングされている。

アクション自体も多くの目的に役立ちます。

アクションのタイプ 説明
情報収集（Information Gathering） Web 検索の実行、データベースへのクエリ、ドキュメントの取得を行う。
ツールの使用（Tool Usage） API 呼び出し、計算の実行、コードの実行を行う。
環境とのやり取り（Environment Interaction） デジタルインターフェースの操作や物理デバイスの制御を行う。
コミュニケーション（Communication） チャットでユーザーと関わったり、他のエージェントと協働したりする。

LLM はテキストだけを扱い、それを使って取りたいアクションとツールに渡すパラメータを記述します。エージェントが正しく動作するためには、完全なアクションを定義するすべてのトークンを出力したあと、LLM は新しいトークンの生成を STOP しなければなりません。これにより、制御が LLM からエージェントに戻り、意図した形式（JSON、コード、function calling のいずれか）で結果を解析できることが保証されます。

Stop and Parse アプローチ

アクションを実装する重要な手法の1つが stop and parse アプローチ です。この手法により、エージェントの出力が構造化され、予測可能になります。

  1. 構造化された形式での生成:

エージェントは、意図するアクションを明確で事前に決められた形式（JSON またはコード）で出力します。

  1. それ以上の生成の停止:

アクションを定義するテキストが出力されたら、LLM は追加のトークンの生成を停止します。これにより、余分な出力や誤った出力を防ぎます。

  1. 出力の解析:

外部パーサーが形式化されたアクションを読み取り、呼び出すツールを判別し、必要なパラメータを抽出します。

たとえば、天気を確認する必要があるエージェントは、次のように出力することがあります。

Thought: I need to check the current weather for New York.
Action :
{
  "action": "get_weather",
  "action_input": {"location": "New York"}
}

するとフレームワークは、呼び出す関数の名前と適用する引数を簡単に解析できます。

この明確で機械可読な形式により、エラーが最小化され、外部ツールがエージェントの命令を正確に処理できるようになります。

注意: Function-calling エージェントも同様に動作し、各アクションを指定された関数が正しい引数で呼び出されるよう構造化します。 これらのタイプのエージェントについては、今後のユニットでさらに深く掘り下げます。

Code Agent

別のアプローチとして、Code Agent の使用があります。 考え方はこうです。単純な JSON オブジェクトを出力する代わりに、Code Agent は 実行可能なコードブロック（通常は Python のような高水準言語）を生成します。

このアプローチにはいくつかの利点があります。

  • 表現力: コードはループ、条件分岐、ネストした関数を含む複雑な論理を自然に表現でき、JSON よりも柔軟性が高い。
  • モジュール性と再利用性: 生成されたコードには、異なるアクションやタスクで再利用できる関数やモジュールを含めることができる。
  • デバッグのしやすさの向上: 明確に定義されたプログラミング構文により、コードのエラーは検出と修正が容易なことが多い。
  • 直接的な統合: Code Agent は外部ライブラリや API と直接統合でき、データ処理やリアルタイムの意思決定といった、より複雑な操作が可能になる。

LLM が生成したコードの実行は、プロンプトインジェクションから有害なコードの実行まで、セキュリティリスクを伴う可能性があることに留意しなければなりません。 そのため、デフォルトの安全対策を統合した smolagents のような AI エージェントフレームワークの使用が推奨されます。 リスクとその軽減方法について詳しく知りたい場合は、こちらの専用セクションをご覧ください。

たとえば、天気を取得するタスクを与えられた Code Agent は、次のような Python スニペットを生成することがあります。

# Code Agent の例: 天気情報を取得する
def get_weather(city):
    import requests
    api_url = f"https://api.weather.com/v1/location/{city}?apiKey=YOUR_API_KEY"
    response = requests.get(api_url)
    if response.status_code == 200:
        data = response.json()
        return data.get("weather", "No weather information available")
    else:
        return "Error: Unable to fetch weather data."

# 関数を実行し、最終回答を準備する
result = get_weather("New York")
final_answer = f"The current weather in New York is: {result}"
print(final_answer)

この例では、Code Agent は次のことを行います。

  • API 呼び出し経由で 天気データを取得し、
  • レスポンスを処理し、
  • print() 関数を使って最終回答を出力します。

この方法も、コードブロックを明確に区切り、実行の完了を信号で知らせる（ここでは final_answer を出力することにより）ことで、stop and parse アプローチに従っています。

アクションが、JSON、コード、関数呼び出しのいずれを通じてでも、明確で構造化されたタスクを実行することで、エージェントの内部推論と現実世界でのやり取りを橋渡しすることを学びました。

この意図的な実行により、各アクションが正確で、stop and parse アプローチによる外部処理の準備が整います。次のセクションでは、エージェントが環境からのフィードバックをどう捉えて統合するかを見るために、観察（Observations）を探ります。

そのあとは、ついに初めてのエージェントを構築する準備が整います！
